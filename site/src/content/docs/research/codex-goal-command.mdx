## 研究问题

Codex 的 `/goal` 看起来像一个 slash command，但源码显示它更接近“thread 级长期任务状态机”。这篇记录回答三个问题：

- `/goal` 如何把目标绑定到一个 thread，并跨 turn 延续？
- 哪些动作由模型工具完成，哪些动作由用户或宿主控制？
- 这个设计对我们构建 AgentLab 的研究流程有什么启发？

## 结论摘要

`/goal` 不是普通 prompt 前缀。它由协议对象、持久化表、扩展生命周期 hook、模型工具和内部 steering 模板组成。

用户设置 goal 后，Codex 会把目标写入 thread 级状态。只要状态仍是 `active`，runtime 会在 thread resume 或 idle 时读取该目标，向模型注入内部上下文，并尝试自动启动下一轮工作。模型可以通过 `get_goal` 查看当前目标，通过 `create_goal` 在明确请求下创建目标，通过 `update_goal` 把目标标记为 `complete` 或 `blocked`。暂停、恢复、清除、预算限制和用量限制不是模型随意控制的状态，而是由用户、宿主或系统机制控制。

最值得借鉴的是：Codex 把“目标文本”“完成标准”“进度记账”“续跑条件”“停止条件”拆成了不同层，而不是让模型在自然语言上下文里自己维持所有状态。

## 背景和来源

官方手册把 Goal mode 定义为跨较长任务持续工作的持久目标。目标文本既是起始 prompt，也是完成标准。`/goal` 可在 Codex app、IDE extension 和 CLI 中启动；CLI 支持 `/goal` 查看或设置目标，也支持 `/goal pause`、`/goal resume`、`/goal clear`。目标必须非空，最多 4,000 个字符。

源码阅读基于 `openai/codex` `main` 分支 commit `dac588f41398e8b628d71838d5745dad430477f1`。关键目录是：

- `codex-rs/protocol/src/protocol.rs`：协议对象和事件。
- `codex-rs/ext/goal`：goal extension、工具、runtime、steering 模板。
- `codex-rs/state`：goal 的持久化表和 `GoalStore`。

## 机制拆解

### 1. 协议层：goal 是 thread 级对象

协议层定义了 `ThreadGoalStatus`：`active`、`paused`、`blocked`、`usage_limited`、`budget_limited`、`complete`。`ThreadGoal` 里除了 `objective` 和 `status`，还有 `token_budget`、`tokens_used`、`time_used_seconds`、`created_at`、`updated_at`。这说明 goal 一开始就被设计成可观察、可记账、可跨轮恢复的状态对象，而不是一次性消息。

同一层还定义了 `ThreadGoalUpdatedEvent`。这让宿主 UI 可以订阅 goal 变化，比如在 composer 上方展示进度行，或者在状态变化后刷新按钮。

### 2. 存储层：`thread_goals` 表承载真实状态

状态存储层有独立的 `thread_goals` 表，主键是 `thread_id`。表字段包括：

- `goal_id`：用于区分同一 thread 上不同历史 goal。
- `objective`：目标文本。
- `status`：状态机当前状态。
- `token_budget`、`tokens_used`、`time_used_seconds`：预算和累计用量。
- `created_at_ms`、`updated_at_ms`：生命周期时间。

`GoalStore` 提供 `get_thread_goal`、`replace_thread_goal`、`insert_thread_goal`、`update_thread_goal`、`delete_thread_goal` 和 `account_thread_goal_usage`。其中 `insert_thread_goal` 只会在没有未完成 goal，或现有 goal 已 `complete` 时创建新 goal；这解释了为什么模型不能随便开新目标覆盖旧任务。

### 3. 工具层：模型只能做有限状态迁移

`codex-rs/ext/goal/src/spec.rs` 暴露三个工具：

- `get_goal`：读取当前 goal、状态、预算、已用 token 和剩余预算。
- `create_goal`：只有在用户或系统/开发者明确要求时才创建目标；`token_budget` 也只有明确要求时才设置。
- `update_goal`：只能把目标标记为 `complete` 或 `blocked`。

这条边界很重要。模型不能调用工具来 pause、resume、clear，也不能自封 `budget_limited` 或 `usage_limited`。这些状态属于用户、宿主或系统控制。源码里的工具执行器也会在 `update_goal` 前先做进度记账，再更新状态并发送 `ThreadGoalUpdatedEvent`。

### 4. 宿主层：app/CLI/IDE 通过 `GoalService` 控制目标

`GoalService` 是外部控制面。它支持 get、set、clear thread goal。外部 set goal 时，runtime 会先拿 goal 状态锁，并在写入前对当前 active 或 idle goal 做一次进度记账。这样可以避免一个竞态：系统刚读到旧 goal 准备 idle continuation，而 UI/CLI 同时把 goal 改掉。

当外部设置的状态是 `active` 时，runtime 会标记当前 turn 或 idle goal active，并尝试 `continue_if_idle()`。如果只是编辑了 objective，runtime 会向当前 turn 注入“目标已更新”的 steering，让模型停止沿着旧目标继续跑。

### 5. 运行时层：idle/resume 触发自动续跑

goal extension 挂在 Codex 的 thread、turn、tool 生命周期上：

- thread start：注册 runtime，并根据 feature flag 和 thread 能力决定是否暴露 goal 工具。
- thread resume：如果存储中有 active goal，就恢复 idle active 状态。
- thread idle：调用 `continue_if_idle()`。
- turn start/stop/abort/error：记录当前 turn、累计用量、在错误时停止 goal。
- token usage：记录 token baseline 和增量。
- tool finish：在工具调用后更新 goal progress，必要时注入 budget limit steering。

`continue_if_idle()` 的核心逻辑是：确认工具可见，读取当前 thread 的 goal，只有状态仍是 `active` 才生成 continuation steering，并调用 thread manager 的 `try_start_turn_if_idle`。这就是 `/goal` 能在一个 turn 结束后继续推进的关键。

### 6. Steering 层：goal 是内部上下文，不是高优先级指令

goal runtime 注入的是 `InternalModelContextFragment`，source 为 `goal`。模板反复强调 objective 是用户提供数据，不是更高优先级指令。这是一个安全设计：goal 能持续提醒模型工作目标，但不能把用户文本升级成 system/developer 级别的指令。

continuation 模板还包含两组审计：

- Completion audit：完成前必须按当前状态逐项验证目标、文件、测试、门槛和交付物，不能因为“看起来差不多”就 `complete`。
- Blocked audit：不能第一次遇到阻塞就标记 blocked；同一阻塞需要连续至少 3 个 goal turn 重复出现，并且确实无法继续推进。

这解释了为什么 `/goal` 不只是自动续跑，也包含一套反过早结束的约束。

### 7. 预算层：budget limited 是状态机结果

`account_thread_goal_usage` 会累计 time 和 token。当 active goal 的 `tokens_used + delta >= token_budget` 时，存储层会把状态改为 `budget_limited`。tool finish hook 检测到该状态后，会向当前 turn 注入 budget limit steering，要求模型尽快收尾、总结进展和剩余工作。

所以预算不是模型“自觉节制”的文本建议，而是由 usage accounting、状态更新和 steering 共同完成的机制。

## 设计启发

对 AgentLab 来说，`/goal` 的价值不只是一个 Codex 功能，而是长期 agent 任务的参考架构：

- 目标要持久化。研究话题应该写入 `research/runs/{slug}/state.md`，不要只留在对话里。
- 完成要可审计。站点文章、来源清单、生成文件、验证命令都应该作为完成证据。
- 用户控制和模型控制要分离。用户可以改方向、暂停或清除任务；agent 负责推进、记录证据、在满足门槛后标记完成。
- 预算和停滞要显式化。未来可以给研究任务增加 source count、token/time、构建状态等软预算，并在预算触顶时自动生成收尾报告。
- 长任务需要 continuation steering。每次恢复研究时，不应该只依赖历史聊天，而要从仓库状态、来源文件和当前待办重新建立工作上下文。
