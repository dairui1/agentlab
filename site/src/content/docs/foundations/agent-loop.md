title: Agent Loop
description: 观察、计划、行动、验证、压缩这五个步骤如何构成 Agent 的工作循环。
---

Agent loop 是 Agent 工程的核心心智模型。不同产品的实现各不相同，但大多数可行动 Agent 都会在某种形式上重复五件事：观察、计划、行动、验证、压缩。这个循环看似简单，实际包含了工具协议、权限、上下文管理和用户交互的全部复杂性。

## 五步循环

<div class="agentlab-flow">
  <div class="agentlab-step"><span>观察</span>读取用户请求、文件、环境、历史和工具结果。</div>
  <div class="agentlab-step"><span>计划</span>形成下一步策略，决定是否需要更多信息。</div>
  <div class="agentlab-step"><span>行动</span>调用工具、编辑文件、运行命令或询问用户。</div>
  <div class="agentlab-step"><span>验证</span>检查行动结果，运行测试，确认目标是否满足。</div>
  <div class="agentlab-step"><span>压缩</span>把有用状态沉淀进摘要、记忆、日志或最终交付。</div>
</div>

这五步并不总是显式出现。很多产品不会把“计划”展示给用户，也不会把“压缩”叫做压缩。但只要 Agent 能跨多轮行动，它就必须解决这些问题：如何知道现在发生了什么，如何选择下一步，如何让行动发生，如何判断行动是否有效，如何避免后续上下文被噪声淹没。

## 观察：上下文不是事实仓库

观察阶段最容易犯的错是把“进入上下文的内容”当作事实。文件可能已经过期，网页可能是恶意的，搜索结果可能是 SEO 噪声，用户的记忆可能是旧偏好，工具输出可能被 prompt injection 污染。Agent 必须把来源和信任等级带入上下文，而不是只拼接文本。

编码 Agent 的观察通常包括：项目目录、README、配置文件、相关代码、测试输出、git diff、issue/PR 内容、用户最新指令。关系型助手的观察则更关注：对话历史、用户偏好、情绪线索、长期关系设定和安全风险。Pi 的价值就在于它把“关系和语气”作为主上下文之一，而不是把任务完成当作唯一目标。

## 计划：计划是风险控制工具

计划不是为了看起来聪明。计划的工程价值在于控制风险：明确将要读哪些文件、改哪些模块、运行哪些验证、哪些步骤需要用户确认。对于简单任务，计划可以很短；对于跨模块修改、远端副作用、数据迁移、权限变更，计划应该更明确。

计划也可以是权限系统的一部分。只要 Agent 在执行前把下一步讲清楚，用户和安全系统就更容易判断是否授权。反过来，如果 Agent 每次都直接行动，审批提示会变成“你信不信模型”的抽象问题，而不是“这个具体操作是否合理”的工程问题。

## 行动：工具调用需要协议

工具调用不是函数调用那么简单。工具需要稳定命名、参数 schema、错误语义、超时策略、幂等性说明、权限标记和日志格式。一个工具如果返回大段未结构化文本，会污染上下文；一个工具如果隐藏副作用，会破坏安全模型；一个工具如果没有明确失败原因，会让 Agent 开始猜。

工具协议至少应该说明：

- 输入参数是什么，哪些必填，哪些有默认值。
- 工具是否只读，是否会写文件，是否会访问网络，是否会影响远端状态。
- 返回值中哪些字段可被模型信任，哪些字段来自不可信外部内容。
- 失败时返回什么，模型是否应该重试。
- 是否需要用户审批或系统审批。

Claude Code、Codex、OpenCode 都把工具和权限放在产品机制里。它们的差异之一在于：哪些工具默认可用，哪些动作必须询问，哪些边界由沙箱强制，哪些边界由配置或 prompt 约束。

## 验证：Agent 不应该只相信自己

Agent 完成行动后必须验证。编码任务的验证可能是测试、类型检查、lint、构建、页面截图、手工检查 diff。研究任务的验证可能是重新打开来源、对比发布日期、检查引用是否可靠。对话型任务的验证可能是确认用户是否被正确承接，是否触及安全边界，是否需要建议寻求专业帮助。

验证不等于“跑所有测试”。验证需要和风险匹配。小文档改动可以跑站点 build；底层工具协议变更需要跑单元测试、集成测试和交互回归；安全策略变更需要审查拒绝路径和绕过路径。Agent 最终回答里应该说明做了什么验证，以及哪些风险没有覆盖。

## 压缩：把状态变成可复用资产

长任务一定会遇到上下文压力。压缩不是把一切变短，而是把状态变成未来可用的结构。好的压缩会保留：用户目标、关键决策、已改文件、验证结果、失败尝试、剩余风险、下一步。坏的压缩会把不确定结论写成事实，把错误路径删掉，把来源丢掉。

压缩有多种落点：

- 会话摘要：给当前任务继续使用。
- 项目记忆：给未来任务使用。
- 文档：给团队和未来 Agent 使用。
- changelog：给版本审查使用。
- 结构化数据：给站点组件和脚本使用。

AgentLab 自身也在做这个循环。我们收集来源，写成研究笔记，提炼成文档，生成站点索引，用 CI 验证，再把结果推回仓库。这个项目既是 Agent 研究内容，也是 Agent 工程方法的样本。
