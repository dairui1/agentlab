开发 Agent 的第一步不是写 prompt，而是画边界。一个 Agent 不是模型加循环，也不是聊天窗口加工具。它是一组系统约束、上下文构造、推理策略、工具协议、权限判断、执行环境和交付标准的组合。模型只是其中的推理核心，真正决定产品稳定性的往往是模型之外的工程层。

## 七层模型

AgentLab 暂时使用七层模型组织这本书：

1. 用户意图层：用户以自然语言给出目标、限制、偏好和反馈。
2. 指令层：系统提示词、开发者提示词、项目规则、技能、记忆和临时约束。
3. 上下文层：文件、搜索结果、历史消息、工具返回、环境状态和外部资料。
4. 推理层：模型根据目标和上下文生成计划、工具调用、编辑或最终回答。
5. 工具层：文件读写、shell、浏览器、GitHub、数据库、MCP、内部 API。
6. 权限层：沙箱、审批、allow/ask/deny、审计、危险操作拦截。
7. 交付层：代码 diff、测试结果、文档、PR、报告、可回放日志。

这七层不是严格的运行时顺序，而是设计和排错时的地图。比如“Agent 改错文件”可能是上下文层给错了路径，也可能是工具层缺少 diff 保护，也可能是权限层没有要求确认，也可能是指令层没有强调用户已有修改不能覆盖。没有分层，就容易把所有问题归咎于模型。

## Agent 和普通聊天机器人的区别

普通聊天机器人主要生成文本。Agent 会把文本变成行动。行动意味着副作用：文件被修改、命令被执行、网络被访问、issue 被创建、浏览器被点击、数据库被查询、CI 被触发。副作用越多，工程系统越要关注可控性。

一个编码 Agent 至少要面对三类副作用。第一类是本地副作用，例如修改文件、删除文件、运行安装脚本。第二类是远端副作用，例如 push、开 PR、发消息、修改配置。第三类是认知副作用，例如把不可信网页内容写进长期记忆，或者把临时失败结论压缩成“事实”并带入后续任务。第三类经常被忽略，但它会污染未来上下文。

## 最小可用 Agent

最小可用 Agent 不一定要有很多工具，但必须有清晰的边界：

- 输入：用户目标、当前工作目录、可访问上下文。
- 输出：文本回答、文件变更、命令结果、结构化事件。
- 工具：至少有读、写、搜索、执行或外部调用中的一部分。
- 观察：每次工具调用后，模型能看到结果并决定下一步。
- 终止：知道什么时候停止，如何报告完成和风险。
- 安全：知道哪些操作默认不做，哪些操作需要确认。

如果这些边界没有定义，Agent 会变成一个“会碰运气的模型”。它可能在 demo 中看起来很强，但很难在真实团队中长期使用。

## 设计问题清单

做 Agent 架构时，可以从这些问题开始：

- 它的主要工作是编码、研究、客服、个人陪伴、数据分析还是运维？
- 它能读哪些上下文？默认会不会读取整个仓库？
- 它能写哪些地方？是否保护 `.git`、配置、密钥和用户未提交修改？
- 它能访问网络吗？网络结果是否被当作不可信内容处理？
- 它能调用哪些工具？工具 schema 是否稳定？返回值是否结构化？
- 它如何获得长期规则？系统 prompt、项目文件、配置、记忆、技能分别放什么？
- 它如何处理失败？重试、回滚、询问用户还是降级？
- 它如何被审计？日志、diff、工具调用、审批记录是否可回放？
- 它如何被更新？提示词、工具、模型、配置、文档是否版本化？

这些问题看起来基础，但它们直接决定 Agent 的产品形态。Claude Code 和 Codex 都把权限、沙箱、项目规则和扩展层放在产品中心。OpenCode 作为开源 Agent，把 agents、permissions、providers、config 等机制暴露给用户。Pi 则把 minimal harness、可观察性、项目指令、skills 和扩展点放在中心。

## 文档如何反哺实现

这本书不是旁观者笔记。理想状态下，AgentLab 的文档会反哺实现：

- 每个章节可以变成 AGENTS.md、CLAUDE.md、skill 或规则文件的素材。
- 每个对比矩阵可以变成产品设计 checklist。
- 每个 prompt diff 可以变成变更评审材料。
- 每个实验组件可以变成内部培训或设计评审工具。
- 每个来源索引可以变成定时检查任务。

一个好 Agent 项目的文档不是“写给别人看的说明书”，而是系统本身的一部分。它告诉人和 Agent：什么是事实，什么是约定，什么是风险，什么还没有验证。
