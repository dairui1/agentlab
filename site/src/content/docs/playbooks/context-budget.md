---
title: 上下文预算
description: 如何为 Agent 请求分配系统指令、项目规则、任务证据、工具输出和记忆的上下文预算。
---

上下文预算是 Agent 工程里最实际的问题之一。窗口再大，也会遇到成本、延迟、缓存和注意力问题。上下文不是越多越好，而是要把最重要、最可信、最稳定的信息放在合适位置。

## 预算分桶

一个编码 Agent 请求可以分成这些桶：

- 稳定系统指令：身份、边界、工具规则。
- 工具 schema：工具名、参数、返回值。
- 项目规则：AGENTS/CLAUDE、测试命令、目录约定。
- 任务上下文：用户请求、相关文件片段。
- 工具观察：命令输出、测试失败、搜索结果。
- 工作状态：计划、已做修改、待验证事项。
- 长期记忆：用户偏好、项目经验。

每个桶都要有预算。没有预算，最容易被大段日志和长文件吞掉。

## 稳定内容放前面

稳定内容放前面有两个好处：行为一致，缓存更友好。系统指令、工具 schema、项目规则的顺序应尽量稳定。当前任务、搜索结果、命令输出放后面，因为它们变化频繁。

如果每轮都把随机摘要插到前缀中间，即使内容差不多，也会破坏缓存和行为稳定。缓存策略和上下文策略是同一个问题的两面。

## 相关性不是唯一标准

选择上下文时，相关性重要，但不是唯一标准。还要看：

- 可信度：官方文档比外部评论可信。
- 新鲜度：2026 文档比 2024 博客更适合当前事实。
- 可追溯性：有路径/URL 的内容比无来源摘要好。
- 行动性：能影响下一步决策的信息优先。
- 风险：不可信内容需要标注，不能进入高优先级指令区。

一个网页很相关，但仍然不应该覆盖系统指令；一段旧记忆很相关，但可能已经过期。

## 文件片段策略

编码 Agent 读取文件时，常见错误是把整文件放进上下文。更好的做法是：

1. 先搜索符号或关键词。
2. 读取相关片段和邻近上下文。
3. 修改前读取完整目标区域。
4. 对长文件生成结构摘要。
5. 必要时再按函数或类读取细节。

这样既保留准确性，又避免上下文膨胀。

## 工具输出压缩

工具输出尤其容易失控。测试失败可能输出几千行，build log 可能包含重复 warning，搜索结果可能过多。压缩时保留：

- 命令。
- exit code。
- 关键错误。
- 涉及文件路径。
- 失败堆栈顶部和根因线索。
- 是否可能重试。

不要只写“测试失败”。模型需要足够信息定位问题。

## 预算指标

AgentLab 后续可以为每次任务记录：

- 总 token。
- 稳定前缀 token。
- 项目规则 token。
- 文件上下文 token。
- 工具输出 token。
- 摘要 token。
- 缓存命中估计。

这些指标会让上下文优化从感觉变成数据。
