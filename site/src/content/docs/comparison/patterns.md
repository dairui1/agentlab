---
title: 设计模式
description: 从四个 Agent 中抽取可复用的 Agent 工程设计模式。
---

设计模式不是“最佳实践清单”，而是一组反复出现的工程解法。Claude Code、Codex、Pi、OpenCode 虽然产品方向不同，但都暴露出一些通用问题：如何加载长期规则，如何区分计划和执行，如何降低审批疲劳，如何连接外部工具，如何保护用户数据，如何让内容持续更新。

## 模式一：项目规则文件

代表：Claude Code 的 `CLAUDE.md`、Codex 和 OpenCode 的 `AGENTS.md`。

项目规则文件把团队约定放进仓库，使 Agent 每次进入项目时都能读取相同背景。它适合保存构建命令、测试策略、代码风格、目录说明、审查要求、禁止事项、发布流程和文档规范。

设计要点：

- 文件要短，优先写高频、稳定、可验证的规则。
- 规则要能被人审查，不能由 Agent 随意改写。
- 多层规则要有明确覆盖顺序。
- 规则变更应该走代码审查。
- 规则中不要放 secrets、token 或私有凭据。

## 模式二：计划模式和执行模式分离

代表：OpenCode 的 Plan/Build，Claude Code 和 Codex 中的 read-only/approval/sandbox 工作流。

很多任务应先分析再修改。把“只读规划”和“可写执行”做成不同模式，可以降低误操作概率。用户可以让 Agent 先解释代码、提出方案、列出风险，再切换到执行模式。

设计要点：

- 计划模式默认不能写文件。
- 计划模式运行命令要更谨慎，尤其是有副作用的命令。
- 计划输出应包含修改范围、验证方式和风险。
- 执行模式应引用计划，而不是重新发散。

## 模式三：工具权限三态

代表：Claude Code、Codex、OpenCode 的 allow/ask/deny 或 sandbox/approval 组合。

工具权限不应只有“开”和“关”。真实系统需要至少三态：自动允许、询问用户、直接拒绝。更复杂时还需要按路径、命令、域名、server、tool、资源类型和环境区分。

设计要点：

- 默认只允许低风险读操作。
- 写操作要记录 diff。
- 网络访问要有域名策略。
- destructive 操作要单独标记。
- 高风险操作不能通过模糊 prompt 授权。

## 模式四：稳定前缀和变化后缀

代表：prompt cache、系统指令、工具 schema、项目摘要。

如果底层模型或平台支持 prompt caching，稳定前缀越稳定，成本和延迟越可控。即使没有显式缓存，稳定组织上下文也能减少行为漂移。

设计要点：

- 系统约束、工具 schema、项目规则保持顺序稳定。
- 当前任务、临时搜索结果、最新命令输出放在后面。
- 不要把频繁变化的随机摘要插到前缀中间。
- 版本化 prompt 前缀，避免不可解释的行为变化。

## 模式五：外部工具协议化

代表：MCP、server API、plugin hooks。

把外部系统接给 Agent 时，直接写 API 调用很快，但长期会失控。协议化的工具边界能表达 tool name、schema、description、side effects、approval、timeout、error、audit。

设计要点：

- 工具参数结构化。
- 返回值区分可信元数据和不可信正文。
- 工具有副作用标记。
- 工具执行要有 timeout 和错误类型。
- 工具调用记录进入审计日志。

## 模式六：可回放的 Agent 轨迹

代表：OpenCode session、Codex logs、Claude Code audit/telemetry 方向。

Agent 出错时，单看最终回答很难排查。需要保留轨迹：用户请求、指令来源、上下文摘要、工具调用、审批、执行结果、文件 diff、验证命令和最终输出。

设计要点：

- 日志不要泄露 secrets。
- 日志要能关联到 commit、PR、session 或任务 ID。
- 失败轨迹比成功轨迹更有价值。
- 回放不一定要重跑副作用，可以先回放决策链和上下文。

## 模式七：人写规范，Agent 写草稿

代表：AgentLab 自身的文档流水线。

文档和研究内容可以由 Agent 起草，但来源规则、事实校验和发布边界必须由人和 CI 共同控制。Agent 可以生成初稿、diff、索引和矩阵，但不能把未验证信息自动发布成事实。

设计要点：

- 来源必须显式记录。
- 自动生成产物要可审查。
- 高风险内容走 PR。
- 定时任务只做低风险更新或开 PR。
- 站点 build 和数据校验是发布门槛。

## 模式八：Minimal harness 的可观察扩展

代表：Pi。

Minimal harness 不应只优化“能跑起来”。它还要让用户看清 prompt、项目指令、工具调用、会话状态和扩展注入。Pi 的价值在于用较薄的架构暴露 agent loop，而不是把所有能力藏进重型平台。

设计要点：

- 系统提示词和项目规则应可见。
- 技能、prompt templates 和 extensions 应可版本化。
- 扩展工具需要声明权限和数据流。
- 会话应能恢复、命名、删除和审计。
- 最小内核不应阻止用户扩展，但扩展不能绕过安全边界。

## 如何使用这些模式

做自己的 Agent 时，不要一次性实现所有模式。先根据场景选择：

- 编码 Agent：项目规则文件、计划/执行分离、工具权限三态、轨迹日志。
- 企业内部 Agent：外部工具协议化、managed config、审计、来源标记。
- Minimal coding harness：可见 prompt、项目规则、skills、extensions、会话审计。
- 研究型 Agent：来源索引、上下文信任等级、摘要可追溯。

设计模式的价值在于让团队讨论具体取舍，而不是抽象争论“Agent 应不应该自主”。
