---
title: 上下文与记忆
description: 区分临时上下文、项目规则、长期记忆和生成摘要，避免 Agent 被噪声或旧信息污染。
---

上下文是 Agent 的工作空间。记忆是跨任务保留的上下文。两者都很有用，也都很危险。给太少，Agent 不了解情况；给太多，模型被噪声淹没；记得太少，用户要重复说明；记得太多，旧偏好和错误结论会污染未来任务。

## 四类上下文

AgentLab 暂时把上下文分成四类：

1. 固定指令：系统/developer prompt、工具 schema、安全策略。
2. 项目规则：`CLAUDE.md`、`AGENTS.md`、项目配置、团队约定。
3. 任务上下文：用户请求、相关文件、搜索结果、命令输出、当前 diff。
4. 长期记忆：用户偏好、历史纠正、项目经验、跨会话摘要。

这四类应该分层管理，而不是拼成一团。固定指令最稳定，适合放在前缀；项目规则随仓库变化，应该可版本化；任务上下文最易变，应该按需要检索；长期记忆最敏感，应该有来源和删除机制。

## 项目规则和记忆不同

Claude Code 的 `CLAUDE.md` 和 auto memory、Codex 的 `AGENTS.md` 和 memories，给了一个重要启发：项目规则和记忆不是同一件事。项目规则是团队明确写下的约定，应通过版本控制审查。记忆是系统从历史互动中提取的经验，应该更容易撤销和标记来源。

如果把二者混在一起，风险很大。模型可能把一次临时调试经验写成长期团队规则，也可能把用户随口偏好应用到不相关项目。正确做法是给记忆加元数据：

- 来源：用户明确要求、模型总结、工具观察、文档来源。
- 时间：什么时候写入。
- 范围：全局、项目、目录、任务类型。
- 置信度：事实、偏好、推断、待验证。
- 生命周期：永久、短期、一次性、待删除。

## 检索不是上下文策略的全部

很多系统把上下文策略等同于 RAG。RAG 只是找资料的方法，不解决资料怎么用。Agent 还需要判断：找到的内容是否可信，是否过期，是否应该覆盖项目规则，是否进入最终回答，是否写入记忆。

编码 Agent 的检索应该关注路径、符号、调用关系、测试、配置、最近 diff。关系型 Agent 的检索更关注用户偏好和对话历史。研究型 Agent 的检索则关注来源权威性、发布日期和引用链。不同场景需要不同检索目标。

## 上下文预算

上下文窗口再大也不是免费资源。长上下文会增加成本、延迟和注意力噪声，也会降低缓存命中。好的 Agent 不只是“能塞更多”，而是会选择。

建议把上下文预算分桶：

| 桶 | 内容 | 策略 |
| --- | --- | --- |
| 稳定前缀 | 系统指令、工具 schema、安全策略 | 尽量稳定，利于缓存 |
| 项目规则 | 项目文档、AGENTS/CLAUDE、构建命令 | 版本化，必要时摘要 |
| 任务证据 | 文件片段、搜索结果、测试输出 | 只放相关部分 |
| 临时状态 | 当前计划、失败尝试、用户反馈 | 周期性压缩 |
| 不可信内容 | 网页、issue、外部输入 | 明确标记，不能覆盖指令 |

未来 AgentLab 的上下文预算组件可以让用户拖动这些桶，观察 token、缓存和风险如何变化。

## 摘要的危险

长任务会压缩上下文，但摘要可能丢失关键细节。最危险的摘要不是短，而是把不确定写成确定，把失败路径删掉，把来源删掉，把用户限制删掉。一个好的任务摘要应该保留：

- 用户目标。
- 关键约束。
- 已读来源和路径。
- 已做变更。
- 验证结果。
- 失败尝试。
- 待验证假设。
- 下一步。

摘要应该能被审查。必要时，Agent 应能重新打开原始来源，而不是只依赖摘要。

## 记忆的用户控制

长期记忆涉及隐私和信任。用户应该知道 Agent 记住了什么，能删除、编辑、禁用。关系型 Agent 尤其重要，因为用户可能在情绪状态下透露敏感信息。Pi 这类产品的研究提醒我们，记忆不只是效率工具，也是关系和安全设计。

编码 Agent 的记忆看起来风险低，但也可能包含公司内部架构、私有路径、客户名、部署方式、历史事故。不要把所有项目经验都写进全局记忆。项目经验优先留在项目仓库的规则文件或文档里，跨项目记忆只保存真正通用的用户偏好。
