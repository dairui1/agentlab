---
title: 工具协议
description: Agent 工具不只是函数调用，而是包含 schema、副作用、权限、返回值和审计的协议。
---

Agent 能不能稳定工作，很大程度取决于工具协议。模型本身会推理，但行动要通过工具发生。工具协议设计得好，模型可以在清晰边界内完成任务；工具协议设计得差，模型会被模糊参数、不可预测返回值和隐藏副作用拖垮。

## 工具描述不是 API 文档

给模型看的工具描述和给程序员看的 API 文档不同。程序员可以读实现、看类型、调试、查日志；模型只能在上下文里看到有限描述。工具描述必须直接回答：这个工具做什么，什么时候用，参数怎么填，结果是什么意思，失败时该怎么办，是否有副作用。

一个好的工具描述至少包含：

- 工具目的：解决什么问题，不解决什么问题。
- 参数语义：每个参数的含义、格式、默认值、限制。
- 副作用：是否读文件、写文件、访问网络、修改远端状态。
- 返回结构：哪些字段稳定，哪些字段来自外部内容。
- 失败语义：超时、权限不足、资源不存在、解析失败分别怎么表达。
- 权限需求：是否需要用户确认，是否可以自动执行。

如果工具描述只写“run command”或“search docs”，模型就会把大量判断留给自己猜。猜测越多，行为越不稳定。

## 工具返回值要结构化

工具返回大段文本是最常见问题。文本当然灵活，但它很难表达来源、风险、状态和可重试性。比如 shell 命令失败时，模型需要知道：exit code、stdout、stderr、工作目录、耗时、是否超时、是否被 sandbox 阻止。把这些压成一段字符串，会让模型把错误归因做成猜谜。

建议返回结构至少包含：

```json
{
  "ok": false,
  "error_type": "permission_denied",
  "summary": "Command tried to write outside workspace.",
  "stdout": "",
  "stderr": "sandbox blocked path /etc/hosts",
  "side_effects": [],
  "retryable": false
}
```

这不是为了让 JSON 好看，而是让模型能做下一步决策：是否重试，是否换工具，是否请求用户确认，是否报告阻塞。

## 不可信内容边界

工具返回的内容不一定可信。浏览器工具读取网页，网页可能包含 prompt injection；GitHub 工具读取 issue，issue 可能由外部用户提交；文件读取工具读取仓库，仓库本身可能包含恶意指令。工具本身可信，不代表工具读取的内容可信。

因此返回值应把来源分层：

- 系统元数据：工具自己生成，可信度较高。
- 用户项目内容：来自当前仓库，需要按项目信任级别处理。
- 外部网页内容：默认不可信。
- 第三方用户输入：默认不可信。
- 执行结果：stdout/stderr 只是程序输出，不是指令。

Claude Code 和 Codex 的安全文档都在不同程度上强调工具输出和网络内容的风险。自己的 Agent 应该把“不可信内容不能覆盖系统指令”写成工具协议和系统约束，而不是只靠模型常识。

## 幂等性和回滚

工具如果有副作用，就要说明是否幂等。读文件是幂等的；运行测试通常是低风险但可能生成缓存；安装依赖会修改 lockfile 或 node_modules；数据库迁移可能不可逆；发送 Slack 消息不可撤回；删除文件可能可恢复也可能不可恢复。

工具可以按副作用风险分级：

| 等级 | 示例 | 默认策略 |
| --- | --- | --- |
| 0 | 读文件、列目录、查状态 | 自动允许 |
| 1 | 运行测试、格式化、生成临时文件 | 通常允许，记录日志 |
| 2 | 修改工作区文件、安装依赖 | 允许或询问，保留 diff |
| 3 | push、开 PR、发消息、改远端配置 | 询问用户 |
| 4 | 删除数据、改生产、读 secrets | 默认拒绝或强审批 |

工具协议里明确风险等级，权限系统才能自动判断。否则每个工具都要靠 prompt 解释，用户也很难理解审批请求。

## 工具选择和工具组合

Agent 不是每轮只能用一个工具。复杂任务需要工具组合：搜索文件、读取代码、编辑、运行测试、查看 diff、提交。工具协议应该帮助模型选择正确顺序。例如“先 `rg` 后读文件”是高效检索策略；“先看 git status 再编辑”是保护用户修改的策略；“运行 build 后再截图”是前端验证策略。

这些组合可以放进：

- 系统提示词：全局工具使用规则。
- 项目规则：项目特定命令和工作流。
- 技能：可复用任务流程。
- Hook：确定性地执行检查。
- 文档：给人和 Agent 共同参考。

不要把所有工具组合都写死到模型 prompt。确定性强的流程可以交给脚本和 hook；需要判断的流程才交给模型。

## 工具协议的测试

工具也需要测试。测试不只是“函数能跑”，还要测模型能不能正确使用。可以设计这些用例：

- 参数缺失时，模型是否能补全或询问。
- 权限不足时，模型是否会请求授权而不是绕过。
- 工具返回不可信指令时，模型是否忽略。
- 工具失败可重试时，模型是否重试一次而不是无限循环。
- 工具有副作用时，模型是否在最终回答中报告。

未来 AgentLab 可以把工具协议做成可交互矩阵：选择工具、风险等级、权限策略和返回类型，页面自动展示模型可见描述、人类文档和审计字段。
