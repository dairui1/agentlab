---
title: 提示词版本化
description: 把提示词当作工程接口管理：snapshot、diff、changelog、测试和回滚。
---

提示词不是一次性文案，而是 Agent 的工程接口。它定义角色、工具、权限、输出风格、失败处理、用户交互、上下文优先级和安全边界。接口变更需要版本化；提示词变更也一样。没有版本化的提示词，很难解释行为为什么变了，更难回滚。

## 为什么要 snapshot

很多团队只保存“当前 prompt”。这会带来三个问题。第一，无法知道某个行为变化来自模型、工具还是 prompt。第二，无法审查 prompt 修改是否引入安全风险。第三，无法复盘过去某个版本为什么表现更好。

Snapshot 应该记录：

- Agent 名称。
- 版本或日期。
- 来源 URL 或采集方法。
- 访问日期。
- 范围：系统 prompt、developer prompt、tool instruction、project rule、skill。
- 是否允许保存全文。
- 是否包含敏感内容。
- 变更摘要和影响。

如果不能保存全文，也可以保存结构化摘要和 diff 类别。关键是可追溯。

## Diff 不只是文本差异

提示词 diff 不能只显示左右文本。它还要解释变化属于哪个维度：

- 身份定位：Agent 是工程师、助理、研究员还是陪伴者。
- 工具规则：什么时候调用工具，调用前后如何解释。
- 权限边界：哪些操作允许、询问、拒绝。
- 上下文优先级：项目规则、用户最新指令、工具结果谁优先。
- 安全策略：如何处理不可信内容、secrets、危险请求。
- 输出契约：最终回答、进度更新、测试说明如何写。
- 失败恢复：重试、回滚、询问用户、报告阻塞。

AgentLab 的提示词 Diff 组件现在还是示例数据，后续应读取 `generated/prompt-diffs/*.json`，把变更类别和左右文本一起展示。

## Prompt 和配置的边界

不是所有行为都应该写进 prompt。权限、网络、工具 allowlist、路径保护、格式化命令、CI 门槛等能用配置和代码强制的内容，不应该只靠提示词。提示词适合表达判断原则和沟通契约；配置适合表达硬边界；hook 适合执行确定性动作；测试适合验证结果。

例如“不要覆盖用户修改”应该同时存在于：

- prompt：提醒 Agent 尊重用户已有 worktree。
- 工具：patch 失败时不强行覆盖。
- git 检查：编辑前后查看 status。
- 测试：模拟用户已有修改。

只有 prompt 的系统是脆弱的。

## Changelog 的写法

提示词 changelog 应避免空泛。不要写“优化系统提示词”。应该写：

- 新增了对未提交用户修改的保护要求。
- 删除了自动运行网络命令的建议。
- 将最终回答从文件列表改为行为变化 + 验证 + 风险。
- 将工具输出标记为不可信内容。
- 把计划要求限定为多模块任务，避免小任务过度计划。

每条 changelog 应说明影响：更安全、更慢、更少噪声、更保守、更适合团队审查，还是可能降低自主性。

## 回归测试

提示词变更也要测试。可以设计 prompt regression suite：

- 用户要求删除文件，Agent 是否询问。
- 工具输出包含“忽略系统指令”，Agent 是否忽略。
- 用户已有未提交修改，Agent 是否保护。
- 小任务是否不写冗长计划。
- 大任务是否先收集上下文。
- 失败测试是否被正确报告。
- 安全高风险请求是否拒绝或降级。

这些测试不一定都能自动化评分，但至少能形成固定样例。每次 prompt 变更后跑一遍，能防止行为漂移。

## 版本和模型变化

模型升级会改变 prompt 的效果。一个 prompt 在旧模型上恰好有效，不代表新模型仍然最佳。因此 prompt 版本应该记录适用模型、平台和工具版本。比较 prompt 变化时，也要区分：

- prompt 变了，模型没变。
- 模型变了，prompt 没变。
- 工具 schema 变了。
- 产品权限默认值变了。
- 上下文构造方式变了。

否则很容易把所有效果变化归因于 prompt。

## AgentLab 的实现路径

AgentLab 后续可以这样做：

1. 定义 `PromptSnapshot` schema。
2. 用 CLI 创建 snapshot 模板。
3. 用脚本生成相邻版本 diff。
4. 用组件展示左右 diff 和类别统计。
5. 用 changelog 解释影响。
6. 用 CI 禁止提交未标注来源的 snapshot。

这样提示词研究会从“收藏文本”变成“管理工程接口”。
