---
title: 权限评审清单
description: 在给 Agent 增加工具、网络、文件写入或远端动作前，需要审查哪些问题。
---

每次给 Agent 增加能力，都应该做权限评审。能力越强，副作用越大；副作用越大，越需要边界、日志和回滚。下面这份清单可以用于新工具、新 MCP server、新自动化任务和新 agent mode。

## 基本信息

先写清楚：

- 工具或能力名称。
- 主要使用场景。
- 谁会触发它：用户、Agent、hook、定时任务、CI。
- 默认是否启用。
- 是否可被项目或组织禁用。

如果连这些都说不清，先不要接入。

## 数据访问

评审问题：

- 它会读取哪些文件、目录、URL、数据库、账号或内部系统？
- 是否可能读取 secrets、token、cookie、私有消息？
- 返回内容是否进入模型上下文？
- 返回内容是否包含第三方用户输入？
- 是否需要脱敏或摘要？

原则：Agent 应获得完成任务所需的最小信息，不要把原始密钥或大范围私有数据放进上下文。

## 副作用

评审问题：

- 它会写本地文件吗？
- 会执行 shell 命令吗？
- 会访问网络吗？
- 会修改远端状态吗？
- 会发送消息、评论、邮件或表单吗？
- 会产生费用吗？
- 操作是否可撤销？

每个副作用都应对应权限策略。只读可以自动；可逆写入可以记录 diff；远端写操作通常需要确认；不可逆操作默认拒绝。

## 权限策略

为每个工具定义 allow/ask/deny：

| 条件 | 策略 |
| --- | --- |
| 只读工作区 | allow |
| 写当前任务文件 | allow 或 ask |
| 写敏感路径 | ask 或 deny |
| 访问公开 docs | ask 或 allowlist |
| 访问私有系统 | ask + connector 权限 |
| destructive 操作 | deny 或强审批 |

不要把所有条件写成自然语言。能配置的就配置，能测试的就测试。

## 审批提示

如果需要询问用户，提示应包含：

- 具体动作。
- 目标资源。
- 原因。
- 副作用。
- 是否可撤销。
- 拒绝后的替代方案。

审批提示不能太抽象。用户不应该看到“是否允许工具调用”，而应该看到“是否允许向 GitHub PR #12 发布一条评论”。

## 日志和审计

工具执行后应记录：

- 时间。
- Agent/session/task。
- 工具名和参数摘要。
- 权限决策。
- 用户审批结果。
- 输出摘要。
- 副作用结果。

日志要避免保存 secrets。对于远端写操作，应记录远端资源 URL 或 ID，便于回查。

## 测试样例

上线前至少测试：

- 正常成功路径。
- 权限拒绝路径。
- 用户拒绝审批。
- 工具超时。
- 工具返回恶意内容。
- 工具返回过大内容。
- 重复调用。
- 部分成功。

权限系统最怕只测 happy path。真实风险通常出现在失败和边界条件。

## 上线策略

新工具不要一开始默认全量开放。推荐顺序：

1. 只读或 dry-run。
2. 手动触发。
3. 小范围 allowlist。
4. 默认 ask。
5. 低风险动作 allow。
6. 高风险动作保持 ask/deny。

Agent 能力应该渐进开放，而不是一次性给满。
