---
title: 设计一个编码 Agent
description: 从最小可用架构开始，逐步加入工具、权限、上下文、记忆、评测和自动化。
---

如果从零设计一个编码 Agent，不要一开始就追求 Claude Code 或 Codex 的完整能力。先做一个最小可用闭环：理解任务、读取相关文件、提出计划、修改文件、运行验证、报告结果。然后再逐步加入权限、记忆、MCP、浏览器、GitHub 和自动化。

## 最小架构

最小编码 Agent 可以分成七个模块：

- Prompt builder：组装系统指令、项目规则、用户请求和上下文。
- Context retriever：搜索和读取相关文件。
- Tool router：把模型工具调用路由到 shell、文件、浏览器等工具。
- Permission gate：判断工具调用是否允许。
- Executor：实际执行命令或修改文件。
- Observer：把结果结构化返回给模型。
- Reporter：生成最终回答和验证说明。

这七个模块不需要一开始都很复杂，但必须有明确边界。否则很快会变成一堆 prompt 拼接和 if/else。

## 第一阶段：只读分析

先实现只读模式。只读模式能做：

- 读取 README、配置和源码。
- 搜索符号和文本。
- 解释模块关系。
- 提出修改方案。
- 列出风险和验证命令。

只读模式不能写文件，也不能运行高风险命令。它适合建立用户信任，也适合在未知项目中探索。OpenCode 的 Plan agent 就是这种思路。

## 第二阶段：受控写入

写入模式应限制在工作区内，并保护 `.git`、secrets、生成目录和用户未提交修改。编辑工具最好使用 patch，而不是让模型直接重写整文件。每次写入后记录 diff，必要时运行格式化和测试。

写入阶段的关键规则：

- 编辑前检查 git status。
- 编辑前读取目标文件。
- 不覆盖用户已有改动。
- 小步修改。
- 修改后运行最相关验证。
- 最终回答说明验证和风险。

这些规则应同时写在 prompt、工具行为和测试里。

## 第三阶段：命令执行

Shell 是编码 Agent 的强能力，也是主要风险。命令执行要区分：

- 只读命令：`ls`、`rg`、`git status`。
- 低风险命令：测试、lint、build。
- 有副作用命令：安装依赖、生成文件、格式化。
- 高风险命令：删除、权限修改、生产操作、网络脚本。

不要直接给 Agent 无限 shell。即使在本地，也应有 allowlist、denylist、工作目录限制、超时和输出截断。

## 第四阶段：项目规则

加入项目规则文件，例如 `AGENTS.md` 或 `CLAUDE.md`。这一步能显著提升一致性。规则文件应包含：

- 项目命令。
- 测试策略。
- 代码风格。
- 目录说明。
- 安全禁止事项。
- 最终回答格式。

规则文件也应有大小限制。长文档可以被链接，不必每次都进入上下文。

## 第五阶段：外部系统

等本地 loop 稳定后，再接外部系统：GitHub、浏览器、文档搜索、Sentry、数据库、Figma。外部系统最好通过 MCP 或结构化工具暴露，不要直接让模型拼 API 请求。

每个外部工具都要标注副作用：读、写、发送、删除、授权、付费。远端写操作默认应询问用户。

## 第六阶段：评测和回归

没有评测的 Agent 会越改越玄学。至少建立这些样例：

- 简单 bug 修复。
- 跨文件改动。
- 保护用户已有修改。
- 工具输出 prompt injection。
- 网络被拒绝。
- 测试失败后修复。
- 最终回答格式。

每个样例既看结果，也看轨迹。Agent 是否读了正确文件？是否运行了验证？是否请求了不该请求的权限？

## 第七阶段：自动化

最后再做自动化：定时任务、PR 审查、CI 修复、文档生成。自动化任务要满足输入稳定、目标清楚、验证可运行、副作用可控。对于不满足这些条件的任务，让 Agent 开 PR 或生成报告，不要直接发布。

编码 Agent 的成熟路径不是“一步到位”，而是从只读到写入，从本地到外部，从交互到自动化。
