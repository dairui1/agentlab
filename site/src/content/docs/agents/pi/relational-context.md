---
title: Pi 项目上下文
description: Pi 如何通过项目指令、系统提示词、技能、会话和扩展构造 coding agent 的上下文。
---

Pi 的上下文不是关系型聊天上下文，而是开发工作流上下文。它需要知道当前项目、用户指令、历史会话、可用工具、扩展能力、技能说明和 prompt template。研究 Pi 的关键，是看它如何让这些上下文保持可见、可控和可替换。

## 项目指令

Pi 支持 `AGENTS.md` 作为项目指令入口。这类文件的价值在于把项目规则从临时 prompt 中拿出来，变成可版本化的仓库资产。它通常应该写明：

- 项目的构建、测试、格式化命令。
- 代码风格和目录边界。
- 哪些文件不要自动修改。
- 提交、PR、review 的本地约定。
- 高风险操作的审批要求。

这和 Codex、Claude Code、OpenCode 都可以横向比较。差异通常不在“是否有项目规则”，而在加载路径、优先级、冲突处理和用户可见性。

## 系统提示词

Pi 还支持 `SYSTEM.md` 替换或追加默认系统提示词。这个设计给了研究者一个很好的观察点：agent 的默认人格、工具契约和行为边界是否应该固定在源码里，还是允许项目按需覆盖。

完全替换系统提示词有强控制力，但风险也高：用户可能破坏默认安全和工具协议。追加模式更保守，但容易形成冗长上下文。好的 harness 应该把这两种模式的语义说清楚，并让用户能看到最终进入模型的内容。

## 技能和提示词模板

Pi 的技能和提示词模板让项目可以复用工作流。技能适合沉淀较稳定的操作，例如“调试 CI 失败”“生成 release note”“审查权限变更”。提示词模板适合沉淀可参数化任务，例如“根据 issue 写实现计划”或“从源码目录提取架构图”。

它们对上下文的影响不同。技能通常会带工具使用规范和流程约束；模板更像一次性任务说明。把两者分开，有助于避免所有内容都堆进一个全局 prompt。

## 会话上下文

Coding agent 的会话不是聊天记录备份，而是工作状态。它应帮助用户恢复：

- 当前任务目标。
- 已经读过的文件。
- 已经执行过的命令。
- 已经做出的决策。
- 未完成的风险和 TODO。

Pi 的会话机制值得研究，因为它可以和 Claude Code 的 transcript、Codex 的 task/session、OpenCode 的 session/share 模型对比。关键问题是：会话如何命名、恢复、删除、审计，以及是否能跨项目安全使用。

## 扩展注入

扩展会改变 agent 能看到什么、能做什么。Pi 的扩展点使它适合个人工作流，但也引入风险：扩展可能增加高权限工具、自动读取文件、外发数据或改变 prompt。研究 Pi 时要把扩展当成上下文系统的一部分，而不是 UI 插件。

一个健康的扩展模型应回答：

- 扩展如何声明工具和说明。
- 用户如何知道扩展注入了什么。
- 扩展是否能被项目锁定版本。
- 高风险扩展是否需要确认。
- 扩展输出如何进入会话历史。

## 对 AgentLab 的启发

Pi 提醒我们：上下文工程不是把更多信息塞进模型，而是让信息入口可分层、可审查、可替换。对于自己的 agent，`AGENTS.md`、`SYSTEM.md`、skills、templates、extensions、sessions 应该分别建模，不要混成一个巨大 prompt。
