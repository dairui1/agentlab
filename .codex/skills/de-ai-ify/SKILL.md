# 去除 AI 味

目标不是给句子撒几粒“说白了”，而是让读者感觉真的有人在想、在判断、在带他看一件事。

人味不等于随便。技术事实、数字、代码名、证据等级和未知边界都要原样站住。变化的是讲法，不是事实。

## 两条底线

### 不演

不要编“我之前遇到过”“我亲自试了”“看到这里我很震惊”之类不存在的经历或情绪。没有动态实验，就别写得像跑过动态实验。

可以有作者判断：

- “我更愿意把它看成一道权限闸门。”
- “真正麻烦的不是报错，而是你不知道动作有没有发生。”
- “这个区别看着小，恢复策略会完全不同。”

判断必须能从现有材料推出。

### 不油

“说白了”“老实说”“对吧”都是调味料，不是文风。连续几段都在抖机灵，会比 AI 腔更假。研究文章可以亲近，但不要装熟、卖萌或替读者兴奋。

## 改写顺序

### 先留下事实骨架

动笔前先圈出不能动的东西：接口名、版本、数字、错误码、因果关系、证据编号、推断边界。删掉这些，文章只剩语气；擅自加强这些，文章就失真。

### 再找到这一段真正要回答的问题

不要从组件清单开场。先问读者此刻最在意什么：

- 这一下到底谁执行？
- 为什么不能直接重试？
- App 已经允许了，为什么还是动不了？
- 截图和 AX 到底差在哪？

一段只扛一个主问题。技术名词跟在答案后面，不要排队冲进第一句。

### 用现场和后果代替抽象结论

差：

> transport 不提供 exactly-once 语义，因此需要重新观察。

好：

> 最麻烦的是 timeout。点击也许没送到，也许已经点下去，只是回执丢了。现在再点一次，可能就变成双击。所以别猜，先重新看一眼界面。

### 打乱过于完美的节奏

长句负责交代关系。短句负责落锤。真的可以很短。

不要每段都长成“定义一句 + 机制一句 + 边界一句”。有时先抛结论，有时先讲一个具体动作，有时用一句反问把读者带进来。

### 让连接发生在意思上

少用“首先、其次、此外、然而、因此、综上所述”。换成真实的思路转折：

- “先别急着点第二次。”
- “问题就出在这里。”
- “可到了原生服务这一层，规则又变了。”
- “这看着只是一个命名差异，恢复方式却完全不同。”
- “到这里还没完。”

不必每句都有连接词。人会停顿，也会直接换角度。

## 不同文本怎么写

### 文章正文

- 先给读者一个能想象的动作，再拆机制。
- 允许使用“我更愿意把它理解为”表达有依据的作者判断。
- 别连续几段只讲抽象机制；该落地时，就给出一个具体后果、选择或反例。
- 标题先帮读者定位：这一节讲哪个组件、哪段链路或哪类边界。判断可以放在冒号后，别用比喻替代技术对象。
- 同一级标题保持同一维度。不要一会儿讲组件，一会儿抛反问，一会儿又突然变成操作建议。

### UI 文案

- 短。说清当前发生什么、用户接下来能做什么。
- 状态不要冒充事实。推演写“场景假定”，真实回执才写“已通过”。
- 按钮写动作，不写解释；解释留给正文。
- 错误文案不要只说失败，要给下一步。

### 证据说明

证据也可以说人话，但不能降低精度：

- observation：“文件里直接写了什么。”
- inference：“这些线索更像在指向什么。”
- boundary：“但凭这份文件，还不能把什么说死。”

少用重复模板“X 证明 Y，不证明 Z”。可以换成：

- “这足以确认入口被打包了。至于这次会话有没有走它，文件没有回答。”
- “符号把方向指向 AX 和 CGEvent；完整的原生控制流仍然藏在二进制里。”
- “我们看到的是 client 的回执形状，不是服务端的留存策略。”

### 表格与流程图

- 表头用读者会问的话：`现在知道什么`、`卡在哪里`、`下一步`。
- 单元格别塞论文摘要，尽量写成动作和后果。
- 相邻格子不要机械复用同一句式。

## 全量过稿

“所有文本”不只指 HTML 正文。提交前一起检查：

- HTML 中的标题、段落、表格、图注、目录、侧注和 aria 文案。
- JavaScript 运行时生成的状态、错误、按钮和场景说明。
- JSON 中会进入界面的 title、summary、description、statement、boundary、unknown 和 recovery。
- 空状态、加载态、失败态、tooltip 与深链接打开后的文本。

## 自检

大声读一遍，然后问：

- 这一段像人在解释，还是像模型在归纳？
- 连续三句是不是差不多长、差不多结构？
- 有没有先列组件，过半天才说它们为什么重要？
- 有没有具体动作、具体后果或具体反例？
- “这意味着 / 不等于 / 不能证明”是不是重复到像模板？
- 口头禅是不是硬塞进去的？删掉后反而更自然吗？
- 是否编了证据里没有的运行结果、经历或情绪？
- UI 的“已通过”到底是真实回执，还是只是场景假定？

最好的技术写作不是完美无缝。它让读者听得见作者在判断，也看得见作者哪里选择停手。
