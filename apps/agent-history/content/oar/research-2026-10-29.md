# OAR 专题研究：把 Coding Agent 接入做成公共基础设施

研究日期：2026 年 10 月 29 日，Asia/Taipei。

**我的判断：OAR 值得认真试用，尤其适合同时接入多个 Coding Agent 的工作台。但值得采用的是它对原生运行时差异的处理和持续验证，不是“一套接口接管所有 Agent”的想象。它还不是持久任务系统，也不是安全沙箱。**

你发来的 `botivrs/oar` 地址在本次 GitHub API 查询中返回 404，没有验证出重定向。本文研究公开可访问、与项目名称及既有研究相符的 [botiverse/oar](https://github.com/botiverse/oar)，即 Open Agent Runtime，不是同名的 Open Agent Relay。

本次以最新正式版 [v0.75.0](https://github.com/botiverse/oar/releases/tag/v0.75.0) 为发行基线，发布日期为 2026-10-27 20:19:55；源码和本地测试固定到 10 月 29 日主线提交 [`5532d7b`](https://github.com/botiverse/oar/tree/5532d7b2a01f26c553def1f4acb4470c94f0ed36)。发行标签实际指向 `51b83c96811735b3a9f045ab20bab7cd20e61cdf`。主线 `package.json` 仍写 0.75.0，但已经包含未随该标签发布的改动，不能把二者混为同一个版本。

## 1. OAR 统一的不是模型，而是已经会工作的 Agent

让一个模型返回文字，与让 Claude Code、Codex 或 Pi 完成编码任务，是两种接入工作。后者不仅有模型，还有文件工具、上下文压缩、会话历史、子 Agent、权限、账户和安装更新。只把模型 API 换成统一格式，无法保住这些原版行为。

OAR 是 TypeScript 库。宿主通过 `Runtime` 找到安装、查询能力、打开 `Session`，再发送输入和观察记录。底层仍调用厂商提供的 CLI、app-server、ACP 接口或 SDK，不复制一份提示词后另起一个推理循环。库采用 Apache-2.0，ESM-only，Node 入口要求 Node.js 24+；浏览器入口和观察层另行导出。[包定义](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/package.json)

对于一个工作台，最简单的任务是“发一条 prompt，拿回答案”。真正容易出错的是后面这些事：用户临时补充一句要求，该插进当前轮还是排到下一轮？子 Agent 先结束了，父任务是不是也结束？窗口重连后，如何接上遗漏的进度？进程被杀时，最后一条输入究竟有没有被处理？

OAR 的价值就在这些问题里。它把原来分散在每个工作台里的接入逻辑，整理成公共接口、厂商映射和可重复测试。**它降低的是重复集成成本，不直接提高模型的编码能力。** 我没有发现可以据此声称“任务成功率更高”或“成本更低”的独立基准。

## 2. 最扎实的设计：请求、回执和原生事实放在同一条记录流

假设 Agent 正在改代码，用户补充“先别执行迁移”。这是说明机制的假设场景，不是本文运行过的生产任务。

工作台至少要区分四件事：输入已发出、运行时接受了输入、原生会话报告开始处理它、它最终影响了模型行为。前三者有机会留下机器可核对的事实，最后一项不能靠一个 `accepted` 回执推出来。

OAR 的内核把三类记录按 `seq` 排序：`request` 是宿主做了什么，`response` 是这次控制是否被接受，`frame` 是原生运行时发来了什么。`events()`、会话视图、状态和用量由记录派生。控制已经结束，不应该导致晚到的原生事实被丢弃。[记录内核](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/shared/session-kernel.ts)

这不是术语上的讲究。只有把它们放在一起，宿主才能回答“中断请求发生在工具完成之前还是之后”，而不是靠两个独立回调的到达顺序猜。

输入还有自己的 `inputId`。一次逻辑输入可以先尝试 steer，被拒后改为 queue，仍然是同一条用户消息，却有两次控制尝试。新版的 `deliver()` 进一步处理空闲、忙碌和状态竞争：空闲时 prompt；运行中优先 steer；缺少能力时 queue；部分竞争会重试状态判断，真正的拒绝则返回类型化原因。它并非不分原因地不断重发。[投递实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/shared/deliver.ts)

| 看到的状态 | 可以说什么 | 还不能说什么 |
| --- | --- | --- |
| `accepted` | 这次控制被接手 | 模型已经读到或遵从 |
| `input_queued` | 原生运行时报告它在等待 | 已开始本轮执行 |
| `turn_active`，带对应输入身份 | 原生执行已与该输入关联 | 所有后端都有同样强的关联证据 |
| `turn_ended` | 对应 Agent 的轮次结束 | 它启动的所有进程都已停止 |

这些观察不是每个 runtime 都完整提供。OAR 宁可缺字段，也不按文本相似度补出消息关联。未知原生内容仍可保留，之后再改投影，不必因为 UI 暂时不认识某种事件就把证据扔掉。[会话与输入合同](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/conversation.md)

这里有两个容易踩的实现细节。本地探针确认，一个 frame 读出两条 event 时，两条 event 可以共享 `seq`，所以不能拿它当扁平事件的唯一 ID。另一个探针确认，独立子会话的 `turn_ended` 不会满足父会话的等待条件。前者防止漏进度，后者防止误报整项工作完成。[本地探针回执](probe-2026-10-29.json)

## 3. 支持名单已经扩展，但能力矩阵比名单重要

主线默认注册九种 runtime；Cursor 需要宿主注入 SDK，Pi Durable 需要宿主提供 Harness 和 Models。不能看到 README 中的标识，就认为全部都能用 `defaultRuntimes.require()` 直接取得。[组合入口](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/index.ts)

下面是固定源码的能力摘要，不是本文逐个运行过的成绩单：

| Runtime | 接入与当前轮补充 | 后续队列 | 子活动可见性 |
| --- | --- | --- | --- |
| Claude Code | stream-json；stdin steer | 适配器内存 | 同一流内按父工具 ID 归属 |
| Codex | app-server；带 `expectedTurnId` 的 steer | 原生持久队列 | 独立子线程与会话图 |
| Cursor | 宿主提供 `@cursor/sdk`；支持文本 steer | 适配器内存 | 子工具活动归入父 task 路径 |
| Pi | SDK，另有 subprocess/RPC 选择；支持 steer | 非持久队列 | 没有原生子 Agent 归属 |
| Pi Durable | 宿主 Harness；原生 submission | 原生持久队列 | 当前 watch 不包含子会话树 |
| Grok | ACP + 厂商扩展；send-now steer | 非持久队列 | 声明 nested，证据仍有专项边界 |
| Kimi / Antigravity | 所选 ACP 通道无 steer | 适配器内存 | opaque，不补造子树 |
| OpenCode v1 | ACP；可向运行中循环补充输入 | 适配器内存 | 子活动不完整暴露 |
| OpenCode v2 | ACP；并发 prompt 被拒，无 steer | 适配器内存 | 原生 metadata 支持子会话归属 |
| Qwen Code | stream-json；忙时原生输入排队，OAR 不宣称 steer | 适配器内存 | 按父工具 ID 归属；真实嵌套交错未充分验证 |
| Qoder | stream-json；`priority: next` | 适配器内存 | 同样保留原生父工具 ID；真实嵌套仍有验证缺口 |

依据：[运行时矩阵](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/runtime-matrix.md)。这里的持久性是输入队列的属性，不代表整个工作流具备持久执行保证。

我比较认可它在两个地方没有取巧。

一是 OpenCode v2 更“新”，但 steer 反而缺失。OAR 没用旧版能力填满新版表格。二是 10 月 29 日作者针对 Antigravity 的原生 ACP 1.4.4 做了脚本模型实验：并发 prompt 没有进入当前工具循环，还出现完成响应与实际输入处理错位；因此继续不暴露 steer。另一个交互 CLI 入口有即时输入，并不能证明 ACP 也有。**产品能做、选定协议能做、适配器已实现，是三个不同判断。** 这些是作者的实验记录，本次没有独立运行 Antigravity。[专项报告](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/experiments/antigravity-steering-2026-10-29.md)

不支持的操作可以缺少成员，不支持的会话选项则用 `UnsupportedOptionError` 拒绝。比起默默丢掉 `effort`、工具限制或环境变量，这种失败方式更适合产品集成。不过逃生口 `launchArgs` 仍有运行时特定规则，不能把“拒绝不支持的标准选项”扩展为“任何参数都验证有效”。

## 4. 从接入层到编排组件：新增能力有用，但没有接管宿主责任

相较于 AgentLab 10 月 1 日基于 0.10.2 的旧专题，现在最值得补看的，不只是更多后端，而是三组面向宿主的能力。

### 4.1 跨 runtime 子 Agent

`@botiverse/oar/agents` 已有 `createSubagents()`，可以 spawn、发送跟进、等待报告、中断和关闭子会话；`oar mcp` 把同一机制提供给 MCP 客户端。每个子 Agent 根轮次结束，生成带 runtime、session ID、轮次、结果和文本的报告。宿主决定把报告放进收件箱，还是通过 `parent.deliver()` 唤醒父 Agent。[子 Agent 合同](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/subagents.md)

这解决了“Claude 做主控、另一个 runtime 做审查”所需的一部分接线工作。它没有替宿主决定谁能发任务、谁拥有工作目录、失败后怎么重试，也没有提供跨进程可靠消息投递。

我对这里做了两项独立合成检查：

1. **回调收到报告，不等于父会话收到报告。** 先关闭一个合成父会话，再按照 README 的写法在 `onReport` 中调用 `parent.deliver()`。投递返回 `runtime_exited`，而 `crew.unread()` 仍为空。实现只知道同步 handler 正常返回，不追踪它后面的异步投递结果。报告并非从一切记录中消失，但不会自动退回待消费队列。
2. **`maxRunning` 不是会话总数上限。** 设置为 1，串行运行三个合成子任务后，三个 idle session 仍被保留。产品必须另设闲置回收和总资源预算。

这两项更适合被理解为集成合同，而不是“项目完全不可用”的证据。要做可靠编排，应该先持久化报告，再投递、确认、重试；要控制机器负载，应同时限制启动中、运行中和保留的空闲会话。[编排实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/agents/crew.ts)；[探针源码](probe-2026-10-29.mjs)

还有一个宣传语容易掩盖的限制：子 Agent 需要通过 `env` 携带深度，所以当前拒绝该选项的 Cursor 不能由这套 crew 直接启动为子 Agent。`maxDepth` 依赖环境变量传递，原生 MCP 子进程若过滤掉它，也不能把这个深度限制当成跨进程强制安全策略。

### 4.2 不开会话，也能建设 Agent 管理界面

`orient()` 汇总安装、认证、配额、模型目录等观察，保留各项的失败、超时和未知状态。`usability()` 再把它们投影成宿主可用性判断。这个分层很实用：读取失败不该显示成“余额为零”，配置了 key 也不该显示成“远端已验证登录”。

但这些查询的成本不一样。`local` 尽量只做本地检查；`account` 可以联系服务、刷新凭据或执行原生 key command；`models` 可能启动运行时、加载配置和连接 MCP。明确选择 customization inventory，即使在 local 深度，也可能执行用户配置。做配额面板时，不能把这些 API 当成可以每秒无副作用轮询的普通 getter。[发现与就绪状态合同](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/orientation.md)

### 4.3 宿主工具与配置表单

`serveMcpTools()` 把宿主工具暴露为带 token 的 loopback MCP 服务，让支持 session MCP 的 runtime 调用；工具列表更新是否会被运行中的 Agent 看见，仍由能力声明区分。它不验证每次调用是否符合工具的 JSON Schema，宿主必须自己做输入校验和授权。这个 loopback 地址也不是跨机器自动可达的服务。[工具服务实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/mcp/serve-tools.ts)

`@botiverse/oar/forms` 则尝试把配置字段、验证和会话映射变成可供 UI 渲染的数据；目前文档明确是 Grok 先行，不能描述成所有 runtime 都已有统一设置页。[配置表单合同](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/config-form.md)

## 5. 恢复、停止和持久性：必须拆开理解

### 重连观察，不是恢复执行

同一个 Session 的 cursor 可以补读内存记录，然后订阅实时流。重新打开原生会话时，原生 session ID 可以相同，但新 OAR 流从 `seq = 0` 开始；宿主必须另存 `streamId`。Voyage 提供 JSONL 记录文件，却不是数据库事务、任务队列或外部动作的 exactly-once 保证。[会话合同](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/conversation.md)；[Voyage 实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/voyage.ts)

原生 resume 主要延续会话。作者在 10 月 2 日针对当时 Claude、Codex、Pi 的崩溃实验中发现：已接收但尚未进入对话的 steer 可能丢失；适配器内存队列会丢失；Codex 原生队列在该实验中保留，并在 reopen 后自行开始执行。它不是今天所有版本的普遍保证，本次也没有重跑这组崩溃实验。[作者崩溃恢复报告](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/runtimes/crash-resume.md)

### Pi Durable 是另一种所有权关系

Pi Durable 的持久 submission 来自宿主提供的 Harness 和 storage，不是 OAR 给其他 CLI 统一增加的能力。相同 `inputId` 可对应原生 `requestId` 去重，但外部工具副作用仍不因此变成 exactly-once。

最关键的区别是 `dispose()`：在这个适配器里，它停止 watch，**不停止宿主 Harness 中正在运行的工作**。要停止工作，需要原生 abort 和宿主自己的生命周期处置。另有任务因反复中断而 parked 时，OAR 仍可能如实报告存在未结束的 run；宿主要读 Harness 的报告才能知道它已无法继续推进。[Pi Durable 映射](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/runtimes/pi-durable.md)；[适配器源码](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/runtimes/pi-durable/session.ts)

### 超时和 abort 都不是“所有东西立刻停下”

`promptAndWait({ timeoutMs })` 的计时触发 abort，之后仍等待原生结束或退出事实，没有第二个通用硬截止。本地合成探针设置 10 ms 超时，在至少 100 ms 后仍 pending；注入合成退出后才以 interrupted / aborted 收尾。这是 helper 合同，不是某家真实模型卡死的复现。[等待实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/observe/turns.ts)

作者 10 月 28 日的 Linux 实验还观察到，Codex 0.165.0 结束被中断的 turn 后，工具启动的命令仍继续运行；Grok 的部分宿主终端也要到 dispose 才清理。实验使用真实运行时与脚本模型，不是线上任务，也不是本机复现。产品里的“停止”按钮应说明它停止的是当前轮次、整个会话，还是执行环境，而不能把这三件事合成一个绿色完成状态。[作者资源与中断实验](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/experiments/runtime-resources-2026-10-28.md)

## 6. 我最不愿意省略的部分：权限与凭据

### 默认是方便无人值守，不是默认安全

Claude 默认带 `--dangerously-skip-permissions`；Codex 以 `approvalPolicy: never` 打开，缺省 sandbox override 为 `danger-full-access`。这对受控环境里的自动化很方便，但 `cwd` 只是工作目录，不是 OS 隔离边界。提供 `oar mcp` 子 Agent 工具，还可能让本来受限的父 Agent 间接获得子会话的宽权限。[Claude 启动](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/runtimes/claude/launch.ts)；[Codex 会话](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/runtimes/codex/session.ts)

10 月 28 日主线新增了 Claude 非交互原生权限模式：显式指定受支持的 `--permission-mode` 时不再叠加默认 bypass，并禁止无人能应答的交互审批入口。**这项改动不在 v0.75.0 发行标签内。** 即使使用新主线，resume 时也要重新传入模式，遗漏会恢复 OAR 默认 bypass。通用 `Session.answer` 与完整人工审批流程仍未交付。[权限参数实现](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/packages/oar/src/runtimes/claude/launch-args.ts)；[设计决策](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/design/decisions.md)

`disallowedTools` 与 `userConfiguration: "exclude"` 也不能代替沙箱。工具名可能有大小写或厂商组名规则，另一种允许的工具可能完成同样动作；排除用户配置只是改变加载来源，不限制文件和网络访问。宿主需要受限 OS 身份、目录挂载、网络出口和独立凭据，而不是仅仅把危险按钮藏起来。

### 无损记录与日志安全之间，有意保留了边界

OAR 已有凭据字段脱敏、已知 session 凭据按值脱敏，以及旧记录的结构化清洗接口。这比把所有 native payload 原样写盘强得多，但并非通用秘密检测器：它不扫描所有宿主凭据，子进程自己读到的秘密不一定在已知集合里；一段秘密被拆成多个流式 delta 时，单条记录匹配也可能漏掉，之后的聚合文本仍能拼回原值。这些限制在当前规范中明确列出。[记录与脱敏规则](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/spec/record-stream.md)

因此我不建议把 Voyage 文件直接当作可公开分享的 trace。产品应在存储、导出和展示层设置访问控制与脱敏策略。

另外两个 open issue 值得跟踪，但不能扩大成已在本机验证的当前故障：[#402](https://github.com/botiverse/oar/issues/402) 讨论短命 Claude 探测进程和并发进程遇到 OAuth refresh token 轮换的风险，作者尚未把用户掉登录的时间线与 OAR 探测对应起来；[#343](https://github.com/botiverse/oar/issues/343) 记录 Codex 0.162.1 / OAR 0.54.3 默认模式打开 Git 项目时可能持久写入 trusted 状态。前者说明“只查询一下”也可能有凭据副作用，后者提醒宿主不要把用户现有配置当成无痕的临时执行空间。

## 7. 工程质量的亮点，是验证方法；维护成本也在这里

OAR 的测试分层比只 mock `session.prompt()` 更有说服力：单测检查解析与状态；mock behavior suite 检查公共合同；aimock 保留真实厂商程序和适配器，仅把模型 provider 换成可控脚本；vendor tests 看 provider 实际收到什么；live experiments 再处理真实登录和模型环境。不同层回答不同问题。[开发与验证说明](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/development.md)

v0.75.0 对应的 [CI run](https://github.com/botiverse/oar/actions/runs/40495932395) 有 26 个成功 job：三个 OS 常规检查、七种 backend 乘三个 OS 的行为测试，再加 clean-install 与 browser-demo。job 成功不能证明每个可选 case 都运行，更不是十一种 runtime 的真实模型任务全部成功。

维护压力可以从这次发行本身看出来：0.75.0 把 Cursor SDK 从精确的 1.0.40 切到 1.1.0，没有保留旧版兼容路径；同时修正 cache token 的 input 计数口径。旧日志保留原有数字，不会在 replay 时自动重算。工作台升级后看到成本曲线下降，可能只是统计口径变了，而不是模型突然更省。[发行说明](https://github.com/botiverse/oar/releases/tag/v0.75.0)

还有资源成本。作者 Linux 单次资源 cohort 中，十个 Codex 独立 app-server 在短任务后的进程树 RSS 约 1,974 MiB；十个 thread 共用 app-server 的实验约 218 MiB。它不是 PSS、吞吐基准或 macOS 数据，且共享模式没有成为 OAR 默认。这里可得出的结论很窄：**进程所有权换来了简单的清理边界，也可能带来明显的常驻开销；不能仅靠 `maxRunning` 评估容量。**[资源实验方法与数据](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/experiments/runtime-resources-2026-10-28.md)

记录内核目前也保留完整内存 log，一些查询扫描记录求值。长期驻留、大工具输出和大量空闲会话的内存行为，需要用目标负载测试。单元测试很多，并不等于这类压力已经被覆盖。

## 8. OAR 与 ACP、AI SDK、原生 SDK 怎么选

**只用一家 runtime，而且需要深入人工审批、厂商新能力或原生历史读取，直接用原生 SDK 往往更短。** OAR 自己也承认单 runtime 场景未必需要它。它的收益通常从第二种 runtime 开始，但是否划算仍要看你实际需要多少共同能力。

ACP 的重点是编辑器与 Coding Agent 的标准通信。OAR 则既消费厂商原生 ACP，也直接使用 app-server、stream-json 和 SDK，再向宿主提供统一对象与记录合同。所以二者既有问题域重合，也可以上下组合；OAR 不是“ACP 的替代协议”，ACP 也不会自动抹平每家实现的差异。[ACP 官方定位](https://agentclientprotocol.com/get-started/introduction)

有一个比较必须更新：**不能再说 Vercel AI SDK 只统一模型、OAR 才统一 harness。** 本次查到的 AI SDK v7 文档已经提供实验性的 `HarnessAgent`，以及 Claude Code、Codex、Cursor、Grok、OpenCode、Pi 等适配器。它把 harness 输出接到 AI SDK stream、response 和 UI 体系。[AI SDK Harnesses](https://ai-sdk.dev/docs/ai-sdk-harnesses/overview)；[官方适配器列表](https://ai-sdk.dev/docs/ai-sdk-harnesses/harness-adapters)

我会这样取舍：

| 产品要求 | 更值得优先验证的路线 |
| --- | --- |
| 本地多 Agent 工作台，要原生状态、账户、能力差异和完整记录 | OAR |
| 已深度使用 AI SDK / `useChat`，希望延续其结果与 UI 类型 | AI SDK Harnesses |
| IDE 要接入遵循标准协议的 Agent | ACP 客户端，必要时再补原生扩展 |
| 单 runtime，需要它最新、最完整的交互控制 | 厂商原生接口 |
| 跨机器可靠任务、数据库恢复、租户权限、审批系统 | 先设计宿主执行与持久化层，再选择接入库 |

这是基于接口范围的选型判断，不是性能排名。AI SDK 文档明确仍属实验性；其部分适配器采用 sandbox bridge，另一些在宿主进程运行。不能将一个框架提供 sandbox 抽象，写成所有适配器天然具备同等隔离。[HarnessAgent 生命周期与执行环境](https://ai-sdk.dev/docs/ai-sdk-harnesses/harness-agent)

同样，OAR 的浏览器入口可用于可移植内核和投影，Pi Durable 也有浏览器接入；这不代表 Claude/Codex 的本地 CLI 可以直接在浏览器中运行。通用远程 `oar serve`、跨宿主 handoff、运行中统一 `Session.configure` 仍在后续路线图，不能提前算成已交付能力。[路线图](https://github.com/botiverse/oar/blob/5532d7b2a01f26c553def1f4acb4470c94f0ed36/docs/design/roadmap.md)

## 10. 最终看法：值得押注共享维护，不值得押注万能抽象

我看好 OAR 的三个原因很具体：它选择保留原版 harness；对“接受、开始、完成、退出”这些容易混淆的事实认真建模；把厂商差异和验证过程作为库的一部分交付。这比再做一个能切换模型下拉框的聊天界面更有基础设施价值。

但它的长期价值不会由接口优雅或支持标识数量决定。真正要看的是：宿主能否删掉自己的厂商分支；厂商升级后，修复能否通过一次 OAR 升级传播；不相关的消费者能否共享同一套合同，而不是各自 fork。AI SDK Harnesses 已进入同一问题域，OAR 的优势必须靠更深的运行时语义和更好的兼容维护来证明，不能只靠“我们统一 harness”。

我的采用建议是一个有边界的试点：先接两种行为差异明显的 runtime，保留业务侧的调度、存储和权限层；验证忙时输入、取消后工具存活、resume、原生子活动和升级兼容，再扩展名单。不要第一天就把它提升为所有后台任务的调度中心。

如果用于 AgentLab 这类证据导向项目，最值得借鉴的是“固定原生版本 + 脚本 provider + 公共合同与厂商专项分层”的验证方式。至于安装和账户观察，应与公开发布数据分开，不能因为多了一个统一 API 就顺手收集私人运行状态。

**一句话：OAR 有机会成为多 Coding Agent 产品的公共接入层；要成为可靠产品的底座，宿主仍要把消息交付、资源生命周期和安全边界接完整。** 它属于运行时集成与编排基础设施，不是 Agentic RL，也没有凭这些循环就构成严格 RSI。
