MiMo Agent

同一个模型放进不同 Agent，究竟换了什么？

固定一个模型，让它修同一份仓库：一次放进 Claude Code，一次放进 Codex，再放进小米的最小 Agent。模型没换，工具、压缩和错误反馈却都可能变了。

教学场景，不连接真实 Agent、模型或外部工具。

查看依据

Compact 先和工具返回配对；到下一次 query 才请求纯文本摘要。成功后重建 system、压缩边界、原始任务锚点和摘要。

摘要失败或为空时保留旧历史。这是小米白盒的实现，不等于 Claude Code 私有压缩，也不同于 Codex 白盒默认关闭的自动压缩。

压缩不是一个按钮状态，而是会改变之后模型输入的一次历史转换。

查看依据

save_traj 直接序列化 agent.messages。黑盒适配器的 messages 可以只有任务和最终回复，查询参数也可能为空。统一格式不会替你补出中间请求。

事件日志适合回看操作；token IDs、log-probabilities、策略版本和训练掩码则属于另一层采集要求。报告中的 Payload Porter 不能算作每个公开 adapter 已经输出了这些字段。

想评测任务，就检查现场；想做 RL，还得核对推理服务端的数据链。

Agent 说完成了，什么时候才算任务通过？

从进程结束往后走，切换读取阶段。观察交付现场、judge 和 verifier 为什么不能混成一个状态。

查看依据

Completed 只是执行状态。batch runner 还要 attach_rollout 并计算 reward，任务通过与否取决于环境检查。

流程先捕获 model_patch，再运行可选 rubric judge，最后运行可能改动 testbed 的 verifier。调换次序，judge 可能看见的就不是原始交付现场了。

把“退出了”“产物保留了”“任务通过了”做成不同状态，实验才有可解释的结果。

Multi-harness RL 改的是模型在不同运行条件下学到的策略，不等于这些 harness 在训练中自己改写。公开适配器也不等于完整训练集群。

作者的保留 harness 成绩说明了一种迁移检验思路。对自己的实验，先固定运行版本、配置和评分，再讨论提升来自哪里。
