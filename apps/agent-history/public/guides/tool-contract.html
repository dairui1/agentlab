04

重试之前，先问动作有没有发生

call ID 是关联键，不是通用幂等键。

timeout 或断线后，命令可能尚未执行，也可能已产生效果而回执丢失。先查文件、远端对象或领域回执；无法判定时保留 effect_unknown。

后台 child 的提交回执、父 ToolPart 的 completed 和 child 最终结果也不能合并。父调用返回了，不代表所有工作都结束了。

结果不清楚时，先核对世界，再重复动作。

05

一份好结果，让下一步有依据

模型需要能行动的信息，人需要能检查的事实。

保留调用身份、参数、结果状态、工具自己的终态字段和截断标识。后台工作再保留 child 句柄，断线后主动查询。

解释文字不能替代进程退出码、实际文件状态或远端提交回执。

工具把动作做出去，结果合同把动作接回来。

正常路径是提出动作、执行、收尾、读取结果，再决定下一步。

失败时找到缺失的那层回执，把不知道的结果留成 unknown。

TOOL-CC-07 · foreground Bash timeout 是 background transition；MCP timeout 才是 hard deadline

fixed prompt 给 Bash timeout default 120,000 ms、max 600,000 ms，并支持显式 run_in_background。 fixed binary 的 timeout result 明写：command 未在期限内完成，被移到 background，返回 task ID 和 output path，完成时再通知。2.0.19 changelog 也记录从 kill 改为 auto-background；2.1.210 改善了这条消息，防止模型把它误认为显式 background。 control channel 也能按 tool_use_id background 正在阻塞的 Bash/subagent；blocking call 立即返回 “running in background” result，task 继续并在 settle 后发 notification。 MCP per-server timeout 是真正 hard wall-clock；progress notification 不延长，低于 1000 ms 的值被忽略。

把 Bash timeout 状态建模为 foreground -> background_running，不是 failed_timeout。相反 MCP timeout 可以归类 runtime timeout。两个都叫 timeout，但 terminality 相反。

TOOL-CX-08 · shell terminal result 由 status + exit code 判定，stdout/stderr/aggregate 是不同数据

core shell output 同时保存 exit_code、独立 stdout、独立 stderr、aggregated output、duration 与 timed_out。执行完成时 exit 0 映射 completed，非 0 映射 failed；拒绝映射 declined 且 exit code 为 -1。默认 command timeout 是 10 秒，timeout 被规范化为 exit 124 并保留已收集 output。app-server v2 的 public commandExecution 只公开 aggregated output、exitCode、durationMs 和 status，不公开 core 的独立 stdout/stderr。

process outcome vs output capture；stderr 非空不自动等于 failed，exit 0 才是当前 shell success rule。

TOOL-CX-18 · output 有多级截断和投影，delta 拼接不能重建所有 terminal data

core command delta 含 stdout/stderr discriminator 和 raw bytes；app-server 映射时用 lossy UTF-8 转成单个 delta string，并丢掉 stream 字段。shell live delta 最多 10,000 个；retained output 有 byte cap；aggregated output 实现是先 stdout 后 stderr，不保留真实时间交错，超 cap 时还偏向保留 stderr。模型看到的 formatted output再次按 token policy 截断。MCP 的 public event copy另有 byte cap，过大时把整个 structured result塌成 text preview；direct model context又独立截断，而 Code Mode拿 raw result。

live display、public terminal item、rollout event、model context、Code Mode result 都是不同 projection。

TOOL-OC-03 · ToolPart 是四态持久状态机，但 pending.raw 在该实现里不是可靠的参数流

text pending { input, raw } running { input, title?, metadata?, time.start } completed{ input, output, title, metadata, time.start/end/compacted?, attachments? } error { input, error, metadata?, time.start/end } tool-input-start/delta/end 只确保 pending ToolPart 存在。 exact-tag processor 并没有把 delta text 追加到 pending.raw；新建值是空字符串。 正式 tool-call event 才把解析后 input 写入 running，并记录 start time。 tool-result / tool-error 将 running 转为 completed/error；非 running 的 late result 不会再次 settle。 每次 session.updatePart 发布完整 message.part.updated snapshot。

UI 可显示 pending，但不能把 raw 当逐字 tool JSON stream。需要可编辑/可审计参数时，以 running state 的 parsed input 为第一稳定边界；若真要 raw delta，必须在 LLM adapter 层另行采集。

TOOL-OC-04 · 本地工具的通用执行合同包含 validation、permission context、hooks 与统一输出

Tool definition 的规范结果是 title:string + metadata:object + output:string + attachments?。 通用 wrapper 先用 Effect Schema decode 参数；失败转成 ToolInvalidArgumentsError，文案明确要求模型 rewrite input。 Tool.Context 包含 session/message/call/agent、AbortSignal、历史消息、进度 metadata callback 与 permission ask。 tool.execute.before 可修改 args；工具完成后 tool.execute.after 可修改 title/output/metadata。 通用 wrapper 默认对 output 做截断；若工具已经在 metadata 写了 truncated，则避免再次截断。 plugin after hook 位于真实工具执行之后；如果 hook 自己失败，最终 ToolPart 可记录 error，但底层副作用可能已经发生。

至少记录四个时间点：advertised input、post-before-hook input、raw tool result、post-after-hook result。否则难以解释模型发出的参数和实际执行参数为何不同，也无法识别“副作用成功但观测 hook 失败”。

TOOL-OC-05 · Shell 将 stdout/stderr 合并；exit、timeout、abort 都主要藏在 metadata/output

Shell 读取 handle.all，因此 stdout 与 stderr 进入同一个按到达顺序合并的文本流；V1 ToolPart 没有独立 stdout/stderr 字段。 运行中不断用 ctx.metadata({metadata:{output:last}}) 保存最多 30,000 字符的尾部 preview。 正常退出码写到 metadata.exit；不论 0 还是非零，Shell 自身都返回普通 ExecuteResult，所以通常进入 completed。 超时和用户 abort 会 kill process，exit:null，并把原因写进 output 的 <shell_metadata>；工具仍返回 ExecuteResult。 大输出保留尾部，完整内容写 truncation file；metadata 标出 truncated/outputPath。 因此“ToolPart completed”只说明 Shell wrapper 完成收尾，不说明 command exit 0。

Shell 结果至少分成：transport terminal、exit code、timedOut、aborted、truncated。不要用 ToolPart status 生成绿色成功标记；exit !== 0 应是独立 outcome。
