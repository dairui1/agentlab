Code Mode

一段程序接过工具调用以后，模型还需要知道什么？

要比较三个仓库的版本，模型可以逐次问工具，也可以写一段程序：查询、筛选、比较，最后只交回有用的结果。Code Mode 把这段中间工作交给程序。

教学场景，不连接真实 Agent、模型或外部工具。

查看依据

Pi 给脚本 VM 设置 256 MB 内存上限；Codex 的新 V8 isolate 不提供 Node、文件系统或直接联网。它们都把外部操作交给宿主工具。

所以 VM 隔离不能替代工具授权。脚本的资源限制，也不是它调用的每个进程和服务的总预算。

Code Mode 改变工具组合方式，没有把工具本身变成无副作用的计算。

这条思路适合把查询、筛选和重复步骤交给程序，让模型集中看决定性的结果。是否更快、更省或更安全，要在相同任务与预算下测量。

先读懂三份状态，再谈恢复：脚本在内存里做到哪里，会话保存了什么，外部工具留下了什么。

CM-01 · Pi 让工具结果先回到程序

Pi 的 codemode 在 QuickJS 沙盒里执行脚本，再把脚本输出交给模型。脚本不能直接读文件或联网，要通过工具访问外部；工具不必一次列全，可以用异步的 searchTools、describeTool 和 describeNamespace 查找。on 模式保留普通工具入口，only 模式让模型通过脚本调用它们。

工具调用会真的发生。脚本后来失败，前面改过的文件不会自动还原；结束时虽会取消未完成调用，也不能据此认定外部动作已撤销。

CM-03 · Pi 只保存成功脚本对 store 的修改

每次执行前，Pi 从当前会话分支读出 store。脚本成功且确实改了 store，才追加一条 codemode-store 记录；脚本失败则留下部分输出，不保存这次修改。成功时的返回值也会作为文本加入输出。

store 没保存，文件却可能已经改了。恢复时需要同时核对这两处状态。会话恢复和分支读取的规则见 CM-01 所引文档第 56 行。

CM-05 · Codex 每次用新的 V8 环境执行代码

exec 接收 JavaScript 源码，作为 async module 在新的 V8 isolate 中运行。代码用 tools 请求宿主做事，用 text、image 等函数输出结果，用 store/load 留下可序列化状态。它没有 Node、文件系统或直接联网能力；代码结束后，未等待的 Promise 会被丢弃。

这是源码中的默认工具说明，产品可以覆盖它。store 能否在进程重启后恢复、当前安装版本是否启用这套入口，这份说明没有回答。

CM-08 · Codex 把脚本里的调用交给工具运行时

脚本发来的调用由 submit_nested_tool 转成 ToolCall，再交给 ToolCallRuntime.handle_tool_call_with_source。这个请求带着 CodeMode 来源、cell_id 和 runtime_tool_call_id，开始时还会记录 ChildStarted。具体工具在宿主执行，不是在 V8 里重新实现一套文件操作。

CM-09 · Pi 用消息把沙盒和宿主连起来

Pi 每次启动 worker 和新的 QuickJS/WASM VM。脚本要调用工具，就发消息给宿主；宿主负责执行、截止时间和取消，并用共享中断标志配合终止 worker。结束时，没等完的调用记为 cancelled。独立内核直接调用 tool.execute，接入者要另外处理前后 hooks。

这份说明交代了隔离和中断的设计，没有经过本专题的沙盒逃逸测试。工具的授权和外部动作的恢复也不由 VM 自动解决。

CM-10 · Pi 给脚本 256 MB 内存，并限制无效等待

原生 codemode 的 VM 内存上限是 256 MB。没有待处理工具调用、等待的 Promise 又永远无法完成时，脚本立即失败；脚本也不能再启动 codemode。整段脚本的期限由 timeout_ms 设置，默认不设。

256 MB 限的是这段脚本的 VM，不是它调用的所有进程和远端服务。这里尚未实测内存超限或无限循环时的表现。

CM-12 · Pi 宿主接到消息后，才真正执行工具

handleCall 按名称从 tools/globals 注册表取出函数，解析 JSON 参数，带着这次调用的 AbortSignal 执行。脚本结束时，finish 先取消未完成请求、设置共享中断标志，再终止 worker 并交回结果。
