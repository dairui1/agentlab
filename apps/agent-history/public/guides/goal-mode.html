查看依据

Codex 把 goal 用量记进 runtime，在进展边界触线后转 budgetLimited，收尾当前轮，并停止新增 substantive work。检查不是每个 token 都执行。

预算要看它控制哪层状态，而不是只看界面有没有一个数字。

查看依据

Codex 的 ThreadGoal 有持久状态和累计计量字段。Claude 从最新 goal_status 找回 active condition，却重置 turn count、timer 和 token-spend baseline。

已经 achieved、failed 或 cleared 的 Claude goal 不会恢复。恢复一个会话，也不能让机器退出期间的工作自动发生。

恢复的字段决定你能接着问什么，不自动决定现实里已经做了什么。

04

把验收写进目标，也把证据带到停止口

“修好登录”太容易被缩成“代码改过”。一个能停下来的目标需要更具体。

目标应交代做什么、不动什么、用什么证据验收。Codex worker 要回到工作区核对；Claude evaluator 则需要在 transcript 里看到那些证据。

后台任务尚未结束时，固定 Claude 版本会暂缓这次 goal 评估。它只是避免过早下判决，不承诺后台工作最终成功。

原研究的协议、版本差异与已有真实运行资料留在独立来源层。控制机制的差别不替代同任务、同预算的效果比较。

Goal 让停止变成一份合同；合同质量与验收证据，仍决定能否正确结束。

别只问它能不能自动多跑一轮。问谁能改状态、谁能宣布完成、谁能看到验收证据。

这些交互只解释固定合同；没有自动 Goal 被创建，没有真实任务被执行。

GM-02 · Goal 是 thread 上的持久结构

公开 protocol 定义一个 ThreadGoal：绑定 thread_id，保存 objective、status、可选 token_budget、tokens_used、time_used_seconds 与时间戳；状态共有 active、paused、blocked、usageLimited、budgetLimited、complete 六种，目标正文上限 4,000 字符。

protocol 字段不是完整项目管理数据库；里面没有 first-class 里程碑、验收项列表或 blocker 日志。

GM-03 · 用户控制 goal 的生命周期

TUI 动作会拒绝临时 session，并为已保存 task 提供查看、创建、替换确认、编辑、暂停、恢复与清除流程；paused、blocked 和 usage-limited 都可以由用户选择恢复。

这是 TUI 与状态 API 的控制面，不意味着目标在 App 或机器退出后仍会离线执行。

GM-04 · Worker 只拿到窄化的状态工具

Codex 给模型 get_goal、create_goal、update_goal 三个工具；update_goal 只接受 complete 或 blocked，并明确把 pause、resume、budget-limit 与 usage-limit 留给用户或系统。blocked 还要求同一阻塞连续出现至少三个 goal turn。

工具描述能约束模型行为，handler 也限制可提交状态；它不构成一个独立于 worker 的完成判定模型。

GM-05 · Codex 在 idle 边界发起新 turn

Goal runtime 读取当前 thread 的持久 goal；只有状态仍为 active 时，才把 continuation steering item 作为内部输入交给 try_start_turn_if_idle。读状态与启动之间还持有 goal-state permit，避免外部修改和续跑竞态。

idle scheduler 是进程内续轮机制；不证明关机、退出 App 或网络断开后还能在后台推进。

GM-07 · 预算是 runtime 状态，不是一句提醒

Goal accounting 会串行记录 turn 与工具结束时的进展，并按非缓存 input 加 output 计算 goal token；触线后状态转为 budget-limited，当前 turn 收到收尾 steering，后续不再开启新的 substantive work。

检查发生在进展边界而非每个 token 上，因而可能超过设定值；time_used_seconds 是计量字段，不是同等的时间预算。

GM-09 · Claude /goal 是 session 的 Stop hook 包装

Claude Code 2.1.227 仍把 /goal 做成 session-scoped、prompt-based Stop hook。设置命令会注册当前 session 的 condition，初始化 iterations、setAt 与 tokensAtStart；第一次判定 unmet 后才写入 lastReason，并持续把 goal_status 留在 transcript。

它是 session 级完成条件，不是独立的 thread 数据表；同一 session 同时只保留一条 active goal。

GM-10 · Claude evaluator 有三种结果，但仍只看对话

evaluator 不会独立运行命令或读取文件，只根据 condition 与 transcript 返回 met、unmet 或 impossible。unmet 会携带 reason 继续；met 与 impossible 都会卸下 hook 并清掉 activeGoal，后者另记 failed goal_status。

impossible 是 evaluator 的失败终态，不是 Codex 式可恢复 blocked 状态；裁判也不保证看见 conversation 之外的真实工作区。

GM-11 · Goal condition、task budget 与 maxTurns 分属不同层

Claude /goal 会显示运行时长、已评估 turn 与 token spend，但 activeGoal 没有 token budget 或 maxTurns 字段。交互式轮数边界要写进 condition。最新版的 --task-budget / taskBudget 是 agentic loop 外层、模型可感知的建议性 token 预算；--max-turns 是非交互 --print 的通用硬上限。它们都不会生成 goal 自己的 budget_limited 状态。

task budget 是建议性外层预算，不承诺像硬 token 闸门一样精确停止；供应商、会话与组织策略仍可能施加其他限制。

GM-12 · Claude 从 transcript 恢复 condition，但重置计数

恢复仍处于 active 的 session 时，Claude Code 会带回 condition；turn count、timer 与 token-spend baseline 全部重置。已经 achieved、failed 或 cleared 的 goal 不会恢复。发布产物会反向扫描最新 goal_status，再决定是否重挂 Stop hook。

session 文件损坏、强制崩溃或跨机器恢复仍可能有额外边界；恢复 condition 也不等于恢复一份跨 session 的累计预算。

GM-14 · 差别在完成权，不在能不能多跑一轮

两套实现都会跨 turn 继续工作，但 Claude 把“现在能不能停”交给 transcript-only evaluator，并允许它以 achieved 或 impossible 结束；Codex 把“goal 是否仍 active”交给持久 runtime，再由同一个 worker 申报 complete 或 blocked。前者有角色分离却缺工作区视野，后者有工作区视野却保留自证风险。

这是控制权位置的对照推断，不等于哪款产品整体更可靠；实际结果还取决于目标写法、模型、工具、权限和验证材料。
