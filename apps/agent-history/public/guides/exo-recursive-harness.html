查看依据

默认启动把整个 ROOT_DIR 以 --rw 挂进沙箱，而宿主状态 .exo 位于仓库下。底座源码和本地事件文件因此可能落在模型可写的树里。

正常 API 只追加事件，文件后端却是普通 JSON 对象。expected_head 和写锁维护并发顺序，不是针对直接文件修改的签名或哈希链。

先追到真实路径和挂载，再判断“可信”是职责名称还是已强制的权限边界。

查看依据

记忆工具最多保留 200 条、每条 600 字符，并在每轮完整注入。它是可审计的事实列表，不是语义检索或模型参数学习。

源码 TODO 指出跨 conversation 的 read-modify-write 没有 compare-and-swap。并发时，两次写入可能都基于同一份旧列表。

持久保存和并发不丢更新也是两种保证，不能只用“有记忆”概括。

Exo 已经提供认真设计的递归自修改路径：可观察、可修改、可重建，以及分开的恢复原语。

要称为闭环 RSI，还缺统一目标、候选实验、独立评价、采用门禁与跨代收益证据。能改自己，是前半程。

EXO-01 · 持久底座与策略层被明确拆开

官方架构把 exoharness 定义为持有 identity、append-only event log、artifact、secret 与 sandbox lifecycle 的有状态底座；executor 负责 Prompt、模型调用、工具调度、记忆、压缩和 approval，可被停止、升级或替换。

这是项目定义的信任模型；边界是否被默认部署真正强制执行，需要继续核对 mount、存储与 guardian。

EXO-02 · 模型循环属于可替换层

默认 Exo Harness 用 runResponsesHarnessTurn 驱动一轮，并把指令组装与工具注册作为参数传入；registerExoTools 每轮从 profile、配置模块和 agent-installed tools 重新构造工具面。

EXO-04 · 整个源码仓库默认以读写方式进入沙箱

canonical 启动的 ensure_self_repo_mount 把 ROOT_DIR 挂到 /workspace/exo，并显式传入 --rw；因此模型通过 shell 不只可改 Prompt 和工具，也能改 crates/exoharness、guardian 脚本以及仓库内其他文件。

这里确认的是默认挂载声明；容器运行时、宿主权限和外部只读文件系统仍可能施加额外限制。

EXO-05 · 自修改的激活入口是一个固定 guardian 操作

rebuild_and_restart_exo 不接受任意 host command，只生成 update id 和 queued record，然后异步调用 guardian 的 restart-all --build；当前 turn 可先结束，结果再写入 .exo/guardian-updates 并追加 host event。

入口形状很窄，但它没有独立审批参数；能否激活取决于当前模型是否拥有该工具及 host 进程权限。

EXO-06 · guardian 只构建 Exo binary 与 scheduler

guardian 的 build_all 执行 cargo build -p exo 和 scheduler-runner build，然后请求 REPL child 重启；这条路径没有自动运行完整测试、行为基准、候选对照或独立 evaluator。

编译成功能阻止部分坏改动激活，但不能证明任务质量、安全性或长期收益提高。

EXO-07 · 事件、Prompt 与 artifact 是三种不同状态

事件以 UUIDv7 排序并持久追加，executor 从事件派生给模型的 Prompt；artifact 则是不可变、带版本的 bytes。压缩可以写成 custom event，但不会成为 exoharness 的硬编码语义。

API 只追加不等于存储介质具备防篡改签名或 append-only filesystem 属性。

EXO-08 · 文件后端把每个 event 写成普通 JSON object

BasicExoHarness 在 conversation/events 下按 event id 写单独 JSON 文件并更新 record.latest_event_id；读取时列出这些 JSON 再按 id 排序。写锁与 expected_head 保护并发顺序，但没有哈希链或签名验证历史完整性。

这是默认 BasicObjectStore 的代码路径；远端 object store 可以有额外保留策略，但当前数据模型没有要求密码学防篡改。

EXO-09 · 默认部署的 trusted substrate 不是强制不可触碰

官方文档说 canonical state 位于宿主 .exo，启动脚本又把包含 .exo 与 crates/exoharness 的整个 ROOT_DIR 以 --rw 挂进模型可执行 shell 的沙箱。按这组默认路径推断，模型可破坏事件文件或修改底座源码；“trusted”目前更多是架构责任与建议边界，不是同一份默认配置中的不可变隔离。

这项推断没有在本机安装并运行 Exo 做破坏性验证；若部署方把 .exo 放到未挂载位置、使用只读 checkout、MAC policy 或独立远端 storage，这个风险会缩小。

EXO-10 · 沙箱回滚不会回滚全部 Agent 状态

snapshot_sandbox 与 rewind_sandbox 只操作所选沙箱的文件系统；conversation event、artifact、adapter、scheduler、secret 与 git 工作树属于其他状态面。项目自己的自控文档明确把 git restore/revert、manage_tool 与 disable_adapter 列为不同回滚路径。

snapshot 支持依赖 backend；attached sandbox 与远端 provider 不保证同等能力。

EXO-11 · 持久记忆很小、可审计，但并发会丢更新

remember 把最多 200 条、每条最多 600 字符的事实写入 agent artifact，并在每轮完整注入；源码 TODO 明确指出跨 conversation 的 read-modify-write 没有 compare-and-swap，两轮并发可能都从 N 写 N+1，丢掉其中一次更新。

这是事实记忆工具，不是针对长历史的语义检索，也不是学习参数或自动经验归纳。

EXO-12 · 工具与 Prompt 可以演化，但没有统一候选实验协议

工具可以通过 manage_tool 从 workspace-relative source 安装，Prompt 与 tool schema 则通过普通代码修改后 commit、build、restart 生效。项目规范要求先检查、优先可逆、风险操作前 snapshot，但这些是 Prompt 和操作流程，不是自动生成候选、评分并择优的优化器。

受约束的工具 manifest 和 git history 提高可审计性，不等同于证明修改带来性能提升。

EXO-14 · 目前更准确的分类是 RSM 平台，而不是闭环 RSI

Exo 已实现 recursive self-modification 所需的可见源码、可写 Prompt/工具/Harness、可重建激活、持久历史与多种回滚原语；但 main 中没有统一 improvement objective、自动候选生成、隔离 canary、独立 evaluator、统计比较、adoption gate 或跨代收益曲线。

项目分支或作者私有实验可能有额外评测；固定 main 只能支持“能改自己并恢复”，不能支持“已经递归地产生可测净改进”。
