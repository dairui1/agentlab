DeepSeek Harness 让上层依赖能力接口，具体实现由插件提供。下面先搭一个一致的工作现场，再跟着请求穿过会话日志、执行循环和外部接口。

一项可替换能力有三个角色：Definition 定义请求与结果，Provider 实现动作，Consumer 使用接口。模型工具是 Consumer，不必绑住某个本机实现。

文件系统、subprocess、shell、terminal 和 LSP 共享执行世界。换 Provider 的时候要沿依赖一起换，而不是只把读文件移到远端。

架构的替换点不是一个 class 名字，而是一组共享现场的能力。

查看依据

默认循环先记录 turn/start，再领取 inbox 输入。实际进入执行才写 step/start，消息从 Session 日志派生，流式 chunk 与聚合消息也回到同一条日志。

查看依据

session/event 留下需要跨 reload 的事实；agent/* 拿着 live Agent 做运行中拦截；fs/*、tools/* 等 capability event 让能力策略不必导入默认 loop。

Waterfall listener 要显式调用 next 才继续委托。不调用就停在当前 listener，不能把它当成单纯的广播通知。

事件名字之外，还要知道它保存什么、持有什么对象、怎样继续执行。

查看依据

三种入口都使用 Agent service，却没有同一份协议保证。Headless 用进程生命周期包住一次任务，SDK 发会话通知，ACP 提供更窄的自动化表面。

启动装配也要留意覆盖顺序：bundle、profile patch、home patch、CLI overlay。模板只说明默认组合，最终组合看实际 --dump-config。

按需要的结果、控制和生命周期选入口，不按“有没有 JSON-RPC”选。

这套架构把装配、执行、事实和扩展分开：上层依赖接口，插件提供实现，日志保留可重建来源。

新增产品行为时先找对应 service、event 或 host integration。只有默认 driver 的生命周期真的需要改变，才先去改 Agent Loop。

架构文档把模型适配器、工具注册表、Session log 和 Agent Loop 都列为插件；插件通过共享 Context 提供 service、typed event 与可逆 effect，卸载时注册随之撤销。

文档说明设计规则和配置能力，不证明任意第三方插件组合都能正确启动或安全协作。

DSH-04 · Turn 在领取输入前打开，并保证写入终态

默认 loop 先记录 turn/start，再领取 inbox 输入并经过 agent/pre-step；reject、首步空输入、取消或异常都通过 finally 写入 turn/end，只有实际进入的 step 才写 step/start 与 step/end。

这是默认 agent-loop 的静态控制流；插件可在 waterfall 与 stopping event 上改写或阻断路径，具体事件序列仍需 trace。

DSH-06 · Session append 在入日志前验证并快照

Session.append 先把 payload 与 surface metadata 转成 lossless JSON snapshot，校验 surface 关系并拒绝重入，之后才分配 seq、写入 log 并同步通知观察者；观察者失败不会撤销已接受事件。

这是内存日志的接受与发布规则；持久化由其他插件异步处理，进程崩溃时哪些事件已 flush 不能从这里单独推出。

DSH-07 · 模型历史不是第二份独立状态

Session 子系统把 append-only typed event log 定义为交互历史的事实源，LLM message history 与 replay 都从同一事件流重新派生；插件还能通过 declaration merging 扩展事件词汇。

event-sourced 设计保证可重建的来源一致，不保证摘要、外部副作用或未 flush 的存储在所有故障点都完整。

DSH-08 · 事件分域，Waterfall 需要显式委托

架构把 session/event 用于需要跨 reload 的事实，把 agent/* 用于携带 live Agent 的运行中拦截，把 fs/*、tools/* 等 capability event 用于不导入 loop 的策略与适配器；waterfall listener 必须调用 next() 才会继续委托。

领域分类给出放置规则，不证明每个已有插件都没有跨域耦合，也不能替代对实际 producer/consumer 的逐项检查。

DSH-09 · 可替换能力必须包含三个角色

架构把 capability seam 定义为 Service Definition、Service Provider 与 Consumer 三个角色；Provider 可以替换，Consumer 依赖 service interface，而不是导入默认 loop 或具体实现。

三角色是架构完整性的要求，不证明任意两个 Provider 具有相同性能、安全属性或部署依赖。

DSH-11 · SDK runtime 使用行分隔 JSON-RPC

SDK protocol 在 caller-owned byte stream 上以一行一个 JSON-RPC 2.0 frame 传输，公开 initialize、session/prompt、shutdown 与 session、subagent 通知；当前没有 cancel、session close 或协议版本协商。

协议文档说明这一固定提交的 wire surface，不保证 RC 版本间兼容，也不代表当前 Python SDK 已在所有平台公开发布。

DSH-12 · ACP 是独立的自动化适配器

ACP 插件通过 stdio 驱动 ctx.agents，支持 fresh session、prompt、cancel 与一次性 permission；它只输出 committed assistant text，并明确不提供恢复、编辑器、工具进度等交互表面。

ACP 适配器暴露的能力比内部 Agent service 更窄；从协议可调用不能推出客户端已经配置好模型、权限或 workspace。

DSH-13 · Headless 是一次性 runner 而不是服务器

headless bundle 创建一个持久 Agent、提交一条普通用户消息并等到 idle，再把最后一条非空 assistant text 写到 stdout；它不开监听端口，也没有交互式 follow-up。

一次性 CLI 适合 command-in/text-out 集成，不等于 SDK 的事件流、Session 生命周期或 ACP 的取消语义。

DSH-14 · 普通产品行为不该默认塞进 Agent Loop

从架构列出的扩展路径看，新行为通常应先落到 session event、agent/tools event、capability service、preset 或 host integration；只有默认 driver 的生命周期本身改变时，才需要修改 agent-loop。

这是根据项目明示的 extension map 得出的放置判断，只说明首选责任归属；不能证明任何跨层需求都无需 loop 变更，实际改动仍要检查生命周期不变量。
