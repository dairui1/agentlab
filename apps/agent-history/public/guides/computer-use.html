查看依据

ActionResult 报 effect、route、delivery 与有限 evidence。verify_state 另查调用方定义的业务条件：satisfied、unsatisfied 或 unknown。

把这两份结果并排看，就不会因为出现一个光标动画，或一次 action confirmed，就提前宣布文件保存成功。

动作发生和事情做成，是两份证据。

04

回执丢了，先别再点一次

超时最麻烦的地方，是动作可能已经发生。

Codex 固定 transport 有 request ID、deadline 与 reconnect，却没有从静态文件得到通用幂等键和 durable action receipt。断线后仅凭失败回执，副作用是 unknown。

先重新看界面与目标对象，再决定要不要重试。旧 element index 在窗口重排后是否一定 fail closed，Codex 与 Kimi 的现有静态资料也没有给出完整保证。

看不清结果时，补观察，不补点击。

05

后台能力，最终要看有没有打扰人

状态合同之外，还有焦点、光标和输入泄漏。

Pi 按物理资源分 lane，Cua Driver 的能力矩阵区分后台与前台，并记录安全拒绝。无法安全投递时，精确 refusal 比伪装成功更有用。

虚拟光标只是呈现：它不授权、不执行，也不证明成功。真实后台效果还要在同 App、同初始状态上检查焦点、z-order、输入泄漏和用户接管。

能点与能可靠地共用桌面，不是一道题。

Computer Use 的核心是把一次观察、一次动作和一次回看接起来，不是把鼠标动画做得更像人。

固定源码可以解释状态协议；跨平台表现与同任务成功率，仍要独立运行验证。

CU-31 · Pi 用 resource epoch 在动作送出前拒绝旧写入

Pi 按物理资源调度实时操作：桌面以进程、CDP 以 page target 分 lane；每个资源有单调递增 epoch。mutating call 必须带观察时的 epoch，若并发写入先一步完成，旧调用在 dispatch 前被拒绝。

按进程串行是保守策略，不代表所有跨进程系统 UI 副作用都能被该资源键覆盖。

CU-32 · Pi 把动作、验证和后继状态收进一个事务

act_ui 接受一个或多个顺序动作，可附 semantic postcondition。helper 逐步 preflight、delivery、verification，返回 worked/didnt/unknown；bridge 保存完整后继状态，只在 identity 可信时渲染 diff。失败或部分执行会给出停止边界并要求重新观察。

语义 postcondition 比事件投递更强，但仍只验证调用方明确表达的可观察条件，不等于理解了完整业务结果。

CU-36 · Cua Driver 把动作事实与业务后置条件彻底分开

ActionResult 只报告 effect、route、delivery 与有限 evidence；effect 是 confirmed、partial、unverifiable、suspected_noop 或 refused。调用方定义的业务条件由独立 verify_state 返回 satisfied、unsatisfied 或 unknown，escalation 只是建议，不能触发 Driver 自动重试。

closed result contract 能减少语义混淆，但它只能证明合同怎么定义；真实 evidence 是否充分仍要看平台实现与动态测试。
