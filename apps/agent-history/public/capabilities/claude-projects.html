你在项目里说“修复登录失败，顺便查一下最近的报错”。几分钟后又补一句“先别上线”。一个像 Projects 的系统，不只是开两个聊天窗口：它必须知道这句补充属于哪项工作，原来的执行者是否收到，谁有权发布，以及进程重启后哪些任务还没有结束。

本文研究的是 Code 里的新版 Projects，不是 Chat 的知识库项目。阅读顺序是：先看外部实验和工具合同，再把它们转成一份可实现、可验收的产品设计。完整实体、事件、API 伪代码和测试用例在 复刻设计文档；工具与证据保留独立、可下载的数据索引。

实验回答“发生了什么”，工具参考回答“接口怎样约定”

pstack 在一个真实项目里安放 canary，观察仓库配置是否加载、线程收到什么、共享文件是否可见，并从 transcript 回读关键事件。它给出了单个项目、单次运行的实测报告，我们没有重新执行这组实验。

dot-tool-reference 则是一份在项目会话内由模型整理的工具参考：63 项协调者工具，区分作者见过的返回值与仅从描述推定的输出。末尾的工作方式说明也是模型转述，不是服务端源码或逐字系统 Prompt。

两份材料都没有表明自己使用了 REA。这里接入的是公开探针和工具快照，不把“研究过内部行为”改称“已经逆向拿到 Projects 源码”。

协调者决定工作去向，线程负责持续执行

最重要的划分不是“主模型 / 子模型”，而是三种生命周期。Coordinator 面向项目总聊天，接请求、看进度、启动或续接工作；Thread Session 绑定一条讨论，持续执行并向该线程交付；worker 是一次委派的辅助执行者，结果回到父会话，不能当成新的项目线程。

pstack 的协调者没有 Bash、Read、Write 等工具，但它能派出拥有这些工具的 worker。这里的“没有文件工具”不能扩大成“底层没有 VM”。实验中的 worker 就在协调者的 VM 上运行。线程则可以自己执行命令，普通 Agent 子任务也不等于继续创建 Projects 子线程。

复刻时至少拆开四类记录：Project 保存配置；Message 保存谁说了什么；Thread 保存讨论根与工作绑定；Session 保存一次具体执行。不要用一个“chat.status”字段包办所有含义。工具参考会分别返回线程状态、runner 状态；“已解决”也不是“进程退出”的别名。

建议把身份映射留在适配器数据库里。pstack 观察到一对 cse_ 与 session_ 的对应关系，但生产系统不应靠替换前缀猜 ID。默认会话列表过滤掉 Projects，会话又可按 ID 查询，也说明“列表没找到”不是“会话不存在”。

先落消息，再决定答复、续接还是启动

协调者的普通最终文本不自动等于用户看见的消息。pstack 记录它使用 post_message 发言；工具参考进一步区分总聊天、没有执行会话的讨论，以及已经绑定会话的线程。向最后一种线程补充工作，要用 message_thread，不能只往 UI 贴一条看似已经送达的回复。

  1. 接收：服务端保存真实用户的消息、作者、项目、时间和附件，得到稳定消息 ID。
  2. 分流：已有工作的补充交给对应 Thread；独立工作创建新 Thread；简单问题直接答复；目标不清楚则澄清。上述分类是原文的角色说明，具体分类器由复刻者选择。
  3. 绑定：新工作锚定用户消息或协调者自己创建的顶层帖子。不要把已经绑定的线程当新根无限嵌套。
  4. 启动：返回 Session 标识和接单回执后异步准备环境。created 不表示模型已开始执行，更不表示任务完成。
  5. 交付：线程产生可核对的事件和结果，协调者在需要时摘要回项目，而不是复述每次工具调用。

其中 start_thread_session 的重复调用行为，在参考中是“已有运行会话则复用”的契约。本文建议用数据库唯一约束、幂等键和 transactional outbox 实现这个承诺，而不是让模型记住“不要重试”。这种事务设计是我们的选择。

消息展示还需要版本。pstack 的协调者读到一条被线程稍后编辑的旧结果，误以为报告被截断。工具参考也允许静默编辑消息；因此 UI 应记录 revision，汇总时注明读取到哪个版本，不能把一次摘要当原消息永久副本。

“用户同意了”不能只存在于协调者的转述里

pstack 从 transcript 确认：启动 brief 被装进协调者 relay，明确区分于用户原话。内容基本保真，但每行多了包装缩进。project instructions 也带不可信内容标记。这里值得复刻的是来源分层，不是那几个 XML 标签或 nonce 的字面形式。

工具参考提供了更明确的入口：context_message_ids 由服务端重新读取合格消息，把正文、作者和时间一起复制；它不是允许模型随手拼一个“用户原话”的字符串。message_thread 最多引用 8 条上下文消息，非法引用会让整次发送失败。线程根、来源权限和跨线程标记都要在服务端检查。

复刻接口可以接受 {text, contextMessageIds}，但可信 envelope 的 actor、origin、authority 必须由鉴权后的服务端生成。模型生成的 brief 只能补充目标；需要本地操作或外部副作用时，继续核对真实用户请求和审批记录。附件也只引用本项目合格的用户上传，不能把任意 URL 或本地路径当可转交文件。

pstack 还试过用 CLI 按 Session ID 注入一条普通 user turn。那条路径缺少正常项目消息的作者、消息 ID 等 envelope。它是研究发现的另一个入口，不是本文建议的可信路由实现，也不是 Projects 的公共兼容 API。

仓库列在项目设置里，不代表协调者已经读过它

pstack 先把仓库加入项目，协调者仍没有读到仓库的 CLAUDE.md、skills、agents 和 hooks。worker 尝试 clone 也失败。之后实际调用 add_repo，worker 才能 clone、运行脚本并 push；再调用 register_repo_root，协调者才出现仓库说明和扩展配置。

这张表不涵盖多仓库优先级、所有 worker 或本地线程。特别是协调者启动后注册仓库，并没有补跑 SessionStart；如果你选择在自己的产品里补跑，应标成产品决策，并防止有副作用的 hook 被重复执行。

复刻的上下文构建器应保存 settings_version、仓库 revision、记忆版本和启用的工具面。工具参考说设置更新作用于后续子会话，正在运行的协调者不会因此重新提示；而较早 pstack 实验观察到项目说明更新通知。这是两份材料在时间和入口上的差异，不能偷偷合并成“所有会话实时热更新”。

分支名、模型和 effort 也属于启动配置，而不是让协调者随意优化的细节。工具参考要求模型覆盖来自明确用户选择；分支建议值则可能由服务端追加唯一后缀。

共享文件可见，不等于并发写入已经安全

Library 在实验中是同一份项目文件存储：协调者的 worker 写入 /mnt/project-files，新线程随后读到，界面也能显示。它适合保存研究笔记和交付文件，但共享可见性不会自动提供任务归属、编辑锁或冲突合并。

项目记忆是另一条接口。read_memory 读共享 MEMORY.md；update_memory 是整文件替换，不是 append。该端点的 16,384 字节上限只约束这次更新内容，不能解释为整个多文件记忆系统最多 16 KiB。工具参考没有给出 memory-store 工具的完整 Schema。

复刻建议：把 MEMORY.md 作为短索引，主题文件保存事实与决策；每次读取返回版本，写入必须带 expected_version，冲突时重新读取和合并。共享文件同样需要路径归一化、项目隔离、大小限制和原子替换。版本比较与 CAS 是本文增加的可靠性设计，原材料没有证明 Claude 使用或缺少这些机制。

任务状态不应只写在记忆里。数据库保存会话绑定、审批、投递回执和最后处理的事件；Memory 保存跨任务有用的信息。否则一次模型摘要丢失就可能把“尚未发布”变成“已经完成”。

本地文件可访问，与代码在本机运行，是两回事

工具参考区分 start_folder_thread 和 start_rc_session。前者提供受限的本地目录文件访问，不提供本机 shell、工具和账号；后者明确在用户设备上运行 Claude Code。本文选择云端承载前一种文件桥接，但原材料没有直接定位其执行宿主。把两者做成一个含糊的“本地模式”，会让权限与进程位置失真。

RC 启动需要真实消息锚点、精确目录或环境选择，并可能先返回 pending_consent。审批卡未确认时没有运行会话。预批准目录也有边界：不要因为某项目获得过一次权限，就向它开放任意目录。设备在线、RC 连接和任务正在推进，应分别显示。

实现上让 CloudRunner、FolderRunner、RemoteControlRunner 共享状态查询与投递接口，但各自声明工具、挂载、凭据、审批和记忆装载能力。两份材料不够完整描述所有本地上下文；因此必须把本地记忆注入列为独立验收项，不能把上面的云线程 canary 表照搬过去。

用持久事件恢复工作，不靠协调者“记得”

协调者通常按线程摘要掌握进度，但 pstack 已经从 list_events 回读完整 transcript，包括工具结果和 hook 事件。因此设计上应区分“默认注入的少量上下文”和“按需查询的完整日志”。分页游标和事件类型过滤能控制成本，摘要则应记录截至哪个事件。

工具参考的角色自述提到协调者会被替换，并依据近期消息、线程与记忆接手。但 pstack 没测试重启后仓库 attachment 是否还在，也没测试 routine 创建全新 Session 或线程并发上限。我们可以把恢复作为复刻目标，不能写成已经观测到的可靠性保证。

本文建议每个 Project 使用一个带租约与 fencing token 的协调者执行权；写入消息时同步写 outbox，消费者按事件 ID 去重；重启先对账 Session，再续接待投递事件。收到消息、队列入列、模型读到、产生交付，分别记录回执。不要承诺网络意义的 exactly-once：外部发布成功而本地回执丢失时，只有下游支持稳定业务幂等键才能直接重试；否则进入 outcome_unknown，先对账或让用户确认。

定时器也要持久化。pstack 观察到一次一分钟 check-in 比计划触发时刻晚约 36 秒；工具契约则将 send_later 解释为一次性定时触发。复刻时记录计划、实际投递和完成时间，取消后拒收旧事件，不把单次延迟写成 SLA。

最后，pstack 还遇到要求 commit/push 的 Stop hook。这是该实验 Harness 的行为，不应该变成复刻产品默认强制推送用户代码的理由。交付门禁应检查用户授权、测试结果和目标分支，失败时保留未完成状态。

先做可恢复的单线程，再加并行和本地设备

不必先复刻全部 63 项工具。最小闭环是：用户发消息，协调者创建绑定，Runner 接单，Thread 交付结果，用户补充后仍回到同一份工作。然后在每个边界注入重复、断线和权限错误。
