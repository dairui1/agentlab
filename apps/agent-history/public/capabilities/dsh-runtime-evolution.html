给模型一个 run_code 很容易。让它一次查十个文件、过滤结果、只返回几行摘要，也不难。真正需要设计的，是下一次调用：上次的变量还在吗？变量里存着的工具函数，是否仍然有权执行？用户刚收紧权限，旧程序发出去的写操作怎么办？

DeepSeek Harness 的 0.2.1 开发周期提供了一组很好的样本。它把这种程序化工具调用称为 Programmatic Tool Calling，简称 PTC。它没有把这些问题都交给一段更长的 Prompt，而是分别放进执行器、工具桥接、Session 状态和任务生命周期。本文沿实际版本差异拆解这些选择。代码用于说明机制，文中的自研方案与验收建议是本文推导，不是 DSH 的官方实现承诺。

如果还不熟悉 Code Mode，可以先读用程序连接工具。这里往下走一层：不再讨论“为什么写代码比逐次调用工具方便”，而是讨论一个可长期运行的实现必须守住哪些约定。

先确定基线，否则一段 diff 能讲出三个不同的故事

0.2.1-rc.1 的发布说明汇总了自 0.2.0-rc.2 以来的变化，不能当成它相对前一天 alpha.5 的新增清单。本次直接比较官方 Git 对象：alpha.5 → rc.1 的 355 个改动文件，全部只更新 package.json 的 version 字段。核验脚本还逐个解析 JSON，检查其他字段没有变化，而不是只看文件名。

另一个容易误判的地方是大段缩进变化。PTC 桥接代码被新的生命周期包装后，看起来改了几百行；忽略空白再看，工具并发调度、类型化返回值、图片回传和调用结束时排空任务，很多在 0.2.0 已经存在。下面会把旧基础、此次扩展、期间修复分开讲。

这也限定了本文与 1017 模型的关系。官方称新模型在训练期间针对 Harness 做过优化，但没有在这份发布材料中给出新旧 Harness 的同模型消融实验。我们能研究工程机制，不能把每项改动换算成跑分提升。rc.2 的 1017 标签本身明确是 display-only，不改变请求路由。

Code Mode 的执行约定不只是“执行 JavaScript”

假设模型写了 return await tools.lookup(...)。如果执行器把它包装成 async function body，这段代码成立；如果执行器接收 REPL 程序，顶层 return 就不成立。再假设代码运行成功，却既没打印，也没按当前模式产出返回值或末尾表达式，模型可能拿不到结果。这里并不是模型不懂编程，而是 Harness 没把“这段代码在哪里、以什么形式运行”说准确。

DSH 新版让运行时提供 programFormat 等执行信息，工具说明和生成的 SDK 指令据此选择函数体或 REPL 的写法。函数体模式明确允许顶层 await 和 return；REPL 则支持顶层声明、await，通过 console.log 或最后一个可无损表示为 JSON 的表达式输出，不能使用顶层 return。工具 schema、系统里的 SDK 和示例需要同时匹配，修一处还不够。

要准确描述这次变化，还得补一段时间线：0.2.0 原本就说明了函数体、顶层 return 和输出方式；alpha.3 引入另一种执行模型后，部分文案变得笼统；alpha.5 又恢复函数体专属说明，同时保留 REPL 分支。因此值得借鉴的不是“多写一句支持 return”，而是从运行时能力生成模型可见的执行约定，不让一段固定文案同时描述两种解释器。

自研时我会把语言、程序形式、状态寿命和权限模型拆开。language: typescript 回答语法，programFormat 回答顶层怎么执行，stateLifetime 回答下次还能看见什么，authority 回答代码通过什么路径取得能力。Node、V8 isolate 和 Python 不是可以只替换名称的三个后端。

还有一项容易遗漏的收敛：工具呈现移除了 both 混合模式，保留 native 与 ptc。PTC 模式下，SDK 里的函数声明不是一个同名的外层工具；模型要把调用写进 run_code。这不只是从 schema 隐藏入口，宿主的直接调用路径也按相同规则拒绝被折叠的工具。如果同时暴露两种入口，就必须承担选择、命名和回放的一致性成本。DSH 选择减少这种组合，但这不是说所有 Harness 都应该禁止双入口。

也别把这理解成“工具定义不再占上下文”。当前可见工具的参数与返回类型仍会生成完整 SDK，进入模型上下文；TypeScript 类型只是提示，执行前剥离类型语法，不会代替宿主的参数和返回值校验。Code Mode 改的是编排与反馈方式，不自动等于按需发现工具或消除全部 schema token。

保留变量之后，异常处理也成了状态协议

原来每次执行都是独立的一次调用。新增的 in-memory 模式允许同一个 live Agent 在多次运行中复用变量、函数、闭包和导入模块。这对反复处理同一批数据很实用：不必每轮重建所有中间对象。但它是可选项，默认仍是 per-call，不能把“升级了客户端”写成“所有 Code Mode 都自动拥有持久内存”。

这个“持久”也有准确的边界。桥接层把状态归属绑定到当前 Agent 对象，并在 Agent 生命周期结束时释放运行时；没有 owner 的调用使用临时执行环境。同一 owner 的重叠执行会被拒绝，不同 owner 可以各用自己的状态。它不是按聊天 ID 建一张永不清理的全局变量表，更不是进程重启后的恢复机制。

DSH 的测试明确区分了两类失败。普通代码异常可以留下报错前已经发生的内存修改；超时、取消、输出溢出或进程故障则会清掉保留的执行状态。前者意味着用户可以修正代码继续使用已经加载的数据，后者避免把可能仍有异步活动或不完整协议状态的进程继续复用。

这给自研实现提出一个很实际的问题：报错之后，模型下一步能假定什么？如果正常异常保留状态，就要告诉它“变量可能已经变了”；如果中断清空状态，就要明确报告环境失效。只返回一个统一的 ExecutionError，随后让模型自己猜，会把恢复成本转嫁给 Prompt。

我的实现建议是从 per-call 起步，先把后面的取消和权限路径做对，再加 owner-scoped 内存。之后再考虑独立的可序列化 checkpoint。不要把堆内存、Session 事件和磁盘文件叫同一个“记忆”：三者的恢复与丢失条件完全不同。

保存工具引用，不应保存旧一轮的调用资格

持久 REPL 最值得细读的不是能保存 let x = 1，而是下面这种情况：模型先把一个工具函数存进变量，下一轮工具被替换或移除，旧变量还能不能继续调用旧工具？如果能，动态工具配置就成了表面工作。

DSH 的实现将工具调用绑定到当前 evaluation 的宿主 bindings。保存下来的 wrapper 再执行时，重新通过当前调用环境找工具；工具已经移除，就不能靠旧引用继续访问。相关测试既覆盖替换后的新结果，也覆盖移除后的失败。另一个测试让旧 evaluation 的异步回调拖到后续运行，再尝试调用工具，要求以 evaluation has ended 拒绝。

这里应该区分两件事：一个已经定义的函数，可以在新 evaluation 里被主动调用；一段旧 evaluation 遗留下来的异步任务，不能因此获得下一轮的宿主工具调用资格。前者是复用代码，后者是越过调用生命周期。测试帮助说明了这个设计意图，但我们没有运行跨进程攻击或验证所有第三方工具都遵守它。

这不是一个只能调用 tools 的纯隔离解释器。Node 模块仍可导入，直接文件访问遵循执行沙箱策略，初始 process.env 为空；这些条件并不证明网络与全部系统资源都被隔离。上游还明确写了一条限制：原始子进程输出按字节到达时正在运行的 evaluation 归属，空闲时输出会被忽略。因此拒绝旧工具回调，不等于消除了所有跨轮输出污染。应等待子进程结束，或在自研实现中给输出增加独立的 evaluation ID 路由。

一次性的权限扩大还多了一层保护。若本次实际策略与常驻策略不同，桥接层不传入保留状态的 owner，而是使用临时环境。这样，临时提权执行不会直接继承普通 REPL 的变量，也不把自己的堆内存带回下一次普通执行。它隔开的是执行环境状态，不会撤销已经写到磁盘或发往网络的副作用。

迁移到自己的 Harness 时，可以把每次 evaluation 看成一个有寿命的授权上下文：有自己的取消信号、当前工具目录、目录快照和策略。跨轮复用宿主工具时重新检查这一轮的资格，不把已授权函数直接塞进全局空间。Node 原生能力是另一条路径，必须由进程隔离、文件及网络策略独立约束，不能借工具 binding 的检查替它背书。

程序、模型和界面，需要三种不同的结果

一个读文件工具可以返回结构化数据，也可以返回供模型阅读的文字，还可以返回供 UI 展开文件差异的元数据。让这三者共用一段字符串，最初很省事，后来程序就得解析 Markdown，界面就得猜文本格式，模型还会被无用信息填满。

DSH 让内层工具返回其类型化 canonical value；失败变成带工具名的 ToolCallError，由程序决定捕获还是继续抛出。中间 JSON 不会自动进入对话，程序只输出所需部分。图片有一条例外：成功子调用的最终 content 只要含图片，就把整份 content 延后附加到模型上下文，同包文本也会进入；外层代码随后失败，也不必然删除已经安排的附加内容。外层 post-execute 阻断则可以替换掉这些内容，异常与策略阻断不是同一结果。做上下文预算时不能只数 console.log。

这套返回值分层和有界并发调度在 0.2.0 已经存在。此次值得关注的补齐，是嵌套 PTC 调用也能携带 presentationMeta，跟直接调用走一致的展示路径。会话记录能解释程序内部具体做了什么，又不必把每个子工具结果再次塞给模型。对于自研系统，这比单纯追求“少几个 token”更重要：你不能为了简洁，丢掉排障和审计所需的记录。

三条通道分开，也会制造一种很隐蔽的安全误判：把展示 content 脱敏，并不会自动替换代码拿到的 canonical value。如果过滤器只把日志里的密钥变成星号，程序仍可能从原始 JSON 中取出并打印它。要阻止访问，必须拒绝调用，或按返回值约定替换 canonical value；文字脱敏不能充当访问控制。

并发也不是简单的“读并行、写串行”。DSH 要求工具的 isConcurrencySafe(args) 恰好返回 true，才允许调用重叠；未声明、无效返回或分类器抛错，都按 exclusive 处理。工具作者要为这项声明负责。调度器把前置检查、body、后置处理与提交拆开，允许安全的 body 有界重叠，同时保持检查和提交顺序，出队时还会重新分类。这比直接 Promise.all 稳妥，但有序提交也可能产生队头阻塞，不提供数据库式回滚。

取消一个程序，要等它的子调用真正收尾

设想程序已经启动了几个工具调用，用户此时把沙箱从可写改成只读。最危险的实现是立刻把 UI 标成“已取消”，马上接受下一段程序，而旧的写操作仍在后台继续。旧策略和新策略的调用于是重叠，界面显示的权限与现实不再一致。

0.2.1 新增的 PtcCalls 按 Session 记录整次调用，监听沙箱模式变化，取消使用旧模式的调用。下一次调用在进入权限解析与执行之前，先等待已取消的前任完成；工具注册表卸载时，也会取消并等待所跟踪的调用。这里跟踪的是完整调用及其嵌套工具清理，不只是代码执行器的一段 Promise。它接在提供 sandboxMode 的 runtime 与 Agent 路径上，监听的是 Session 沙箱模式，不应泛化成任意权限或工具配置修改都自动拥有这道屏障。

其中 abortNestedCalls → drainNestedCalls 的基础收尾在旧版本就有；新版把它纳入策略变化、保留运行时和 owner 的整体生命周期。程序进程层也要处理策略变化与保留状态的失效，不能只在外面改一个布尔值。

取消不等于撤销。子工具可能已经写了一半文件，也可能远端已经接受请求，只是本地没收到回执。等待 drain 的意义，是知道本地旧调用何时不再占用执行通道；它不能把现实恢复到调用之前。对于有副作用的工具，自研 Harness 仍需要稳定操作 ID、幂等键或执行后的 readback。

也不要从“有 drain”直接推出“永远不会卡住”。如果一个第三方工具忽略取消且不返回，等待本身就可能拖长。应该给宿主进程、远端请求与收尾设计各自的截止条件，明确记录超时后的未知副作用，而不是通过吞掉 Promise 把状态伪装成干净结束。

环境事实不能只在会话开始时告诉模型一次

Code Mode 保存状态之后，工作目录的问题会更明显。用户把 Session 从仓库 A 切到 B，REPL 里还保存着 A 的数据，系统 Prompt 又写着最初的 cwd。哪一个才是真的？DSH 把当前目录变成带事件的 Session 状态，并统一文件工具、Shell、子 Agent 和程序执行的目录来源。每次程序启动时捕获当前目录；已经运行的程序仍使用自己的起始目录。当前 cwd、最初的 session.header.cwd 和沙箱允许访问的根目录是三件事，切换目录不等于扩大文件权限。

模型请求的构造也需要防止时间差。pre-step 插件可能改变状态，压缩或 provider preparation 也可能发生在请求真正发出之前。新版在准备请求的路径上再次刷新 runtime context，让当前 cwd 等动态 sections 跟上这些变化。这里刷新的是动态上下文，不是每次重建全部 System Prompt 和工具 schema。

值得借鉴的是稳定指令与动态事实分开维护。Agent 的角色、工具规则可以保持稳定；cwd、当前策略、委派深度属于会改变的环境事实。开发环境上下文里还有一个具体兼容处理：对于包含旧格式 Harness checkout 与 Web GUI URL 段落的 Session，保留这两段原文，当前值另走动态上下文。保护范围只限这两段，其他 Prompt 变化仍可能重写头部，不是所有历史指令都永久不变。这个做法为稳定前缀创造条件，但没有实际请求和缓存计量，不能声称提高了多少命中率。

自己的实现不一定需要复制 DSH 的整套事件系统，但至少要确定一个事实源，以及各自取快照的时刻。请求准入时的 cwd，不保证与稍后工具启动时的 cwd 永远相同，用户可能在两者之间再次切目录。应记录变更事件，让模型请求和工具执行分别能追到自己的快照，而不是宣称整个回合具有原子一致性。测试时故意在 pre-step、压缩完成和重试之间切目录，比只测“第一次打开仓库能读文件”更容易暴露错误。

子 Agent 没在生成文字，不代表它已经完成

一个子 Agent 进入 idle，收件箱里可能还有新消息；一个子 Agent 正在结束，又可能仍有后代任务在创建或 flush。父 Agent 如果只检查 isRunning === false，就会过早汇报完成。0.2.1 的重要整理，是把原来的 one-shot 与 continuable 等分叉收敛到统一的 activation 管理，让本地与外部执行共享更一致的启动、等待和结果交付方式。

这里也不能把旧约束全部写成新发明。资源池、释放顺序和 flush 后检查等做法，旧 continuable 分支已经有了。新版的价值在于减少另一套返回路径绕过这些约束的机会，并把 host wait 与 Goal 自动续轮接到同一套等待语义上。

waitForChildren 要区分“还在推进的子树”和“只是停在 inbox 等外部输入的子树”。前者应该等，后者不能让父任务永久挂起。Goal 在准备自动开启新轮次前，先等正在推进的子任务，再复查人类输入、暂停和轮次上限；纯等待不应占掉新的目标执行轮次。

要区分两个“结束”。单次 activation 交付结果之前，会等待资源清理尝试结束、归还容量并发出通知；但清理失败有独立通道，拿到成功结果不证明每项 teardown 都成功。host wait 返回更只表示此刻没有需要继续等待的推进中工作。停在 inbox 的子 Agent 仍可能驻留，不能把父任务能返回说成“所有子任务都完成且释放”。另外，子任务最后的 flush 失败会告警后继续收尾，是 best effort，不是强持久化提交保证。

为什么等完还要看事件序号？因为等待子任务期间，它的完成消息可能又唤醒了父 Agent。Headless 路径把父级 idle、子树等待和 Session 是否变化结合起来，避免检查完一个标志就提前退出。自研时不要把 idle、waiting、settling 和 completed 压成一个 finished 布尔值；也不必通过不断调用模型，轮询宿主已经掌握的任务状态。

热更新和卸载，也会改变任务是否真的结束

插件下载成功，不表示运行中的 Agent 已经用上新版本。DSH 在此前已有开发态 HMR 的基础上，于 alpha.3 扩展了已安装包替换后的重新组合：重新解析入口和依赖映射，计算静态导入的反向依赖范围，再处理受影响的插件。host module 或不受管理的插件不能直接热替换，会保留旧实现并标记待重启；真正进入替换路径后，如果重新加载失败，旧插件也已停止，不能一概宣称自动回滚。已安装包替换与开发源码 HMR 的回滚不是同一条路径。

对自研插件系统，最有参考价值的是状态划分：磁盘上装了哪个版本、运行中激活了哪个实现、哪些变更失败、哪些仍待重启，应该分别记录。否则用户看见“更新成功”，模型却仍在用旧工具。失败之后修复依赖或文件，再重新组合，与原子更新、零停机是不同的保证。

卸载的顺序同样影响正确性。以 JSONL 会话存储为例，如果先关日志监听器，再让使用它的 Agent 结束，最后的 turn/end 就可能来不及落盘。新版将相关跟踪与监听的寿命延长到消费者 teardown 之后；测试特意阻塞消费者清理，确认存储卸载也在等待，末尾事件仍可写入。

这是明确的卸载路径约束，不是断电恢复证明；上游还注明并发 root disposal 不提供同样的顺序。可以迁移的原则是：先停止新工作，再取消或完成旧工作，最后关闭它们依赖的记录与资源。只把所有对象一起 Promise.all(dispose)，可能很快，也可能丢掉最需要保留的最后一条状态。

还有一个值得借鉴、但不宜直接依赖的设计：插件自己的会话记录，与给模型看的历史分开。alpha.2 出现的 appendPluginRecord 使用可忽略记录承载插件数据，随 fork/resume 保留，不自动进入模型输入；读取时仍须校验数据，迁移保留也只是 best effort。文档明确把它限定给仓库内 experimental 包，外部插件不应调用。我们可以借鉴这种分层，不能把内部实验接口写成稳定 SDK 教程。

模型接入层的收益，常常来自不再无故失败

还有几项没有 Code Mode 显眼，却很影响长期任务。一个例子是流式请求超时：外层已经 abort，finally 却还在 await 一个永远不返回的 iterator.return()。结果“超时保护”自己卡住，后续重试永远进不来。新版不再让这段清理阻塞已经确定的超时结果，而是异步调用 return 并用 .catch(() => {}) 消费其拒绝，传输取消交给 abort 路径。这里没有额外记录清理异常，不能把吞掉拒绝说成已经具备完整观测。

另一个例子是旁路元数据。插件清单读取失败，或者某个扩展准备附加字段失败，不应该自动等同于“模型不能回答”。相关路径按贡献项省略失败的可选字段；HTTP 2xx 之后，accept 回调的异常由 adapter 包装层捕获并转入未接受通知，不直接打断后续流处理。此时 SSE 还没读完，流本身当然仍可能失败。这个取舍只适用于可选扩展，不能照搬到权限检查、必需参数验证或核心消息转换。

历史序列化也遵循类似分层：发往 Messages 接口时过滤空文本和转换后没有内容的 assistant 消息，避免因协议不接受空消息而失败；这不要求重写持久化的 Session 记录。原始事件负责保留事实，provider adapter 负责生成当前协议能接受的投影。支持多个模型供应商时，这条边界比到处修改聊天历史更容易维护。

账号模型目录则把模型输入能力、上下文限制和最低客户端版本从服务端读回来，再判断当前客户端是否支持。模型名称不是完整的能力描述；把它写死成一个字符串，会让后来的能力升级或版本限制难以表达。但这里存在门禁机制，不等于已经证明 1017 实际把最低版本设置成 rc.1，更不能泛化到 API Key 路由。

把这些放在一起，所谓 Harness “更能发挥模型能力”，有时不是模型多想了几步，而是相同的推理终于能穿过有效历史、正确参数和可收尾的传输，完成一次任务。这是合理的工程解释；量化收益仍需要真实对照。

自研时，先写下失败后的约定

如果从零实现，我不会先复制 DSH 的插件目录，也不会第一天就加入持久 REPL。比较稳妥的顺序是：先实现单次执行的工具桥接与明确输出；把取消、嵌套调用和副作用记录补齐；再引入 live-Agent 状态所有者；最后加入工具热替换、临时权限与多 Agent 等待。每扩展一种寿命，就补一组跨边界测试。

下面是从本文机制推导的自研验收用例，不是本站已经运行的 DSH 测试。即使暂时不做持久 REPL，也可以先把失败后的约定写进自己的测试计划。

验收时应同时保存模型实际收到的 Prompt/schema、evaluation 与子调用 ID、权限和 cwd 快照、终止原因，以及文件或远端服务的最终状态。只保存聊天文本，会漏掉本文最关心的一半问题。

DSH 这轮最值得借鉴的，是把“谁拥有状态、谁授予能力、什么时候算结束”分别落实到了代码。一个 Code Mode 做得好不好，不只看它能否执行漂亮的一段程序，还看失败、换环境和继续运行之后，这三个答案是否仍然一致。
