MiMo Agent

黑盒究竟怎么“模拟”？

把原版 Agent 放进容器，与自己写一个长得像它的 Agent，是两件事。小米两条路都做了：前者接真实 CLI，后者把 prompt、工具和上下文管理拆开，用于可控的训练。最值得研究的，恰恰是它没有照搬的部分。

假设要让一个 MiMo checkpoint 修复同一份仓库：一次用 Claude Code，一次用 Codex，再用小米自己的最小 Agent 跑一遍。真正需要固定的不只是模型。模型看见什么工具、什么时候被要求压缩、格式错了会收到什么反馈，都会改变它接下来能走的路。

这篇沿着这条任务链读源码。依据是小米 mimoagent 的固定公开提交和 MiMo-V2.6 技术报告；另外运行了离线测试与合成事件探针。没有运行真实模型或 RL 训练，文中的成绩仍是作者报告。

“黑盒”说的是怎么接入，不是代码一定闭源

最容易读错的是名字。cc-agent 和 claude-code 不是别名；codex-agent 和 codex 也不是。前两组中的第一种由 mimoagent 自己掌握消息、模型调用和工具执行；第二种则在任务环境里启动上游 scaffold。注册类型决定路径，不能看模型名猜。

配置真正运行谁的循环适合回答什么
cc-agent小米 Python 循环，Claude 风格工具工具与上下文机制怎样影响学习
codex-agent小米循环，可复用 code-mode host直接工具调用和代码调用工具如何训练
claude-codeClaude Agent SDK 驱动真实 Claude Code模型放进这套生产 scaffold 后怎么表现
codex真实 Codex CLI 子进程同一模型在 Codex 执行环境里的表现

这里的黑盒是把 Agent 当作外部进程使用。Codex、OpenCode 等即使有公开源码，也可以采用这种接法。对于 Claude Code，不需要先知道闭源内部每一个分支，就能运行它、指定模型服务、收集它公开输出的事件，再检查它改完的仓库。这是集成，不是反向训练一个“Claude Code 替身”。

训练时，他们反而不想照搬生产 Agent

MiMo-V2.6 报告 §4.2.5 给了一个很具体的理由：生产 harness 里有许多安全约束、交互流程和产品指令，任务通过率却未必衡量这些要求。RL 只奖励修复成功，模型可能学会忽略那些没有被奖励覆盖的约束。另一个麻烦是组件耦合，换一种压缩策略，可能同时改变很多别的行为。

小米选择从最小循环出发，保留完成任务需要的 system prompt、工具和上下文管理，再组合成不同 mini-harness。目的不是尽可能像某一个产品，而是让模型接触多种可控制的交互条件，别把解题能力绑在一种工具包装上。

所以，研究问题应从“它怎样复刻黑盒”改成两问：白盒删掉和保留了哪些交互机制？这些机制学到的能力，换成真实 harness 以后还剩多少？报告中的保留 harness 实验正是在检查后一个问题。

白盒保留会影响训练的交互，不复制整套产品

同样一次修复，工具名称和参数只是开头。格式写错以后，模型有没有机会改正，也会改变训练结果：Claude 风格白盒遇到普通文本里的 <tool_call>，会返回错误反馈，让模型再试；Codex 白盒没有相同的补救，没有结构化工具调用就可能结束 rollout。一个任务最终能否得到奖励，已经受到这个区别影响。

上下文压缩也是一种不同的交互。Claude 风格路径会提示上下文压力，由模型自己调用 Compact；摘要等到下一次查询才生成，失败则保留旧历史。Codex 白盒的自动压缩默认关闭，开启后采用本地摘要。这些可调的条件适合做机制实验，却不能说明白盒已经和原版 Agent 等价。

查看 Claude / Codex 风格的工具、Prompt、压缩和对齐来源

Claude 风格：连错误反馈也参与训练

CCAgent 使用大写的 Bash / Read / Write / Edit 等工具名，对齐参数形状，例如 Bash 的毫秒超时、Read 的 file_path / offset / limit。但示例 system prompt 只是几句通用任务说明，没有复制整套 Claude Code 指令。示例再显式加入 Grep、Glob、Agent、Compact，总共八种工具。工具目录里有，不代表默认配置都会启用。

压缩也被设计成可训练的动作：模型看到上下文压力提示，自己调用 Compact。当前工具调用先正常配对返回，到下一次 query() 才请求摘要，随后把历史改成 system、压缩边界、原始任务锚点和摘要。摘要失败或为空，保留旧历史。这里没有“token 到阈值便自动压缩”的规则。

还有一个不显眼的差异：如果工具调用落成了普通文本里的 <tool_call>，CC 路径会报格式错误，让模型得到一次修正反馈；Codex 白盒路径没有同样的补救，没有结构化工具调用就可以结束 rollout。对训练来说，这不是显示细节。一次错误后还能不能继续，决定哪些轨迹能最终拿到奖励。

Codex 风格：复用宿主，不复用完整决策循环

codex-agent 只接受 Responses 协议。ptc: true 时，模型面对的是 exec 与 wait，用 JavaScript 调用嵌套的工具；ptc: false 则直接暴露配置里的工具。JavaScript 由独立的 Codex code-mode host 运行，但消息维护、工具派发和终止判断仍在小米这边。

它的 core prompt 明确是经过删减的版本：保留查找文件、编辑范围、交付等工程习惯，删除部分人格、用户交互、可视化与 skills 指令。自动压缩默认关闭；开启后也用普通模型请求做本地摘要，而不是专用远程 compact 端点。这些选择适合做机制实验，却让“完整模拟原版 Codex”的说法站不住。

官方 NOTICE 也直接写明：Codex 部分重实现工具语义与 prompt，Claude 部分跟随工具 schema 和描述。这些材料展示了对齐后的实现，却没有交代一套自动探测黑盒、推断隐藏状态机的流程，也不足以重建所有工具合同最初如何采集、逐项怎样校准。这里能研究的是可观察交互的重实现，不能补写成一次已经完成的黑盒逆向工程。

最值得借鉴的地方

不是复制一份长 prompt，而是把会改变训练分布的东西变成明确配置：工具参数、输出截断、格式纠错、压缩时机和退出条件。这样才能知道一次收益究竟来自模型，还是来自 harness 替模型处理了错误。最后这句是本研究的工程判断。

到了黑盒路径，真的把 CLI 装进任务现场

回到那条代码修复任务。batch runner 先准备数据集对应的环境，按 agent.type 创建适配器。黑盒适配器不调用小米的原生 step()，而是接管 run(task)：安装 scaffold，写配置，启动进程，取回结果。CLI 就在任务仓库所在环境里读文件、改文件和运行命令，不是在一个假文件系统里表演。

例如 Codex 安装脚本默认选择 0.154.0，下载的不只是一个命令，还包括 code-mode host 等组件，并检查版本与 bundle 是否完整。Claude 适配器默认固定 2.1.269 的 CLI，由 SDK runner 驱动。SDK 是控制通道，CLI 才是实际 scaffold。固定版本很重要，但脚本允许 latest，因此重现实验时仍须保存最终解析出的版本，不能只留 YAML。

仓库还支持 OpenCode、Pi、Kimi、Grok、Hermes、DeepSeek Harness 等接入。可共用的是任务和环境合同；每家的启动参数、provider 配置、事件解析和续接方式仍要分别维护。“支持十四种”不是一次抽象就解决了十四种运行差异。

换掉模型端点，让原来的循环继续工作

为什么闭源 scaffold 也能用于测试其他模型？因为要替换的不是它的内部控制流，而是它向外请求推理的端点。Claude 适配器从共享模型配置派生 Anthropic 协议的地址、凭据和模型名，并把不同模型档位及子 Agent 路由钉到同一个模型，避免辅助调用悄悄跑到另一个默认模型上。

Codex 路径则写入独立 CODEX_HOME 下的 provider 配置，再启动 codex exec。原生 Python model 对象在这条路上主要充当配置和统计容器，不负责每一步推理。模型请求由外部 CLI 自己发起。

因此，不必先重建隐藏的 system prompt，真实 scaffold 会按自己的流程组装请求；但目标端点必须接受它实际使用的协议、工具调用、流式事件和历史格式。填了一个 base_url 并不等于兼容性已经验证，更不代表仓库提供了全部模型服务或训练端的实现。

这套设计的研究价值在于把变量分开：可以固定模型比较不同 scaffold，也可以固定 scaffold 比较 checkpoint。前提是把工具裁剪、思考预算、压缩和权限设置一起记下来。否则，名义上只换了模型，实际上实验条件也变了。

“运行原版”也不等于“原样运行”

为了无人值守和批量 rollout，适配器会改掉日常交互的若干条件。最直观的是 Claude 的提问工具：遇到 AskUserQuestion，回调按每题选项顺序选第一个；没有选项则填空。退出计划和其他权限询问也不等真人确认。这解决了卡住的问题，却给任务加上了一种特定的“用户”。

路径此快照的改动研究时要防止的误读

Codex默认关网页搜索；绕过 CLI 审批与沙箱；可替换内置指令执行隔离要靠外层容器，不能把 CLI 当最后防线

上表是固定实现的差异记录，不是建议关闭安全控制。部分工具调整来自作者记录的端点兼容性问题；本研究没有重现这些上游服务的拒绝行为，也不把兼容补丁当成绕过服务限制的使用指南。

比较成绩时，实验对象最好写成“某版本 scaffold + 适配配置 + 目标模型”，而不是只写 Claude Code 或 Codex。黑盒接入省掉了重写循环的工作，没有省掉实验条件的说明。

日志能解释一次运行，却未必能训练它

这是这份开源最需要仔细读的地方。Claude Code 与 Codex 适配器都会把自身的 messages 保持得很短：本轮任务，加最终回复。save_traj() 直接序列化这些消息和查询参数；查询参数又是空的，所以统一 traj.json 不会自动出现原版 scaffold 的完整工具合同和所有中间轮次。完整程度必须去各自的原始日志里另查。

Codex 原始事件流会保存到 codex.txt。复制失败时还会退回到读取最后 2,000,000 字节，这显然不能保证长轨迹完整。统计也有近似：api_calls 按 assistant 消息计数估计，而非一个覆盖全部内部请求的计数器。Claude SDK 日志使用对象序列化，某些嵌套值可以退为字符串，也不能直接当成完整的线上 API 请求。

拿到了什么足够做什么还不能据此认定什么
退出状态与最终仓库运行 verifier，衡量任务结果过程可靠或所有工具都正确
事件流与工具记录排错、回看可见操作每轮模型实际输入完整无损
usage、最终答复用量汇总与结果展示逐 token 的训练概率已保存
实际模型请求和训练元数据核对可训练样本、策略版本与掩码仅凭这个仓库就拥有完整 RL 闭环

技术报告 §6.2 另外描述了真正的大规模训练数据通路：轨迹载荷包括 token IDs、log-probabilities、MoE 路由与采样信息，Payload Porter 把它们放在分布式存储里，调度层只拿轻量元数据。这是训练系统的描述，不能倒过来算成每个黑盒 adapter 已经导出了这些字段。

本研究的判断：若要把这套接入拿去做自己的黑盒 harness RL，关键补课在模型服务端，而不只是日志解析器。要能对齐最终 prompt、工具 schema、输出 token、策略版本以及哪些 token 参与学习。客户端留下一个“完成了”，离这些要求还很远。

CLI 说完成了，任务还没算通过

黑盒进程正常退出，适配器返回的 Completed 只是执行状态。batch runner 还要把任务、Agent 与最终答复交给数据集环境，再计算 reward。任务是否通过，依赖仓库状态与 verifier，不依赖模型最后写了多有把握的总结。

评分次序也值得保留：先捕获修改，如果配置了 rubric judge，先让它看交付现场，然后才运行可能恢复测试文件、应用标准测试补丁或清理工作区的 verifier。否则 judge 看到的就可能是评测器处理过的仓库，而不是 Agent 真正交付的版本。

但同容器运行 judge 不等于对恶意修改有硬隔离。白盒的 AntiHackGuard 也是默认关闭的可选拦截器，并不是所有黑盒工具都会经过它。评测环境坏了、网络断了、代码没修对，要分别看错误元数据；只留下一个零分，就会把基础设施失败变成模型的负样本。

本地确认了哪些部分？

本次执行了两组固定版本的上游测试：黑盒适配与 detached 生命周期组 358 通过、7 跳过；压缩、动作拦截、模拟用户、测试文件恢复与 rubric judge 组 73 通过。合计 431 通过。测试主要使用伪环境和固定事件；7 项真实 Linux shell / 进程组测试因当前 macOS 环境跳过。它们验证的是代码合同，不是生产 CLI 端到端可运行性。

另写了一个小探针，直接调用固定源码的 Codex adapter：给它两轮合成日志，其中包含 command_execution 事件，把原生 model.query() 设成一旦调用就报错。结果两轮都完成，原生模型调用为零，第二轮生成了续接命令；保存出的统一轨迹仍只有 user、assistant、user、assistant，没有工具 schema 或中间调用。Claude 的问答回调也确实选了第一项。探针结果

没有做过的事

没有安装并启动这些生产 CLI，没有连接真实模型 API，没有跑容器基准、GPU 训练或黑盒对照实验。探针替换了环境执行与 SDK 返回类型，不能拿它宣称 Claude Code 或 Codex 已在此机器上成功完成代码任务。

继续研究时，我会优先做三个实验，而不是先跑一张更大的成绩表：

  1. 同模型、同任务的白盒与原版配对。比较实际工具参数、错误反馈、截断和压缩后的输入；记录最终 patch、任务成绩与 token 成本。
  2. 把“日志完整”变成可检查的条件。在授权自建端点记录每次最终请求与响应，对照 CLI 事件、统一轨迹和训练字段，查缺失轮次与辅助调用。
  3. 一次只变一个机制。固定模型与任务，分别改变 Compact、PTC、格式纠错、提问替代策略，再观察失败类型，避免把适配层收益错算成模型收益。

到这里，我更愿意把 mimoagent 看成一套连接研究实验与真实 Agent 的 rollout 基础设施。它有价值的不是声称打开了所有黑盒，而是同时留下两种能力：在白盒里控制变量，在真实 scaffold 上检查迁移。两边的差异必须被记录下来，而不是被“模拟”这个词抹平。

长任务怎样续接，还怎样模拟后续用户？

一个 rollout 跑几个小时，不能依赖一条永不掉线的 exec 连接。Kubernetes 和 Modal 使用的 detached 实现把命令放进独立会话，标准输出落到远端文件，控制端通过短请求轮询退出标记。可选 watchdog 按日志修改时间判断是否停滞；阈值太小会误杀慢模型，设为零则关闭。

多轮输入也不是把第二条消息塞给一个全新的 CLI。Codex 的后续调用使用 resume --last；Claude runner 使用继续会话选项，并继续写入 session 日志。工作目录保留与模型会话保留分别实现，不能以“文件还在”推断“上一轮上下文也在”。

仓库里确实还有一种“模拟”：可选的 UserAgentDriver。它让独立模型检查主 Agent 的结果、轨迹和任务现场，生成后续用户消息，通过 query_N.md 交回主 Agent，再继续下一轮。轮数耗尽、交付缺失或主 Agent 状态不可续接时停止。这里模拟的是用户，不是那个被接入的黑盒 Agent。
