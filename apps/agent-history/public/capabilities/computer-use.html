01 / 整体架构

整体架构：从模型调用到 macOS 原生能力

只看界面，“模型在控制 Mac”这句话很顺口，却把中间最重要的几层全抹掉了。实际更像一场接力：模型说出意图，封装层（wrapper）找到目标 App，客户端（client）检查参数，传输层（transport）把请求塞进本地协议，最后才轮到 CUAService 和 macOS 处理屏幕、辅助功能与输入权限。原生二进制链接的框架和静态符号，确实都指向 macOS 辅助功能（Accessibility，简称 AX）、屏幕捕获和合成输入。不过要说清楚：这是静态证据支持的推断，不是已经还原出来的 Swift 控制流。

这条路看着绕，恰恰因为绕，出了问题才有地方查。App 没找到、策略拒绝、socket 超时、屏幕锁住、系统权限没开、AX 读不到，这些情况没必要都挤进一句“点击没反应”。这个固定构建列出了 21 类原生错误，wrapper 和 transport 也各自保留失败信号。先认出坏在哪一层，再谈重试。顺序不能反。

靠近用户意图的那一层，不该顺手攥住系统权限；真正碰系统输入的那一层，也不该替模型猜用户到底想要什么。我更愿意这样理解这套分工
02 / 调用入口

调用入口：stdio MCP 与 node_repl

包里能找到两种入口。一种是走标准输入输出（stdio）的 MCP 客户端，由 .mcp.json 拉起安装后的 SkyComputerUseClient；另一种是 node_repl，也就是一个会保持状态的 Node JavaScript 控制台。模型只需导入一次 @oai/sky，后面可以继续复用同一份绑定。两边都认识 IPC-2 这套进程间通信 schema，但请求从哪儿来、会话能活多久，完全不是一回事。

从哪儿进上层怎么调用能保持多久在实现链中的位置
node_repl + @oai/sky模型生成 JavaScript，再调用 window 门面内核会保持；客户端用到时才创建主分析路径
stdio MCP 客户端独立进程接收 MCP 请求跟随 sidecar 辅助进程并列入口

安装包能证明两扇门都在，也足够让我们看清 node_repl 这一路怎么调用。它证明不了的，是某次真实会话里的功能开关（feature gate）最后选了哪一扇。所以看到“这个能力在包里”，先停一下，别顺手写成“这次调用肯定走过它”。

03 / 信任边界

信任边界：@oai/sky 如何取得宿主特权

cua_node 把平台固定在 darwin-arm64，用的是 Node 24.14.0，还有自己那套 node_repl。模型写出的根单元（root cell）先待在不可信域里。只有包依赖图（package graph）通过路径或内容的信任规则，代码才会跨进可信上下文，拿到被冻结的特权桥（privileged bridge）。像 nativePipe、LaunchServices、createElicitation，甚至暂停外层超时计时器的能力，都藏在这条边界后面。会写代码，不等于能越过它。

这里还有一个容易想多的地方：@oai/sky 并不是一只装着完整智能体的黑盒。第一次访问它的属性时，它才读取可信平台配置、创建 Mac 目标，随后把客户端缓存起来。那十个 window 原语做的事相当具体：把 snake_case 参数翻成 typed client 能吃的输入。它们不替模型规划任务，也不会直接去碰 AX 或 CGEvent。

04 / 权限模型

权限模型：动作确认、App Policy 与 macOS TCC

把它想成三道各管各的门，会比较好懂。App policy 问的是：“这个会话能不能接触目标 App？”动作时确认问的是：“用户同意这次有风险的副作用了吗？”最后，macOS 的隐私权限系统 TCC 才决定服务能不能读屏幕、访问 Accessibility，或者发送输入。第一道门开了，另外两道不会跟着自动弹开。

哪道门它在管什么谁来做决定拒绝时会看到什么
动作确认眼前这个有风险的动作模型与用户的对话动作发生前没有拿到确认
App policy目标 bundle / App 路径CUAService + 可信询问流程denied / forbidden
macOS 系统权限屏幕、AX 与输入TCC + 原生服务permissionsPending / notGranted

遥测不是偷偷藏着的第四张通行证。适配器会尽力记下 client 启动、批准请求及结果、工具耗时和最终状态（terminal status）；就算记录失败，主调用也会继续。反过来，只看见这些事件，仍然推不出服务端会留存多久、怎样采样、何时删除。证据到哪，就说到哪。

05 / App Policy

App Policy：权限查询为什么也要经过 socket

假设只是读取某个 App 当前的画面，JavaScript 也没资格在本地自说自话地判一句“允许”。wrapper 会调用 MacComputerUseClient.getAppPolicy()；typed client 再把 ComputerUseIPCAppPolicyRequest 交给 MacNativePipeTransport，经 socket 送进 CUAService。等服务回了 allowed、denied 或 forbidden，后面的路才知道能不能走。说白了，应用访问策略（App policy）不是 socket 前面那个轻飘飘的 if。光是问“能不能访问”，就已经跨过 socket 了。

服务只有在允许“去问用户”时，wrapper 才会打开可信批准流程，并把规范化的 App 路径（canonical appPath）写进一份新的冻结参数。组织规则拒绝了，或安全策略给出 forbidden，多点几次也不会翻篇。更重要的是，App 获准访问以后，高风险动作照样要单独确认。“可以看这个 App”和“可以替我发送、删除、付款”，根本就是两道题。

06 / 状态观察

状态观察：截图与 AX 树如何组合成 AppState

get_app_state 一次会带回两份视角。skyshot 是窗口截图，保住按钮在哪、面板怎么排这些视觉关系；辅助功能文本（accessibility text）则给出控件角色、名称和临时索引。适配器把两份材料拼成 AppState。第一次碰某个 App 时，它还可能顺带附上这个 App 的操作提示；以后再读，则可以只回传 AX 的变化，少重复一大段没变的内容。

两份材料，缺哪份都别扭。比如找一个有明确标签的按钮，优先看 AX，角色（role）、标签（label）和元素索引（element index）通常比一组坐标稳。可碰上画布或自定义控件，AX 也可能一片空白，这时就得回到同一轮截图。要是差量（diff）已经零碎到看不懂上下文，disableDiff 可以重新要一棵完整树。还有个细节很容易踩坑：窗口视口（viewport）里的坐标，不能和窗口外的桌面坐标混着算。

元素索引会过期，别把它当门牌号

它只指向最近一次 get_app_state 返回的那个元素。点过按钮、切过页面，甚至界面自己刷新以后，都该重新观察。至于服务会不会把每一种过期索引都强制拒掉，目前没有直接证据。别替它补上这层保证。

07 / 动作接口

动作接口：十个 Window 原语如何进入 IPC

Mac 侧的对外门面（facade）总共露出十个原语：list_apps 和 get_app_state 负责观察，另外八类负责动作。client 会分别检查 App、坐标、元素、滚动页数、按键和枚举值，再把它们翻成不同的 IPC 请求。底下虽然都挤进同一条 transport，上面却不能偷懒。一次滚动和一次文本输入，不该套同一份风险判断；出错以后，也不能不分青红皂白地自动重试。

读界面

list_apps / get_app_state

先找出正在运行的 App，再拿窗口截图和 AX 文本。注意，“只是看看”也要经过 App policy；只读，不代表可以绕开目标 App 的授权。

找谁显示名称 / bundle id
拿回什么截图 + AX 文本
要留心画面里可能有敏感内容
动指针

click / drag / secondary action

可以拿最新的元素索引，也可以拿窗口坐标来定位。secondary action 还要看服务和 AX 控件公开了什么动作名，不能因为“右键大概有这个选项”就凭空猜一个。

点哪里elementIndex / 坐标
拿回什么动作响应
要留心位置过期 / 动作有副作用
走键盘

press_key / scroll

组合键会查枚举，滚动页数会查范围。参数过关还不算完，因为焦点可能已经跑了，滚动容器也可能不是刚才那个，当前窗口更会随时变化。

作用在哪当前焦点 / 滚动区域
拿回什么原生输入响应
要留心焦点漂移 / 快捷键副作用
改内容

set_value / select_text / type_text

直接设值、选择文字、模拟键入，对控件的要求各不相同。尤其别小看一个换行：它可能直接把表单交出去，所以给模型的动作约定（contract）会在动作发生时把这类输入纳入风险判断。

改哪里可编辑的 AX 元素
拿回什么设值 / 输入响应
要留心敏感数据外传 / 意外提交
08 / 执行闭环

执行闭环：观察、动作与结果验证

靠谱的做法其实很朴素。先拿 AppState，用最新的 element index 找目标；实在没有 AX 节点，再退回同一轮截图的坐标。做完一步，或一小组紧挨着的动作，马上再读一次状态。为什么这么谨慎？因为窗口会换，焦点会跑，AX 树也会更新。几秒前的界面，不是永久有效的地图。

沿链路做判断

没反应。现在能直接重试吗？

先别猜。同样是“没反应”，卡在不同层，处理办法可能正好相反。这里会拿固定构建的证据一步步推演；它不是，也不会假装成一台真实服务模拟器。

正在把固定构建里的故障路径摊开…

到这里，Computer Use 和 Record & Replay 的区别也清楚了。前者跟着状态走：做一步，看结果，再决定。后者可以把一次演示变成工作流（workflow），但真想让它经得起界面变化，保存的就该是稳定目标和验证条件，而不是一长串迟早会过期的坐标。

09 / 故障恢复

故障恢复：按失败层判断能否重试

原生错误枚举分得很细：appNotAllowed、runningApplicationNotFound、permissionsPending、screenLocked、blockedURL、accessibilityError，各有各的名字。可 policy wrapper 返回的 denied / forbidden 只是普通 Error，不能硬给它套上 -10006 appNotAllowed。transport 还有自己那组问题：连不上、超时、管道关闭、数据帧过大、JSON-RPC 格式坏了，或版本对不上。表面都像“没反应”，根因差得很远。

坏在哪一层常见信号接下来怎么查这时最忌讳什么
找目标ambiguous / not found从 list_apps 拿规范 ID，再试一次盲猜另一个相似 App 名
应用策略denied / forbidden把边界说清楚，或者就此停下改坐标、换别名，绕去更低层硬做
系统权限pending / not granted等用户把系统设置处理完什么都看不见时继续盲操作
传输通道timeout / closed / malformed重新拿状态，先查副作用有没有发生认定请求没执行，然后自动重放
观察现场AX failure / stale index重读完整 AX 树，或退回截图抓着旧索引一直用

socket 第一次没连上时，client 会先尝试确保宿主已经启动（ensure/start host），再给自己 5 秒重连。每个数据帧前面都有 4-byte 小端序长度，整帧上限是 8 MiB。这些设计让连接更耐用，但有件关键的事仍然看不到：它没有露出“副作用只执行一次”（exactly-once）的回执。于是 timeout 最麻烦。动作可能根本没发生，也可能已经发生，只是回执堵在路上。恢复时先重新观察。不要直接重放 click 或 type。

10 / 相邻组件

相邻组件：History、Skysight、PIP 与主动控制的边界

CUAService bundle 里面还能翻到 Computer History / Skysight 事件流、记忆管线（memory pipeline）和历史控制项；native/sky.node 与 Codex shell 里，也露出了 remote-hosted PIP 的显示和设置字符串。它们确实和 Computer Use 挨得很近。但“挨得近”只能证明组件存在，不能证明每一次主动 click 都要经过历史捕获或 PIP。眼下没有这份证据。

这条界线一定要守住。不然看见一个 event stream 字符串，很容易脑补成“每次动作都会长期记录”；看见一个 PIP 组件，又顺手把它当成动作传输通道。现有证据只能确认这些组件存在，并给出部分职责线索。采集是否开启、数据留多久、会不会上传、怎样和会话关联，安装包没有回答。

11 / 证据范围

证据范围：固定构建、文件摘要与推断强度

这份档案把证据根目录锁在 Codex.app/Contents/Resources。插件清单（manifest）和 skill 文件、cua_node 清单、@oai/sky 编译后的 JavaScript、Codex Computer Use.app、签名 Mach-O 元数据、app.asar，还有旁边的原生扩展（native addon），全部回到同一份安装包。每条证据都留着完整 SHA-256、文件位置和能外推到哪一步的边界。这样换个版本，才知道到底是哪一块变了。

有两组看起来很像的东西，尤其不能混。app.asar 整个文件的摘要，不是 Info.plist 里的 ElectronAsarIntegrity 元数据；眼前能直接读的编译后 JavaScript，也不是上游 TypeScript 源码。深挖不是把编译产物叫得更响亮。先把别人能复核的对象钉牢，才算真的往下走了一层。

哪部分证据最硬？

JavaScript 这一层可以直接读到 policy wrapper、typed client、transport、AppState 的组合方式和遥测适配器。到了原生层，就只能把 bundle 身份、链接库、符号、静态字符串和错误枚举拼在一起推断。两边的确定程度不一样，所以结论也不会故意写成一样硬。

12 / 结论与边界

结论与边界：这套实现能确认到哪一步

把整条链收回来，Codex Computer Use 并不是模型直接接管 Mac。沿 node_repl 这条主路，模型生成调用，可信的 @oai/sky 负责绑定目标和检查参数，App Policy 与系统权限逐层放行，本地 transport 再把请求交给 CUAService。截图和 AX 树提供观察，动作执行完还要重新读取界面，才能知道用户要的结果是否真的出现。

这套分层会直接改变排错方式。看得到 App，不代表有权操作；调用超时，不代表动作没有发生；安装包里出现 History、PIP 或 telemetry，也不代表一次主动控制必然经过它们。权限问题、重试策略和隐私判断，都得沿各自的链路找证据，不能混成一句“Computer Use 做的”。

仍然不能确认的部分

现有安装包还回答不了几件事：CUAService 怎样保存和合并 App Policy；AX 树、截图裁剪与输入合成在原生层怎样衔接；过期的 element id 是否一定会被拒绝；timeout 或断线发生时，动作究竟执行到了哪一步；历史捕获、PIP 与主动会话之间是否存在运行时关联。没有动态 trace 或完整的原生实现，这些都只能留在未知项里。

主线就这一条node_repl → @oai/sky → socket 策略查询 → 状态/动作 → CUAService → macOS别忘了，光查询策略就已经跨过 transport。
最容易混淆的地方App 获准访问，不等于动作获准，也不等于 macOS TCC 放行。三个“允许”，回答的是三个问题。
