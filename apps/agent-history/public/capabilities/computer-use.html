01 / 核心判断

核心判断：Computer Use 是状态机，不是遥控器

四套实现都能列窗口、读 Accessibility（AX）树、截屏、点击和输入。这只能说明它们有相似的“手脚”。真正决定可靠性的，是模型拿什么证明这只手正在操作刚才看见的那个界面。Codex 与 Kimi 的公开合同都反复要求动作后重新观察；DSH 也会保存最近一棵 AX 树；Pi 则更进一步，把根、元素、资源版本和后继状态写进公开协议。

“成功调用了点击工具”和“用户要的结果已经出现”，是两句完全不同的话。这也是本专题选择 Pi 作为开源主样本的原因
02 / 四套栈

四套栈：相似的外形，不同的责任边界

Codex 和 Kimi 的原生执行层没有完整开源，所以最硬的结论来自公开接线、工具合同、签名产物和静态符号；DSH 与 Pi 可以一路读进 daemon。它们不是同等证据下的跑分，也不是四个可以直接互换的安装包。

闭源产品基线

node_repl → @oai/sky → CUAService

模型代码先留在不可信 realm，受信包才能取得 nativePipe、LaunchServices 和批准桥；App Policy 查询、状态与动作再经 framed JSON-RPC 进入原生服务。安装包另有 stdio MCP 入口，静态证据不能证明某次会话选了哪条。

状态AppState + 最新 index
策略App Policy + TCC
缺口原生控制流不可见
产品化接线

Plugin → stdio MCP → launchd/XPC

Kimi Code 把 Plugin、App、后台服务和系统权限拆成四种 capability 状态；独立 KimiCU.app 才持有 AX 与屏幕录制权限。原生层显式认识 stale snapshot，但公开工具仍以 app 和临时 index 为主。

状态快照 + 临时 index
运维安装、服务、权限 doctor
缺口执行层 proprietary
开源主样本

Pi extension → state contract → platform backend

Pi 不再公开一堆彼此松散的 click/type 工具，而是让 act_ui 消费一份不可变 state。macOS、Windows、Linux 和 CDP page 都进入同一 root forest，平台差异留在 backend 后面。

状态stateId + @e + epoch
验证事务 + postcondition
边界三平台能力并不对称
早期 clean-room 复刻

Cordis tools → Unix socket → Swift daemon

DSH 把 Codex 风格的十工具、长度前缀 JSON-RPC、Swift AX/截图/输入 daemon 和 turn 生命周期写得很直白，是理解协议的好教材。它的 actionPerformed 仍主要表示请求没抛错，状态和验证合同明显比 Pi 薄。

价值实现小、协议透明
护栏peer UID + App approval
短板无 stateId / postcondition
03 / 观察合同

观察合同：临时 index 和 stateId 差在哪里

Codex、Kimi 与早期 DSH 都把模型引向“先取状态，再用最新 element index”。这比纯坐标稳，但 index 自己不说明来自哪次观察。DSH 的 Swift daemon 只在当前 AppSession 保存 lastTree；同一回合若界面更新或并发动作抢先发生，旧 index 仍可能指向另一棵树上的同一数字。turn/end 清理只能挡住跨回合泄漏，挡不住回合内部竞争。

Pi 的关键进步不是换了命名，而是把所有权写进协议：@e12 只属于一个 stateId；每个物理资源还有单调递增的 epoch。缓存查询可以并行，真正读写同一 App 进程则进入同一 lane；一份旧状态发起写操作时，会在事件送出前被拒绝。动作返回的新 stateId 才是下一步的合法起点。

小白版区别

临时 index 像“刚才画面里的第 12 个控件”；stateId + @e12 + epoch 像“照片 A 上的第 12 个控件，而且拍照后没人先改过这扇窗口”。后者才足够让系统在出手前发现地图过期。

04 / 动作合同

动作合同：送出事件不等于任务成功

早期 DSH 的 TypeScript 工具只要 daemon request 没报错，就固定返回 actionPerformed: true；点击、拖拽、键入等路径还会先激活目标进程。调用方当然可以再取状态，但“执行”和“验证”没有被同一个合同锁住。Codex 的旧专题也暴露了类似风险：transport timeout 后看不到 exactly-once 回执，动作可能没发生，也可能发生了但响应丢了。

Pi 的 act_ui 把一组依赖动作做成一项事务：先检查 base state，再按顺序 preflight、delivery、verification；可附上“Saved 出现”之类的语义 postcondition。helper 报 worked、didnt 或 unknown，bridge 保存完整后继状态，只有身份匹配可信时才显示紧凑 diff。事件被系统接受，不再自动等于业务结果成立。

结果它真正表示什么下一步
worked有可核对证据支持动作生效使用返回的后继 state
didnt已检查且没有达到要求根据无副作用证据决定是否换策略
unknown无法证明成功或失败停止重放，重新观察
05 / 权限边界

权限边界：谁获准看，谁获准动

四套实现最终都绕不开操作系统权限。Codex 还在上层加了受信 realm 与 App Policy；Kimi 把 Plugin、App、service 和 TCC 权限做成可诊断的独立状态；DSH 用 ctx.approval 管 App 首次访问，并用 getpeereid 与 0600 socket 限制本机同用户；Pi 的 headless 则把“不抢焦点、不动真实键鼠”提升为执行策略。

门回答的问题不能替代什么
模型/动作确认这项副作用是否符合用户意图不能授予操作系统权限
App 范围Agent 是否可以接触这个目标不能证明某次点击安全
本地进程认证谁能连接原生 daemon不能判断业务意图
TCC / OS capability进程能否读屏、访问 AX、合成输入不能替用户决定该不该做
06 / 失败恢复

失败恢复：先判断副作用，再决定重试

UI Agent 最危险的默认值不是“失败”，而是把未知当失败后自动再做一次。按钮可能已经按下，只是 AX 没及时变化；文本可能已经输入，只是回执超时。Codex 的 21 类原生错误和 transport 错误必须分层读；Kimi 静态合同也明确区分 stale、弱回读与缓存失效；Pi 则禁止对模糊的 pointer 结果盲目重放。

07 / 怎么选

怎么选：产品使用与工程参考不是一回事

想直接在 Kimi Code 里用：KimiCU 的安装、服务和权限检测更产品化，但执行层闭源，应把敏感动作确认、telemetry 和真实 App 兼容性留作风险项。单产品的安装链与二进制边界在 Kimi 专项附录里保留。

想学习或二次开发：优先读 Pi v0.5.1。理由不是 star 多，而是它把不可变状态、陈旧写拒绝、并发资源调度、动作事务、语义验证、bounded output 与三平台 backend 一起开源，并有对应的 schema、lifecycle、concurrency 和 platform tests。

想看 Codex 风格的最小复刻：AzaiSakura 的 DSH 仓库很适合读协议和 daemon 边界，但不应当作今天最成熟的可靠性基线。它的价值是“看得懂”，不是已经解决了所有 stale state、后台输入和结果验证问题。

09 / 证据边界

证据边界：这次确认了什么，还缺什么

Codex 样本固定在 build 6234，能直接读到模型合同、可信 runtime、typed client 和 transport，原生层仍主要依赖 Mach-O 元数据与符号。Kimi 固定到 Kimi Code 提交 b184b314 和带哈希的 KimiCU 0.5.8，公开接线完整，动作内部仍是专有实现。DSH 固定到 a572908，Pi 固定到 v0.5.1 的 4b8dbd7，两者可以直接检查源码。

尚未完成的是同任务动态基准。我们还不能说 Pi 的真实成功率一定高于 Kimi 或 Codex，也不能把其他同名 DSH fork 的新能力算进 AzaiSakura 这份早期实现。下一步真正有价值的实验，是在隔离用户下让四套系统完成相同的原生 App、Electron、浏览器和画布任务，并注入 stale state、焦点漂移、回执超时与权限中断。届时比较的是可复现行为，不是 README 形容词。

当前推荐结论

把 Pi 当作今天最值得读的开源设计参考；把 DSH 当作 Codex-style 最小实现教材；把 Codex 和 Kimi 当作产品级但证据受闭源边界限制的样本。使用产品时看权限与体验，设计系统时优先抄状态合同，不要只抄十个工具名。
