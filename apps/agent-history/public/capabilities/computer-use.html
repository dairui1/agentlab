CUA：后台执行与可视化交互

目标不是让 Agent 悄悄接管电脑，而是让它尽量在后台完成动作、不移动你的物理鼠标，同时把虚拟轨迹、目标、点击、输入和结果清楚地呈现出来。每一步都应该看得见、停得住、查得清。

想象 Agent 要点击一个后台窗口里的“保存”。可靠的系统必须同时完成三件事：把动作送到正确控件、让你看到它正在点哪里、再证明保存结果真的出现。动画不能代替动作，动作回执也不能代替结果。

01 / 核心模型

核心模型：后台执行不等于隐形执行

“不抢鼠标”描述的是执行方式，“看得见轨迹”描述的是呈现方式，两者并不矛盾。真正的点击可以通过 Accessibility（AX）动作或发给目标进程的定向事件完成；屏幕上另外画一枚虚拟光标，告诉用户目标在哪里、动作何时发生、结果是否确认。虚拟光标只解释动作，不参与输入，因此不会碰物理指针，也不该改变窗口焦点。

02 / 两套平面

两套平面：动作与动画必须解耦

执行平面掌握真正的系统能力：读取 AX、截取目标窗口、解析控件、发送输入、等待变化。呈现平面只消费执行平面已经算出的目标点和状态，在透明、click-through 的 overlay 上画路径、高亮和反馈。Pi 的开源实现把 agent cursor 放在原生 helper 内，是因为最终屏幕坐标也在那里产生；同时明确规定 cursor rendering 不能延迟 action delivery，新动作可以替换仍在播放的旧动画。

平面拥有的状态可以影响什么绝不能声称什么
执行平面root、state、element、资源 epochAX、截图、目标 App 输入事件送出就等于业务成功
呈现平面轨迹、目标点、动作阶段透明叠层、虚拟光标、状态提示动画播完就等于点击生效
用户控制面暂停、批准、前台降级选择允许、拒绝、接管或终止系统权限等于用户意图
可视化不是把真实鼠标借给 Agent，而是为后台动作制作一份实时、不可冒充成功的解释层。
03 / 后台动作

后台动作：语义、定向事件与前台降级

先别把所有“后台”混成一件事。语义后台直接调用控件能力；定向事件把像素输入送给确定的进程与窗口；隔离桌面让 Agent 在自己的 VM、X11 DISPLAY 或 compositor 里占据前台；浏览器原生路径则直接操作 DOM/CDP target。前两种解决本机共存，后两种靠环境或协议绕开单一物理桌面。

后台类型真正的隔离边界适合的表面主要风险
语义后台element / AX、UIA、AT-SPI按钮、文本框、菜单树缺失或语义不完整
定向事件精确 PID + window自绘控件、像素区域事件被过滤、窗口目标漂移
隔离桌面VM、DISPLAY、compositor完整桌面与视觉任务环境成本和登录态隔离
浏览器原生tab / target / document generation网页 DOM 与后台标签页浏览器 Chrome 与系统弹窗仍需原生 CUA

本机动作仍应按能力阶梯选择，而不是所有控件都模拟鼠标。按钮先尝试 AXPress，文本框先尝试 AX value/editable semantics；只有 AX 不能表达的区域，才使用与最新观察绑定的坐标和定向事件。早期 DSH 会在 click、drag、type 前直接激活目标 App，这能提高成功率，却已经不是纯后台；成熟 Driver 还应在目标窗口不唯一、状态过期或无法证明路由安全时直接拒绝。

首选路径

直接操作控件语义

利用 AX/UIA/AT-SPI 的 press、set value、editable text 等能力，不移动真实指针，也通常不需要抬升窗口。

优势目标明确、后台优先
证据控件属性与回读
限制画布和自绘 UI 可能缺失
第二路径

把事件定向给精确窗口

使用从同一份截图和窗口几何得到的坐标，将点击或键盘事件投递给确定的 PID 与 window。它可以不移动物理鼠标，但“传给进程”不等于“落在该进程的正确窗口”，多窗口目标不唯一时应该拒绝。

优势覆盖自定义控件
证据精确窗口 + 后继观察
限制遮挡、焦点和坐标漂移
显式降级

确实需要焦点时再前台化

某些编辑器、系统弹窗和全局输入只能在前台可靠工作。系统应该先告知用户，再聚焦、执行并恢复，而不是偷偷抢走键盘。

触发后台路径已明确失败
呈现显示“需要前台”
限制不得重放模糊副作用
安全终点

无法保证目标时停止

没有新状态、权限不足、目标不唯一或动作结果未知时，正确选择是停下并让用户接管。

触发stale / denied / unknown
呈现保留最后可信位置
限制不能改成全局点击硬做
04 / 虚拟光标

虚拟光标：显示轨迹但不移动真实指针

虚拟光标适合放在原生透明叠层中：窗口不接受点击，不出现在可操作根列表里，不改变 key window；输入点由执行 helper 直接交给动画层，避免再做一次坐标转换。它可以从上一个 Agent 目标平滑移动到新目标，抵达时显示点击波纹，输入时给控件外框加状态，等待验证时则停留但改变状态，而不是假装继续忙碌。Pi 公开了 ghost cursor 的基本所有权和生命周期；Qwen Code 的 Cua Driver 又把 session 颜色、Agent 名称、background/foreground 与 AX/pixel/browser 目标类型做成 overlay 语义，同时明确它不是授权或成功指示器。

不要追着真实鼠标画

真实鼠标属于用户。Agent cursor 应维护自己的位置和动画队列；用户移动物理鼠标不会拖走它，Agent 动作也不会把用户指针吸过去。两者可以同时存在，视觉样式必须明显不同。

画面元素表达的信息消失条件
轨迹Agent 正在前往哪个已定位目标新动作覆盖、暂停或目标失效
目标高亮当前 element ref 或坐标区域状态 epoch 改变
点击波纹事件在何时送出短动画完成，不表示成功
结果标记worked、didnt 或 unknown用户确认或下一份状态取代
05 / 状态绑定

状态绑定：光标必须指向这一次观察

最危险的错觉，是动画仍然准确地飞向一个已经不存在的按钮。element index 只写“第几个”，没有写它来自哪次观察；窗口移动、菜单重排或并发动作发生后，同一个数字可能换了对象。Pi 的 stateId + @e ref + resource epoch 把这件事变成可检查约束：旧写入在 dispatch 前失败，坐标只属于带图像的那份状态，动作完成后返回新的 stateId。

呈现层也应遵守同一约束。每条轨迹必须带 stateId、目标 ref、屏幕坐标和 resource epoch；只要执行层发现状态过期，就立即取消动画并显示“目标已变化”，而不是让虚拟光标完成一段漂亮但错误的移动。

06 / 交互回执

交互回执：点击已送达不等于目标完成

一次点击至少有三层结果：事件有没有送出、Driver 有没有证据表明控件响应、用户要求的状态有没有出现。早期 DSH 在 daemon request 不抛错后固定返回 actionPerformed: true，这只能覆盖第一层。Pi 用 worked / didnt / unknown 与后继状态改善了这一点；Cua Driver 的合同又把动作事实收敛为 confirmed / partial / unverifiable / suspected_noop / refused，并把业务后置条件单独交给 verify_state 返回 satisfied / unsatisfied / unknown。

07 / 焦点降级

焦点降级：什么时候不能继续装作后台

“纯后台”是目标，不是所有桌面软件都能满足的事实。原生按钮和标准文本框常能走语义路径；画布编辑器、游戏、复杂 Electron 控件、系统级弹窗和依赖 key window 的输入可能要求前台焦点。Pi 的严格 headless 模式会禁止激活窗口、移动真实指针和发送 raw input；非 headless 才允许在已证明后台键盘输入没有副作用后尝试前台降级，模糊的 pointer 结果不会重放。

正确的产品文案不是“始终后台”

界面应明确显示当前动作属于“后台语义”“后台定向”“需要前台”还是“等待用户”。只有用户允许后，CUA 才能跨入会打扰当前工作的路径。

08 / 用户控制

用户控制：可见、可停和可接管

可视化的价值不只是好看，而是给用户一条控制回路。overlay 或 PIP 至少要显示目标 App、动作类型、当前阶段和结果强度，并提供暂停与接管。用户一旦接管，执行层应取消未送出的动作、让当前模糊结果进入 unknown、丢弃旧 refs，再从一份新观察恢复。Codex 的固定构建已经能看到 PIP、用户干预和 session 错误边界；Kimi 则把 App、service 与权限状态拆开诊断。

失败时怎么停

没反应。现在能直接重试吗？

同样是“没反应”，卡在权限、观察、动作或回执，恢复办法可能正好相反。

09 / 参考架构

参考架构：一套值得实现的 CUA

如果按你想要的体验来做，我不会整包照搬一个项目：Host 层借鉴 Pi 的 root forest、immutable state、resource epoch 与受检查事务；Native Driver 层借鉴 Qwen Code 发行的 Cua Driver 的精确窗口路由、结构化拒绝、ActionResult、跨平台能力矩阵和 session cursor；产品层再补 Codex/Kimi 的签名 Helper、权限诊断、审批、暂停和接管。关键不是拼产品清单，而是守住下面这条链：

必须满足的不变量原因
真实鼠标与 Agent cursor 分离用户和 Agent 可以同时工作
动画不阻塞输入，输入不等待动画呈现故障不能改变执行语义
每个目标绑定 stateId 与 epoch拒绝漂亮但过期的轨迹
pointer unknown 不自动重放避免双击、重复发送或重复删除
前台降级必须可见且可拒绝不偷偷抢走用户的键盘焦点
完成标记必须来自 postcondition不让执行者自己宣布成功
10 / 证据边界

证据边界：产品只作为实现样本

本文用 Codex build 6234 研究可信 runtime、App Policy、本地 transport、PIP 与失败分层；用 KimiCU 0.5.8 研究 Plugin、MCP、launchd/XPC、权限 doctor 和后台输入合同；用早期 DSH clean-room 源码暴露简单实现的 session、socket 与验证缺口；用 Pi v0.5.1 研究 Agent Host 的 stateId、epoch、transaction 与 successor diff；再用 Qwen Code 的 Cua Driver 0.20.3 发行版研究更成熟的 Native Driver、ActionResult、精确拒绝和 session cursor。它们服务于同一个 CUA 问题，不各自成为产品章节。

仍缺少的是同任务动态实验：虚拟光标是否准确落在最终 grounded point，后台动作是否真的不改变用户焦点，动画与动作在并发时会不会错配，以及前台降级后能否安全恢复。当前结论是源码与固定发行包支持的设计研究，不是已经完成的真实 App 成功率测评。

收束

你要的 CUA 方向是成立的：后台执行负责不打扰，可视化负责不隐瞒，状态回执负责不自欺。三者必须由同一份观察身份连接，少一个都只是“看起来会操作电脑”。

执行原则语义后台优先，前台降级必须明示。不把成功率建立在偷偷抢焦点上。
呈现原则虚拟光标和物理鼠标完全分离。轨迹解释动作，不参与动作。
完成原则绿色完成来自后继状态，不来自动画。unknown 时停止，不自动再点一次。
