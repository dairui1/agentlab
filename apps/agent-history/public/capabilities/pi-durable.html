你让 Agent 发布一个版本。它已经跑完测试，也构建了安装包。就在上传时，进程退出了。

现在重新打开它，应该从哪一步继续？从头来一遍，测试和构建会白做；可上传如果已经成功，只是结果没记下来，再传一次又可能重复。

Pi Durable 想解决的，就是这种工作做到一半以后，怎样接着做的问题。下面沿着这次发布看它的办法。这个例子是机制推演，不是实际发布记录。

聊天记录里有进度，为什么还不够？

从对话里，大致能看出测试已经通过。但一句“开始上传”，并不能告诉新进程上传有没有成功。人或新 Agent 还得检查文件、查询远端，再决定哪些步骤要重做。

Pi Durable 换了一个办法：把正在执行的工作直接保存成任务记录。除了对话，它还记着当前阶段、执行参数，以及正在等什么。新进程打开同一份存储，就能找到尚未完成的任务。

库自带模型请求、工具调用的执行记录。要让整个发布流程准确停在“测试完成，等待上传”，开发者还需要把这些业务步骤设计成可保存的阶段。这个例子按这样的应用设计展开。

例如，上传前保存“接下来上传这个安装包”，收到结果后再保存“这一步已经完成”。源码把这类可保存、可接续的工作叫作 Task。

这是供开发者接入应用的库。终端里的 Pi Coding Agent 仍是另一套产品，已有会话不会因为安装 Durable 就自动获得这套恢复流程。

正常运行时，先保存，再动手

先把没有中断的一次上传看完整。

为什么不先上传，回头再记进度？因为进程如果在中间退出，存储里甚至不会留下“尝试过这次上传”的记录。Pi Durable 的工具执行流程会先保存调用意图，然后才让工具动手。

结果也一样，要先存下来，再让界面和其他任务看见。内置工具流程把调用结果和任务状态一起保存，随后才发布变更。否则界面已经显示“上传完成”，新进程却找不到这份结果，恢复就会失去依据。源码中的 commit() 负责这种成组保存。

到这里，它建立了一条很有用的规则：后续工作依据已保存的进度继续，而不是依据旧进程碰巧还记得什么。

进程重启，工作从保存的阶段继续

回到那次中断。新进程不可能接住旧进程的函数调用、网络连接和内存，它能读到的是存储里的记录。

Pi Durable 打开存储后，会找出未完成的任务，把上次标为“正在运行”的任务重新排进待运行队列。应用启动调度后，任务按保存的阶段继续。

在这套按阶段保存的发布流程里，测试和构建已经提交完成结果，就可以继续后续工作，不必靠模型重新回忆。上传的结果也已经提交，就往下一步走；如果只留下“准备上传”，却没有结果，这一步便需要单独处理。

还有一件实际的事：库不会替你把退出的服务重新启动。应用或进程管理器要先启动新进程，再打开这份存储、接续任务。

上传成功了，却没来得及保存结果

最难处理的中断，发生在第二步和第三步之间：远端已经收到了安装包，本地却还没保存结果。

新进程看到的只有“准备上传”。它无法仅凭这份记录，分清请求还没发出、发出了但失败，还是已经成功。这时再做一次，可能真的多做一次。

Pi Durable 默认不会替应用猜。工具执行被打断后，它会给模型一个 interrupted 结果，说明这一步可能已部分执行，留下已经保存的输出。应用还需要安排一次远端查询，确认上传是否完成，再决定是否重试。

开发者也可以明确声明一个工具能安全重跑，源码里的选项叫 replay: "safe"。但让上传变得可重跑，需要上传服务一起配合。例如，每次请求都带同一个任务编号，服务发现这个编号已经处理过，就返回原来的结果，而不是再创建一个版本。

这种“再试一遍不会多做一次”的约定，叫幂等。Pi Durable 能保存编号和执行进度；真正防止远端重复动作的，是服务对这个编号的处理。恢复测试里也能看到这个分工：假服务被调用两次，但凭同一个编号，只应用了一次业务操作。

什么应用值得承担这套复杂度？

如果一个 Agent 由你一直看着，任务短，失败后很容易核对、重新执行，普通会话记录往往已经够用。Pi Durable 的收益，更容易出现在任务还没结束，服务却可能重启的地方：重开后接着处理工单，等待人的审批后继续，或几个步骤要分开保存和接续。

它把模型请求、工具调用和开发者自己的任务放进同一套保存与恢复流程里。应用因此可以围绕“哪些工作还没结束”组织界面和调度，而不必把所有进度塞进一段长对话。

代价是，开发者要把重要阶段设计清楚，选择真正持久的存储，并为上传、发消息等外部动作准备核对和重试规则。当前 API 仍是实验性的，升级时也要考虑旧任务能否继续运行。

Pi Durable 让继续工作有了明确起点。至于那一步该不该再做，它把判断所需的记录留下来，而不是替外部世界作保证。

技术细节与研究范围

本文依据 2026-10-08 固定的源码与本地离线测试。下面补充正文没有展开的实现，完整文件、行号和哈希保留在证据索引中。

模型生成到一半时，具体保存了什么？

普通流式请求会保存模型、部分请求选项和上下文截止位置。重开后从这个位置重建上下文，再请求模型；已保存的半截回复标为中断。请求前的 hook 会再运行，模型输出和费用也可能与第一次不同。

如果提供商已经返回后台请求的 handle，并被保存下来，则走另一条路径：重开后继续轮询已有请求。等待重试的时间也会保存，而不是每次重启都从头计时。每个会话另存 provider session UUID，用于缓存和会话身份，不是提供商的请求去重承诺。

新消息、子 Agent 和取消，怎样接续？

会话忙碌时，新输入先进入持久队列。纠正当前工作的 steer 在工具轮结束后放入上下文，下一项 followUp 等当前回答结束后接续。同会话的 requestId 可找回已有输入，但不会比较两次正文是否相同；不要用同一个编号发送另一项请求。

子 Agent 是由工具任务拥有的会话。恢复时，工具应先查找自己已经创建的孩子，再复用之前的输入，避免多创建一个。取消标记向孩子传播，清理则等孩子收尾后再到父任务；后台任务不会被普通会话取消顺带停止。

关闭 Harness 与取消任务也不同：关闭保留未完成检查点，供以后接续；取消先保存取消标记，再安排清理。过期任务不能继续写入 Session，但忽略取消信号的自定义代码仍可能让关闭一直等待。

会话分叉，会连文件一起复制吗？

应用的计划、工单等 JSON 状态可以与对话一起保存，具体哪些记录一起提交，由应用安排。分叉时，文档可选择复制分叉位置的旧值、父会话当前值，或从初始值开始。复制的是这些数据，不是它们指向的目录或容器；两个分支指向同一路径，仍会改同一份文件。

本地执行环境的 cwd 只是路径解析起点。官方“每会话一个 sandbox”的例子实际分配的是目录，容器、文件权限与网络限制要由宿主另行提供。

重启后，还会用原来的代码吗？

存储保存任务状态和所选工具的名字，不保存函数源码。新进程需要重新安装相应定义；缺少定义、代码版本太旧或迁移失败，旧任务会等待处理。重跑工具时也可能使用当前的代码和工作目录，因此升级应用时要考虑已有任务。

memo 可以为正在运行的任务保存第一次作出的决定，适合避免恢复后重新作出同一判断。但外部审批消息发出后、memo 写入前，仍有中断窗口。内置 read、bash、write、edit 都没有声明 safe；能否重跑，需要工具作者明确选择，保存时与当前定义也都要允许。

聊得太长时，旧内容怎么办？

压缩也是可恢复任务：接近上下文阈值时后台总结旧消息，后续边界再采用摘要；到更靠近上限的阻塞阈值时，会先等压缩完成，再请求模型。提供商仍报告上下文超限时，可以压缩并再试一次。旧消息保留在存储里，可供查询。摘要是否遗漏重要约束，需要另行评测。

存储能承受什么故障？

MemoryStorage 只在内存里，不提供跨进程恢复。Node SQLite 使用 WAL 和 synchronous=NORMAL，官方区分进程崩溃与主机故障：主机故障可能丢失最新提交。JSONL 默认不启用 fsync；启用后先刷 sidecar，再追加主日志提交标记，但主流程没有在每次返回前无条件刷主日志。

同一份存储只允许一个进程拥有，库没有跨进程的任务执行锁。多实例部署要防止两个调度器同时执行同一项工作。固定版本已有 Cloudflare Durable Object SQLite adapter，本研究没有部署它来验证完整托管服务。

本次验证做了什么，还有哪些问题？

源码固定为 earendil-works/pi 的 1cedd32724abfcb0915f76cc61b6827e2c16dbad，包版本 1.1.0、MIT 许可、Node ≥ 22.19.0。固定 main 比 v1.1.0 tag 多两个提交，Durable 的 src、test、package.json 未变化；研究和测试仍明确以 main 为准。

47 个非 e2e 测试文件通过，977 项通过、2 项平台相关跳过。运行环境为 macOS arm64、Node 25.6.1、Vitest 4.1.11，清空凭据并隔离 HOME。首轮模块解析失败后，只用外置配置合并上游已有 source aliases，未修改源码或构建发布包。

恢复测试主要使用受控关闭与重开、假模型和假服务。两个真实模型 cache e2e 没有运行，也没有做 SIGKILL、断电、真实外部服务或生产负载实验。对应固定提交的上游 CI在 Test 步骤失败，具体失败包未确认，不能以本地 Durable 合同通过替代整仓结果。
