恢复有三层保存事实、恢复任务、核对外部动作。Pi Durable 主要接住前两层，第三层需要应用和外部服务一起完成。

假设 Agent 正在发布一个版本：测试已经通过，上传请求已经发出，进程却在写回结果之前退出。重新读一遍聊天记录，并不能回答“再上传一次会不会重复”。Pi Durable 值得研究的地方，是它把这类中断拆成了可保存、可恢复、也能明确拒绝盲目重试的状态。

持久化的不只是对话，还有正在做的事

Pi Durable 是 Earendil 在 Pi 仓库中提供的实验性库，用来构建长期运行的 Agent 应用。它通过 pi-ai 访问模型，通过 chord 管理文档状态，采用 MIT 许可，包声明 Node ≥ 22.19.0。终端里的 Pi Coding Agent 仍是另一套产品；安装 Durable，不会自动把原有 CLI 会话升级成后台服务。本文固定包版本为 1.1.0 的源码，而不是把发布时的介绍当成今天的接口。

一个 Harness 打开一份存储，运行其中的多个 Conversation。对话由不可变的 Entry 组成，应用状态放在可更新的 Document 里；一次模型请求、一次工具调用、一次压缩，则各自是持久 Task。Task 不是聊天里的一句“下一步去上传”，而是带阶段、检查点、等待条件和所有者的状态机。

三种“继续工作”并不相同
办法留下什么进程已死以后
对话记录 / 进度文件已写下的消息与业务进度由人或新 Agent 重新判断下一步
tmux / 常驻进程仍在运行的进程进程本身退出后仍需别的恢复办法
Pi Durable消息、排队输入、任务检查点与文档应用重启并重新打开存储，再调度未完成工作

这个定位适合由消息触发、需要等待审批或跨进程接续的应用。不必为了让一个有人照看的终端会话“更高级”，就把它改成持久工作流。要获得恢复能力，也得接受状态模型、迁移和副作用核对带来的成本。

先保存，再让界面与调度器看见

Session 把所有修改排在同一条串行提交线上。提交回调可以一起追加消息、修改文档、创建任务；内核先准备这批写入，等待 Storage 提交成功，再接纳新的文档状态并发布变更。界面和调度器因此观察到的是已提交事实，而不是刚在内存里发生、随时可能消失的动作。

例如工具把“发布完成”的结果和业务文档里的版本号写在同一批提交里，可以避免一处更新、另一处没更新。但这个原子范围只到这份 Storage。上传文件到远端仓库，不会因为写在 commit() 回调里，就突然与本地数据库成为一笔事务。

源码还区分了“确定没写进去”和“无法确认写入结果”。只有 StorageRejected 表示整批没有生效；其他存储异常会把 Session 标成不可继续使用，要求重新打开。若存储已经提交，内存接纳却失败，也走这条路径。这里没有假装所有报错都能原地回滚。调用方取消等待，也不会打断已经获准进入存储的提交。

恢复的是最后一个检查点，不是旧进程

重新打开 Harness 时，调度器加载非终态任务，把上次留下的 running 改回 pending。它没有复活旧的 JavaScript 调用栈。应用调用 resume()，或提交、等待工作时，调度器才开始按保存的阶段继续执行。只打开存储和真正恢复调度，是两步。

自定义 Task 每次用 runtime.commit() 保存下一阶段，或者保存要等待的子任务和计时条件。进程在一次阶段处理函数中途退出，下次可能重新进入同一阶段。因此“每个阶段有检查点”不等于“阶段内每条语句各执行一次”。发送消息、扣款、部署等动作仍要用稳定任务 ID 派生幂等键，并在外部系统确认。

close() 与 abort() 也不同。Close 封闭提交和调度，发信号并等待正在执行的代码，但不写持久取消结果，留下检查点供重开恢复；Abort 先保存取消标记，再安排清理。过期调用不能继续提交 Session，但忽略取消信号的自定义代码，仍可能让 Close 等很久。

工具默认不盲目重跑，safe 也不是认证

工具先保存执行意图，再进入 execute()。重启后，如果意图里保存的 replay 策略和当前工具定义同时是 safe，才允许重新执行；否则返回 interrupted 错误结果，带上已经提交的部分输出。这个保守默认值很重要：系统宁可告诉模型“这一步被打断”，也不替应用猜远端动作没发生。

以“上传版本后进程退出”为例，以下是场景推演
恢复条件Harness 怎么做应用还要知道什么
未声明 safe记录 interrupted，不自动重跑 execute远端是否已经接受上传
声明 safe，但只是普通上传允许重跑同一工具任务可能重复上传；safe 标签本身没有消除副作用
safe + 远端幂等键重新请求，以稳定键寻找或复用结果服务的去重范围、有效期与请求一致性

固定版本的内置 read、bash、write、edit 都没有声明 replay，因此默认按 unsafe 处理。不要因为工具名叫 read，就假定恢复时会自动重跑。应用可以提供显式 safe 的读取工具，但重新读取可能看见新内容；“可重跑”不是“结果与第一次相同”。

本地恢复测试使用带幂等账本的假服务，检查的是调用两次、业务动作一次。去重由假服务提供，不是 Pi 完成了跨系统原子提交。unsafe 工具返回 interrupted 后，模型仍可能继续回答，最终 Submission 也能是 done；done 不是所有工具成功。

取消也不能被理解成撤销。任务可以执行应用提供的 abort 清理函数，外部服务是否支持补偿、补偿能否再试、失败后谁核对，仍需要专门设计。

中断的流式请求会重发，不会从半个词接着生成

Generation 保存准备请求时的模型、thinking、stream options 和上下文截止位置。恢复时从这个 committed cutoff 重建上下文，再发起请求；已经持久保存的半截回复，会留下带中断状态的 Entry，而不是伪装成完整答案，也不是继续旧连接上的 token 流。

这里要谨慎使用“同一个请求”。beforeRequest hook 位于实际请求阶段内，恢复后会再跑；模型服务也未必是确定性的。能确认的是保存的截止位置与部分选项被复用，不能据此断言线上请求字节完全一致、答案完全相同，或不会重复计费。

已经取得并保存 provider handle 的 deferred 请求是另一条路径：任务保存 handle 和 pollAt，重开以后继续 fetchDeferred，不是重新创建请求。Retry 的 backoff 也保存绝对等待时间。能恢复轮询，不代表提供商一定保留了结果；取消远端任务也只能尽力请求，不能只凭本地取消状态认定已经停止。

每个 Conversation 另存一个 pi.provider UUID，传给模型层作 session identity。重开、压缩和模型切换保留它；子会话或 fork 获得新的身份。它服务于缓存与会话亲和性，不是提供商承诺的 exactly-once 请求键，更不是恢复权重、KV cache 或旧流的凭证。

部分回复和运行中工具输出按配置周期提交，默认间隔为 100 ms。这意味着最近尚未提交的片段可以丢失；也意味着存储越慢，进度提交和恢复窗口的取舍越重要。不要把默认周期写成断电时绝对不会丢失更多数据的上限。

输入被接收，不代表模型已经读到

submit() 在一次提交中接收输入并返回 Submission；忙碌会话把它放进持久 pi.inbox。requestId 可让同一 Conversation 的重试返回已有 Submission，避免重复接收。它比较的是身份和输入类型，不会逐字比较新旧内容：同一个键若被拿来发送另一句话，也可能只拿回旧记录。所以应让键表示一次真实请求，而不是一个可随意覆盖的槽位。

队列不只保存“待发消息”。steer 可以在工具轮结束的边界进入当前 run；followUp 在最终边界接续；普通 write 是被动写 Entry。它们按模式在边界挑选、写入消息并更新 Submission 状态。当前正在执行的工具不会因为一句 steer，自动停止或把已经做的事撤销。

要显示“用户纠正已生效”，应用应区分 queued、placed 和最后的 done / unanswered，再追踪后续请求。取消 wait() 只是停止这次等待，不会取消后台工作；撤回已 placed 的输入，也不能假定能从模型或外部世界收回。

子 Agent 是被任务拥有的会话，取消沿归属树走

工具可以创建一个 Conversation，把 owner 指向自己的 task ID，再给它配置模型、工具和指令。这样子 Agent 与普通会话共用持久化机制，不必另造一套临时 Promise 管理器。重放安全的子 Agent 工具还要先按 owner 查询已有孩子，并用稳定 requestId 复用提交，否则一次恢复仍可能生出两个子 Agent。

任务完成并不总是立刻进入 terminal。如果它拥有的工作还没收尾，结果会暂存在 completing。取消标记沿归属树向下传播，abort 清理则从叶子向上执行：等孩子的普通 owned work 收尾，再调用父任务的 abort。父子关系因此不仅是界面上的缩进，还影响何时能宣布结束。

后台任务则是明确的例外：它属于 Conversation，却不阻止当前会话进入 idle，普通 Conversation abort 也会留下它及其孩子。要停下后台工作，必须直接取消那个任务，或显式包含 background。界面显示“当前回答结束”，不能被当成“这个会话再也没有活动任务”。

业务状态跟着提交走，文件系统不会跟着 fork

待办列表、计划、工单、执行环境的地址，都可以定义成 typed JSON Document，与消息和任务一同提交。文档声明自己的 scope、history 和 fork 策略：asOf 复制分叉位置的历史值，current 取父会话当前值，initial 从初始状态开始。不同业务状态不应被迫采用同一种复制办法。

Conversation fork 看得见父对话截至指定 Entry 的消息，再独立追加。保存“sandbox 的路径”不等于复制 sandbox：如果两个分支都指向同一个目录，它们仍会改同一份文件。分叉实验要同时检查消息范围、文档值和真实执行环境，而不能只看两个不同的 Conversation ID。

官方 per-conversation sandbox 示例用 fork: "initial" 避免自动继承旧目录，再由应用分配新的环境。示例中的“sandbox”只是目录；用目录区分用户，不会自动得到容器、网络限制或操作系统隔离。

状态可以保存，运行它的代码仍要重新安装

Registry 在进程里安装 extensions、tools、hooks 和任务定义；Conversation 保存的是选择的名字，不是这些函数的源码。新进程需要重新提供定义，旧任务才能继续。缺少定义、任务记录比代码版本新或迁移失败，会让任务阻塞；不是丢掉旧状态以后随便从头来。

恢复还不保证用回上次完全相同的环境。工具 intent 的 safe 策略被固定，但重新 execute 时可以解析到当前 agent、extension 和 cwd。源码测试就覆盖了重开前后目录从 /one 变成 /two 的情况。因此生产应用应记录运行定义与环境版本，审慎决定升级中的旧任务是否继续，而不只固定 npm 包版本。

Hooks 可以拦截或改写调用，也可能在恢复中再次运行。memo 提供“第一次写入生效”的持久值，适合保存已作出的决定；可如果请求审批的消息已经发出、memo 还没保存，仍有重复询问的窗口。memo 能留住结果，但不会把外部审批平台纳入本地事务。

压缩本身也是任务，旧消息仍然留着

为了让长会话继续工作，Compaction 在上下文接近阈值时后台总结旧消息，到后续边界才采用摘要。下一次请求真的放不下时，才必须等；提供商若仍报告 context overflow，生成流程会压缩并重试一次。它不是无限重试模型请求，也不是在当前生成一半时悄悄改掉上下文。

压缩改变的是后续模型看见的 active range，旧 Entry 没被删除。Reset / handoff 同样建立新的上下文起点，历史仍可由工具查询。这给长期工作的 Agent 留出了重新出发的办法，但“历史可查”不等于模型会主动查对，更不保证摘要保留了所有关键约束。摘要质量、恢复后的任务质量，都需要另外评测。

这属于推理时的运行基础设施。本文没有发现据此建立的奖励驱动训练实验，也不把长任务、子 Agent 或自我 handoff 归为严格 Agentic RL / RSI。

进程崩溃、主机断电、多个进程抢同一份存储，是三种问题

Quick Start 中的 MemoryStorage 只保存在内存，不能跨进程恢复；要持久化，需要选择 SQLite、JSONL 或宿主存储。Node SQLite adapter 使用 WAL 和 synchronous = NORMAL。官方合同把进程崩溃与主机故障分开：前者可以恢复已提交内容，后者可能丢失最新提交。JSONL 默认不启用 fsync；启用后，先 flush sidecar 再追加 commit marker，但源码没有在每次提交返回前无条件 flush 主日志。不要把选项名直接升级成“断电零丢失”。

同一份存储只允许一个进程拥有，库不提供跨进程的 Harness 所有权锁。SQLite 的文件锁与 busy timeout 保护数据库操作，不替多个调度器仲裁谁执行同一个任务。进程管理器应负责重启，部署层应负责唯一持有者、备份和故障切换；存储 API 返回成功，也不是整项业务已经验收。

固定版本已提供 Cloudflare Durable Object SQLite adapter，不能再沿用发布初期“只有 Node adapter”的描述。但一个存储 adapter 不等于已经验证了完整的 Workers 托管 Agent 服务：网络请求、唤醒、alarm、权限和部署仍需要宿主接入与运行证据。

ExecutionEnv 把文件和进程操作交给宿主，支持按 Conversation 配置环境。Node 实现本质上使用本地文件系统和进程权限，cwd 只是路径解析起点，不是沙箱根。无环境时内置工具报错；有本地环境时，持久化不会替你补出权限隔离。

值得带走的判断是：把恢复单位变成可记录的任务，把不能确定的外部动作留成显式不确定性。Pi Durable 已经有具体的提交、调度和恢复机制，不只是给会话日志换个名字；但它仍是实验性 API。应用开发者可以借用这套结构，不能把宿主重启、幂等服务、安全隔离和业务验收一并外包给“durable”这个词。
