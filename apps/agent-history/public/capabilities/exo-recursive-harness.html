证据范围只覆盖固定 main 提交的源码和官方文档。没有运行安装脚本，没有接入付费模型，也没有把项目自己的效果描述当作独立复现。

Exo 最有价值的想法，不是让模型拥有更大的 shell 权限，而是把“可变的 Agent”放在“应该保持稳定的历史和恢复层”之上。问题也恰好出在这里：架构图画出了这条边界，默认启动配置却还没有把它完全变成模型无法越过的墙。

01 / 先说结论

先说结论：Exo 已经完成哪一半

把 recursive self-improvement 拆成两半，Exo 已经完成了很少项目认真做的前半段：Agent 能读自己的源码和运行历史，能改 Prompt、记忆、工具与 Harness，能请求宿主重新编译和重启，还能从 Git 与沙箱快照退回。

后半段仍然空着：什么叫“更好”，怎样生成多个候选，在哪里隔离试跑，谁用盲测结果批准采用，退化如何自动回滚。当前 guardian 只保证代码能编译并重新拉起服务，不会替 Agent 做行为验收。

Exo 已经是一个认真设计的递归自修改系统，但还不是一个已经证明能递归产生净改进的系统。本专题的核心判断
02 / 两层架构

两层架构：底座保存事实，Executor 决定行为

exoharness 管 agent、conversation、turn、event、artifact、secret 和 sandbox lifecycle；executor 决定给模型看哪些 event、用哪个模型、暴露什么工具、怎样压缩以及何时结束。这个拆分非常干净：Prompt 或 turn loop 改坏时，历史不必跟着换一种格式。

这比“Agent 把自己的 system prompt 存在一个文本文件里”更深入。真正允许演化的是策略层边界：同一份持久状态上可以换 turn loop、tool registry、memory policy，甚至换成 Codex 或 Claude Code 驱动的 executor。

03 / 自修改链

自修改链：看、改、编译、重启

canonical launcher 把 Exo 仓库挂进共享 agent sandbox。模型先从 exo/SELF.md 找到 Prompt、Harness、工具和 supervisor，再用 shell 修改同一份宿主工作树。修改完成后，rebuild_and_restart_exo 把固定的 restart-all --build 交给 detached guardian，当前 turn 先正常结束，新进程再接手。

阶段实现当前保证还没保证
观察源码、事件、adapter telemetry有结构化入口没有统一健康指标
修改RW repo mount + shell / manage_tool覆盖 Prompt 到 Harness没有路径级信任强制
验证cargo build阻止编译失败不测任务质量与安全回归
激活deferred guardian restartturn 可完成，服务有记录没有独立 adoption approval

这里最聪明的细节是 supervisor handoff。正在运行的 executor 不直接杀死自己，而是写一张带 update id、reason 和 conversation id 的工单，让宿主进程稍后构建并重启。问题是 guardian 的验收条件仍只有构建成功。

04 / 三种状态

三种状态：日志、Git 与沙箱不是同一个撤销键

Exo 的恢复能力来自三个互补的时间轴。event log 记录 conversation 与工具事实；Git 记录 Host 工作树中的代码变化；sandbox snapshot 记录执行环境的文件系统。rewind sandbox 不会倒回 event、secret、adapter 或 Git，git revert 也不会撤销已经发送的外部消息。

05 / 渐进变化

渐进变化：记忆、Skills 与 Tools

Exo 不要求每次改进都重写 Rust。最轻的是 remember：最多 200 条短事实作为 agent artifact，每轮完整注入。Skills 只注入名字和描述，正文按需读取。再重一点是 manage_tool 安装有严格 schema 的 TypeScript 工具。最后才是改 Harness 与重启。

这形成了一个很实用的修改梯度：事实记忆不该升级成代码，操作说明不必进入每轮完整 Prompt，一个 API adapter 不必重写 turn loop。只是最轻的记忆层也有现实缺口：并发 conversation 的 read-modify-write 没有 compare-and-swap，可能静默丢掉一条记忆。

06 / 关键问题

关键问题：trusted substrate 真碰不到吗

官方架构写得很明确：event log 和 secret 位于模型不可修改的 trusted substrate。可默认启动的另一段代码同样明确：整个 ROOT_DIR 以 --rw 挂载到模型拥有 shell 的沙箱，而持久状态就在宿主仓库下的 .exo/。

这意味着“append-only”目前主要是 API 语义。BasicObjectStore 为每个 event 写普通 JSON 文件，顺序由 latest head 与 write lock 维护，没有哈希链、签名或 WORM storage。正常 API 不会改旧事件，但拿到文件系统写权限的进程未必受这个合同约束。

这不是说 Exo 完全没有安全设计

secret 内容以 AES-256-GCM 加密，macOS 默认 master key 可放 Keychain；guardian 也只暴露固定 build/restart 动作。问题更具体：canonical repo mount 把信任层源码和本地状态放进了同一个读写树，部署方需要额外隔离才能兑现文档中的强边界。

07 / 克隆与谱系

克隆与谱系：底层原语有了，整机复制还没有

CLI 可以 fork conversation，底层 trait 也有 sandbox fork / restore。但“完整 Exo”还包括 Git ref、agent 与 conversation artifacts、secret、scheduler、adapter pairing、sandbox snapshot 和外部身份。SELF-CONTROL 把完整 cloning and migration 明确标为 not yet built。

这条边界很重要。能从某个 event 分叉新对话，是状态树；能让两个后代在隔离环境中改不同 Harness、跑同一组试验、比较结果并选择一个接管外部身份，才是 RSI 所需的 lineage workflow。README 的“clone itself”更像目标与底层能力概括，不能直接理解成 canonical Agent 已有一键克隆。

08 / RSI 检验

RSI 检验：能改自己不等于会变好

Exo 对 “recursive” 的定义很强：一个完整系统产生另一个带状态谱系的完整系统，而不只是用 AI 加速写代码。按这个标准，它的工程方向是对的。但“self modification”和“self improvement”之间还隔着一套实验科学。

闭环环节固定 main 中的状态达到可证明 RSI 还需要什么
观察自己源码、日志、工具结果已具备跨组件健康与退化指标
提出修改交给模型自由完成明确目标、预算与候选协议
隔离试验snapshot / fork primitive并行 clone canary 与相同初态
评价build gate盲化任务、独立 verifier、多次重复
采用模型可请求 guardian 重启外部 approval / policy gate
证明递归收益未提供跨代能力、成本和失败曲线

所以最准确的定位是 recursive self-modification platform。它把未来 RSI 研究最难补的系统原语提前做好了一部分，却还没有用公开 receipt 证明一次自改进，更不用说多代收敛。

09 / 值得借鉴

值得借鉴：把恢复能力放在智能之外

对 AgentLab、Goal Mode 或长期 Codex 任务，Exo 最值得借的不是“放开所有权限”，而是四个更克制的设计：模型上下文只是 event log 的投影；自重启由外部 supervisor 接棒；代码、执行环境和对话历史分开回滚；工具每轮重建，安装结果下一轮才生效。

这些设计都在把一个事实说清：不能要求正在被修改的那层同时负责保存唯一真相和救自己。即便不做 RSI，任何会持续几天、能改基础设施、会自动恢复的 Agent 都需要这个分层。

10 / 研究边界

研究边界：下一步该怎么验证

本文没有运行 setup.sh。它会安装 pinned Node、pnpm 与 Rust 工具链，需要 Docker 和模型 API key，属于应先确认环境变更的实验。静态研究也没有验证一次真实 self-update 的 drain、restart、event replay 和 failure recovery。

最有价值的下一步不是让它随便改自己，而是做一个受控实验：冻结 commit、模型、预算与十个任务；先跑 baseline；允许 Exo 只改 executor 上层；让每个候选在 clone sandbox 中重复运行；由外部 verifier 决定是否采用；最后故意注入一次坏改动，确认旧 supervisor 能回退。只有这张 receipt 闭合，才可以开始讨论“improvement”。

当前最需要修的不是能力，而是信任边界

把 durable state 移出 RW repo mount，底座 binary 与源码设为模型只读；给 executor 单独可写 worktree；用外部 guardian 做测试、验收和原子切换。这样 Exo 的架构主张才会从职责分层升级成部署可验证的安全性质。

一句话模型不可变历史在下，可变策略在上，guardian 负责换代。这是 Exo 最漂亮的设计。
当前判断递归自修改平台，不是已验证闭环 RSI。能改不等于会改好。
最大风险默认 RW root mount 削弱 trusted substrate。API append-only 不是文件系统不可篡改。
最该补clone canary + independent verifier + adoption gate。让旧版本拥有最后的回滚权。
