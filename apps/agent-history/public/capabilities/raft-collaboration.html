Raft 协作架构

两个 Agent 都想接下任务，人类中途说“先别发布”，旧线程却又恢复失败。Raft 的价值不只在把它们放进同一个频道，而在区分：谁收到了消息、谁看过消息、谁认领了工作，以及谁真正执行了动作。

Raft 更像现成 Agent 引擎之上的协作系统，而不是又一个独立 Coding Agent。最值得借鉴的部分，是把容易混成一句“已处理”的状态拆开；最需要小心的部分，是这些协作约束并不会自动限制主机上的所有动作。

延伸阅读：Raft 多智能体：从博客到实现。沿官方 AX 文章继续追踪 Inbox、服务端 freshness 与 CLI 草稿，补充有界上下文和读取边界的取舍。

01 / 整体架构

模型引擎负责做事，Raft 负责把工作接起来

Server 保存协作对象、处理 API 和实时通信；机器上的 daemon 启动 Agent、递送输入、代理 Raft 凭据；driver 再把统一的启动和消息需求映射到不同引擎。Web、桌面端、CLI 和 SDK 是进入这套系统的不同入口。

以熟悉的 Codex 为例，Raft 接入的是 app-server：线程启动与续接走 thread/start、thread/resume，新一轮走 turn/start，忙碌时可以通过 turn/steer 送入新输入。它没有在这里重写 Codex 的模型循环。Built-in 引擎也复用了 PiDriver。

02 / 场景推演

同一个请求，四个不能省略的问题

场景假定：人类在频道发出修复请求，Agent A 和 B 都收到；A 工作期间，人类补了一句“只提交，不发布”；之后 A 的 Codex 旧线程无法续接。下面是源码合同推演，不是实际运行记录。

时刻对应机制还不能保证什么
A、B 同时接活先 claim；服务端条件更新决定认领结果失败者一定不会直接改文件
新限制已经到达发送等协作动作前检查目标消息的可见性限制已被理解，或所有 shell 动作被阻止
旧线程续接失败特定错误可新建线程并注入恢复通知旧上下文全部保留，外部动作不会重做
A 汇报修复完成通过 raft CLI 发消息，任务按规则进入审核消息成功即代表代码正确或人类已验收

这四步分别对应可见性、归属、恢复和验收。把它们都压成一个“Agent 在线 / 已完成”状态，界面会简单，出错后却很难知道该从哪里恢复。

03 / 消息可见性

消息到了，不代表模型看过

agentInboxStateMachine 不是只有一个 unread 计数。它处理具体目标下的 pending messages、模型已见记录和序号边界。对于 send、task_claim、task_update，存在尚未看过且带有可解析边界的消息时，可以先返回 local_hold，把新上下文交回执行者，而不是立即转发动作。

为什么不能简单取最大的已读序号？因为模型可能看过一条新消息，却漏了前面的一条。上游测试专门覆盖了“已见的新消息不能越过更老的未见消息”。这说明实现关注的是模型实际获得哪些内容，而不只是网络收包顺序。

04 / 任务认领

数据库能仲裁任务，但不能替执行者锁住文件

这次能看到后端实现，而不只是“请先认领”的 Prompt。canonical task 的更新同时检查 revision 与可认领条件。成功时写 assignee、递增 revision，并让 todo 进入 in_progress；另一位执行者拿着旧 revision 再写，就不会悄悄覆盖归属。

但认领锁管的是同一条 task 记录。两个 Agent 各自创建一条重复任务，或失败者绕过协作命令直接写同一目录，都需要其他约束。任务锁、worktree 隔离和外部系统幂等键解决的不是同一个问题。

任务卡片的修订还有另一条值得借鉴的路径：在事务内重新检查成员资格，用 revision-CAS 更新，并追加修订事件。它能避免基于旧卡片的静默覆盖，也避免把消息正文里的名字当成修改权限。这里只确认 amend 路径，不把它推广为所有任务动作都有完全相同的事务保证。

05 / Prompt 与工具

把协作协议放进指令，但保留引擎自己的能力

Raft 的 standing prompt 包含身份、机器环境、启动顺序、通信规则和记忆要求。普通 assistant 文本不作为面向同事的交付渠道，Agent 要通过 raft message send 发出结果。这里“模型生成答案”和“频道收到回复”是两件事。

CLI 覆盖消息、任务、附件、提醒和手册等协作动作。它没有宣称接管一切能力：本地 CLI、runtime 原生工具、MCP 和浏览器仍可以独立工作。于是本文不把 CLI 命令族数当成模型工具数，也不把静态 Prompt 写成实际请求捕获。

对于 Codex，Raft 通过 developerInstructions 追加指令，而不是用 baseInstructions 替换基础指令。优点是保留原引擎习惯；代价是必须验证两层规则如何共同生效，尤其是压缩之后。源码自己也为这点保留了验证说明。

06 / 记忆与恢复

新线程能继续工作，不等于旧线程已经恢复

Raft 的文件记忆并不神秘：初始化持久工作目录，创建 notes/，只在 MEMORY.md 不存在时写入初始内容。Prompt 再要求把它当作恢复索引。这条路径容易审计，但记忆是否及时、准确，仍取决于执行者如何维护。

Codex 续接错误被分成不同类别：缺少 rollout 或已有 active writer，可以走 fallback_fresh_thread；权限拒绝与未知错误保留为终止错误。新线程会收到恢复说明，要求从 Raft 历史和本地记忆找回工作，不能假定旧 Codex 上下文已经加载。

这种诚实的降级比“无缝恢复”更有用。后续实验必须检查：上一轮是否已提交代码、是否已调用外部服务、旧 writer 是否还活跃。否则换一个线程 ID 并没有解决重复执行，只是换了执行入口。

07 / 权限边界

凭据代理不是主机沙箱

本地代理先校验注册 token，再把目标 URL 的 origin 与注册服务器比对，随后由 daemon 附加上游 apiKey 和 Agent 身份。这能把 Raft API 凭据转发收进一个具体入口。

执行引擎是另一条边界。Codex driver 明确请求 approvalPolicy: never 和 danger-full-access；Claude 启动参数也包含权限绕过。这适合无人交互执行，但不能据此认为频道权限会限制宿主文件与网络。

约束层主要对象不能替代
Raft 协作权限平台内身份、频道与动作宿主文件和网络访问控制
本地凭据代理向注册服务器转发 API 请求同机进程隔离与完整凭据审计
任务与消息状态机认领冲突和部分动作的新鲜度全局 shell 授权与业务幂等
OS / 容器 / 运行账号实际执行资源和权限模型理解、任务验收与行为质量

部署建议：首次验证使用独立低权限环境和测试凭据。不要因为 UI 里有 scope 设置，就把 Agent 放进保存生产密钥的日常账号中。这是根据启动配置得出的工程建议，不是漏洞复现或安全认证。

08 / 工程取舍

值得带走的是状态区分，不是更多协作口号

  • 可见性有独立记录。到达、进入上下文、执行动作分开后，恢复和排障才有落点；但要保留绕过与缺失边界，不能把产品状态说成认知保证。
  • 复用成熟引擎。Driver 保留已有工具和模型生态；相应地，版本兼容、错误分类、压缩和忙碌投递都需要逐引擎验证。
  • 持久身份不绑定某个线程。线程丢失后仍有工作目录与协作历史；能否安全续做，则需要独立的副作用对账。
  • 数据库保证与行为要求分开。认领 CAS 是实现；先认领再动手是规则。两者缺一不可，但不能互相冒充。

以上是基于前述代码的工程归纳。它足以解释为什么 Raft 应归入协作基础设施，却不足以给出“多 Agent 一定更快、更省钱”的结论。
