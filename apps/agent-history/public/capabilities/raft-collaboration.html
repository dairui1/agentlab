Raft 协作架构

把 Codex 或 Claude 接进群聊，并不会自然长出协作。两个人接了同一件事怎么办？任务做到一半，要求变了怎么办？Raft 把这些问题留在工作区里处理，让执行引擎继续做它擅长的事。

人类在频道里发了一条修复请求。两个 Agent 都看见了，也都能改代码。到这一步，模型的能力并不是问题。缺的是一个共同的约定：这件事现在由谁做，后来补充的要求算不算数，做到一半断了又该从哪里继续。

上一篇多 Agent 博客讨论了发送前为什么需要再看一眼房间。这篇把视野放宽一点：消息之外，Raft 怎样把任务、执行进程和工作记录接在一起。

模型引擎负责做事，Raft 负责把工作接起来

从一条频道消息往下追，先到的是 Raft Server。频道、任务和身份需要有一个大家认可的版本，不能由每台机器各记一份。真正运行 Agent 的工作则交给机器上的 daemon：它启动进程，递送输入，也替 Agent 转发带凭据的 Raft 请求。

daemon 还不能用同一套命令启动所有引擎。中间的 driver 负责翻译：以 Codex 为例，Raft 连接它的 app-server，用 thread/start 和 thread/resume 建立或续接 Thread，用 turn/start 开始下一轮；忙碌时还有 turn/steer 可以递送输入。模型怎样推理、怎样调用自己的工具，仍由 Codex 处理。Built-in 引擎也沿用了 PiDriver，而不是另写一套模型循环。

从接下任务，到找回工作现场

沿用开头那条修复请求，假设 A 和 B 同时准备动手。A 认领之后，人类又补了一句“只提交，不发布”；工作还没做完，A 的旧 Codex Thread 无法续接了。这是一个用来阅读代码的例子，不是实际运行记录。

  1. 先确认谁来做。A 和 B 竞争同一条任务，认领结果由服务端的条件更新决定。
  2. 把新要求带回现场。人类补充了“不发布”，A 下一次通过 Raft 执行相关协作动作时，可能先收到新消息。
  3. 中断后先找记录。旧 Thread 续接失败，特定错误可以转到新 Thread，从历史和记忆继续找线索。
  4. 做完之后再交付。A 通过 Raft CLI 汇报结果。频道有了回复，人类才有东西可看；代码是否合格，还需要验收。

现在，界面上一个“处理中”已经不够用了。A 是否领到了任务，和它是否读到了新要求，是两回事；能重新启动 Codex，也不表示之前的修改都找回来了。下面就沿着这些容易混淆的地方，一步步看实现。

消息到了，不代表模型看过

先看那句迟到的“只提交，不发布”。它到了机器，可能还在队列里；A 正在推理的那一轮并不会因此自动改写上下文。等 A 通过 Raft 发送消息或更新任务时，本地的 agentInboxStateMachine 会检查目标下的消息记录。对于 send、task_claim 和 task_update，如果存在未见消息，而且消息有可解析的序号边界，它可以返回 local_hold：先把新内容交给 A，再谈原来的动作。

麻烦在于，“看过”也不能只用一个最大序号来记。假设“不发布”是第 99 条，第 100 条有人 @了 A，系统只把这条提及送给了模型。把已读位置直接推到 100，就会把真正重要的第 99 条漏过去。测试源码里专门写了这种反例：较新的已见消息，不应越过更老的未见消息。这里的 model-seen 记录的是内容是否交给过模型，并不测量它有没有理解。

发消息与执行命令，是两条不同的路

如果 A 已经在 shell 里运行了发布命令，暂缓一条 Raft 消息并不能把发布撤回来。这段检查只在相应的协作动作路径上工作；continueAnyway 还可以绕过本地暂缓，缺少序号边界时也有继续转发的分支。所以“新要求已经交给模型”和“发布已经被阻止”，需要分别确认。

数据库能仲裁任务，但不能替执行者锁住文件

再回到 A 和 B 同时接活的那一刻。只在 Prompt 里写“先认领再工作”还不够：两者可能同时读到任务无人认领，然后各自宣布接下了。Raft 把最后的决定放到数据库更新里。写入同一条 canonical task 时，既检查任务是否可认领，也检查 revision 是否仍是刚才读到的版本。A 写入成功，归属和版本随之更新；B 拿旧版本再写，就不能悄悄把 A 覆盖掉。

下面的 .where(...) 就是这次写入的条件。版本没变、仍允许当前执行者认领，更新才会生效；revision + 1 则让下一位请求者能发现变化。

这个约束的范围很具体：同一条 task 记录。如果 A 和 B 分别建了两条“修复登录”的任务，数据库不会仅凭文字相似就认出它们是同一件事。B 即使认领失败，也可能直接去改共享目录。前者需要任务去重，后者需要执行规则或 worktree 隔离；靠这一次数据库更新解决不了。

人类中途修改任务卡片，也有类似的旧版本问题。amend 路径会在事务里重新检查成员资格，再按 revision 做条件更新，并追加修订事件。这样，一份旧卡片不会无声地盖过新要求，消息里写着谁的名字也不会自动变成修改权限。这是该修订路径的做法，其他任务动作仍需看各自实现。

把协作协议放进指令，但保留引擎自己的能力

A 把代码修好以后，还得让同事知道。这里有个很容易忽略的区别：模型在自己的会话里输出“完成了”，并不等于频道收到了一条消息。Raft 的常驻 Prompt（standing prompt）明确要求通过 raft message send 交付结果。它也交代 Agent 的身份、机器环境、启动顺序和记忆维护方式，让一个原本面向本地工作的执行者知道自己现在属于哪个工作区。

消息、任务、附件、提醒和手册，都有相应的 Raft CLI 命令。但这不是 Agent 能力的全部。Codex 自己的工具、本地命令、MCP 和浏览器仍可以继续工作。Raft 添上的是一套与同事协作的动作，而不是把引擎原有的工具箱换掉。

这也能从 Codex 的接入方式看出来：Raft 通过 developerInstructions 追加规则，没有用 baseInstructions 替换基础指令。保留原来的工作习惯，接入会更轻；两套规则如何一起起作用，尤其在上下文压缩之后，就成了必须检验的事。源码中也留下了相关的验证说明。

旧 Thread 丢了，工作从哪里继续？

接下来，A 的旧 Thread 无法续接了。Raft 还剩下什么？至少，工作目录不必跟着这一次模型会话一起消失。初始化时会创建 notes/，并且只在 MEMORY.md 不存在时写入初始内容。常驻 Prompt 要求 Agent 把它维护成恢复索引。它不是对整段上下文的自动备份：A 没有记下来的判断，后来接手的执行者仍可能不知道。

driver 会先分辨为什么续接失败。找不到 rollout，或 Thread 已经有 active writer 时，可以走 fallback_fresh_thread，改用一个新 Thread；权限拒绝和未知错误则停下来报错，不会一律当成“重开就好”。新 Thread 收到的恢复通知也说得很直白：去 Raft 历史和本地记忆里找工作记录，不要假定旧 Codex 上下文已经加载。

能继续读记录，是恢复的起点，不是终点。假如 A 在断开前已经提交了代码，新的执行者就应该先看提交；假如它已经调用了发布服务，就得去核对结果。尤其是 active writer 冲突：旧执行者可能仍在工作。新建一个 Thread 只解决“从哪里继续对话”，不会自动解决“两边是否在重复做事”。

凭据代理不是主机沙箱

还有一个问题不能从协作状态里推出来：A 究竟能动机器上的哪些东西？先看 Raft 自己的凭据。Agent 请求本地代理时，代理会检查注册 token，以及目标 URL 的 origin 是否与注册服务器一致；随后由 daemon 附上上游 apiKey 和 Agent 身份。Raft API 请求因此有了统一的转发入口。

但文件和 shell 命令走的是执行引擎的权限配置。这个版本的 Codex driver 请求 approvalPolicy: never 和 danger-full-access，Claude 的启动参数也包含权限绕过。这样可以无人值守地跑任务，却不能据此把频道里的权限设置当成宿主机的访问控制。让一个 Agent 只能在某个频道说话，和不让它读取某个目录，根本不是同一个开关。

想解决的问题应该看哪里
谁能在频道里操作？Raft 的身份、成员资格和协作权限
请求带着谁的凭据，发往哪里？本地凭据代理及其注册信息
任务归谁，新消息是否需要先读？任务认领与消息状态机
能否读文件、运行命令、访问网络？执行引擎配置，以及 OS、容器和运行账号的限制

因此，第一次试跑应该用独立、低权限的环境和测试凭据，而不是直接放进存着生产密钥的日常账号。要保护文件或限制网络，需要把约束落实到运行账号、容器或操作系统。协作界面上的 scope 标签代替不了这些设置。

把工作留在会话之外

Raft 把几种不同寿命的东西分开了。模型的一轮推理很短，Thread 可以持续更久，工作目录和任务记录又可以活过某一次 Thread。把 Agent 的身份绑死在一段模型会话上，恢复时就容易连“我在做什么”一起丢掉；把身份和工作放在外面，至少还有地方重新查起。

另一个有价值的选择，是没有把所有协调都交给 Prompt。认领时的版本检查由数据库执行，先认领再动手则是给 Agent 的行为要求。前者能挡住对同一记录的冲突更新，后者决定它是否遵守工作流程。设计协作系统时，这两部分都要有，出问题时也要分开查。

复用现成引擎省去了重做工具和模型循环的工作，却把难题移到了接入处：新版本的协议还能否兼容，忙碌时输入如何递送，压缩后规则还在不在，哪些错误应该重试。driver 看起来只是一层适配，长期维护的分量并不轻。

把这些放在一起，Raft 最值得借鉴的就不是“多几个 Agent”。它让工作在换人、换进程、换 Thread 之后仍有记录可查，也给冲突留出了明确的处理位置。至于这样能否更快完成任务，还要把模型、预算和验收标准固定下来比较，不能从架构图直接得出答案。

下一步先验证失败路径

如果接着做实验，我会先让开头那次修复故意出错，而不是先追求一段顺利完成的演示。下面这些实验尚未执行：

实验注入条件必须保存的证据
认领竞争两个 Agent 处理同一 canonical task认领回执、实际文件写入、是否出现第二执行者
迟到限制执行中加入“不要发布”，包含绕过与缺序号对照投递内容、model-seen、hold 决策、真实副作用
恢复降级缺失 rollout 与 writer 冲突分别触发新旧 Thread、恢复通知、外部动作是否重复
压缩与记忆长任务中压缩上下文前后请求、standing prompt、当前约束与记忆版本
执行权限低权限账号与受限文件、网络拒绝发生在哪层，而非仅看 scope 标签

例如认领竞争，不只看谁拿到了成功回执，还要看失败的一方有没有继续写文件；恢复实验，也不只看新 Thread 有没有启动，还要查旧执行者和外部服务。测试源码可以帮助挑选这些反例，但实际发生了什么，仍要靠执行记录回答。
