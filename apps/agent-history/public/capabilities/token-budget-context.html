先记住一句话在本页固定的 Codex 0.151.0 中，TokenBudget 已随稳定版分发，但仍默认关闭，不是该版本的默认 compaction。

长任务会遇到一个问题：模型一次能看到的消息有上限。通常的办法是把旧对话浓缩成摘要，再继续聊。Codex 的 TokenBudget 尝试另一条路：换掉当前消息窗口，进度另存，原始记录需要时再查。

关键不在于“丢掉对话”，而在于换窗以后靠什么继续。下面先解释这个分工，再看实现经过了哪些版本。研究固定到 2026-08-31 核验的 0.151.0，不代表今天所有 Codex 会话的配置。

01 / 先给答案

先给答案：换了窗口，怎样接着工作

如果正在修 OAuth 超时，新窗口至少需要知道：改到了哪个文件、测试还差什么、用户禁止改动什么。TokenBudget 不要求把全部旧消息再浓缩一遍，而是让模型把这些工作状态写进可读写的 notes，并给重要原文留下查询地址。

目标：修复 OAuth 登录超时。 决定：保留 token refresh API，只调整客户端 retry。 进度：auth/session.rs 已修改；login_test 还有 2 个失败。 原文地址：用户约束 → window 01… / item a83f 失败测试 → window 01… / item e912 下一步：检查 reconnect 路径。

这是笔记格式示例，不是实测记录。新窗口可从这些进度继续；需要核对用户原话或测试输出时，再通过只读 history 找对应条目。笔记会写漏，查询也需要模型知道该找什么，因此这套办法没有自动保证“不丢约束”。

实现已经随稳定版分发：主动换窗从 0.140.0 开始，手动与自动压缩接到换窗路径从 0.143.0 开始，notes/history 扩展从 0.150.0 开始。但本页固定的 0.151.0 仍把它标为 UnderDevelopment、默认 false；当时本机 CLI 0.149.1 也未开启。

本次核验的可用性

代码已发布，但不是固定 0.151.0 的默认压缩方式。未开启 TokenBudget 的会话仍会走原有摘要路径。版本够新，也不自动说明当前任务已经启用。

02 / 两套路径

没有全局取消：两套 compaction 并存

同样执行 /compact，不同配置可能做不同的事。任务入口 CompactTask 先检查 TokenBudget 开关：开启就进入新换窗路径；没开启，仍按模型提供商能力和 RemoteCompactionV2 开关，在远端 V2、远端 V1 或本地摘要之间选择。旧摘要实现没有被全局删除。

摘要路径

用浓缩后的记录替换旧消息

到阈值后，在本地或远端压缩，生成摘要或由服务器封装的压缩条目，再交给模型。旧要求是否继续影响回答，要看摘要或保留的尾部消息有没有留下它。

触发/compact 或自动阈值
核心动作summarize / compact response
默认状态仍在使用
换窗路径

新开消息窗口，再查询需要的旧记录

进入 TokenBudget 分支后，不再为旧对话请求摘要，而是分配新的窗口 ID，重新加入标准初始上下文和当下环境状态。后续可读 notes，再按需查 history。

03 / 硬切窗口

硬切窗口：换掉模型当前看到的消息

“硬切”切的是下一次请求里给模型看的内容。旧用户消息、回答和工具输出不再整批发送，新请求从标准初始上下文和当前环境状态起步。0.143.0 的手动与自动入口都调用 start_new_context_window，明确跳过模型或服务器的对话摘要。

客户端生命周期被刻意保留：PreCompact 与 PostCompact hook 仍会运行，ContextCompaction item 也照常发出 started/completed。因此从 app-server 或 UI 的表面事件看，它仍然叫 compaction；仅凭这个 item，不能判断底层究竟做了 summary 还是 fresh window。

04 / 三层状态

三层状态：窗口、notes 与 history

三处数据回答三个问题：当前窗口决定模型这次直接看见什么；notes 保存接着工作要知道什么；history 提供旧记录到哪里查。notes 由模型主动维护，可跨窗口保存；history 只读，来自后端，查询结果是最终一致的。旧记录可查，并不表示它一直在当前请求里。

01 / ACTIVE

Context Window

速度最快，也最短命。只放当前推理真正需要的工作集。

会被 replacement 整体换掉
02 / CHECKPOINT

Notes

保存目标、决定、进度、关键引用与下一步。模型能读写。

跨窗口生存，但仍可能写漏
03 / RECOVERY

History

列窗口、列 item、定点读取或按字面搜索旧记录。

只读、最终一致，不常驻 prompt
notes 不是 history 的摘要副本

好的 checkpoint 应该保存“现在处于什么状态”和“哪里能找回原始事实”，而不是试图把十几万 token 再压成一篇小作文。这样窗口 B 不必先吞回窗口 A 的全部内容，遇到具体疑问时再查对应 item。

05 / 定点恢复

定点恢复：window_id + item_id

history.read_item 的参数要求非常具体：完整 window_id 加目标 item_id。不知道 ID 时，可以先 list windows、list items，或按 role、tool namespace、tool name 与字面内容搜索。它恢复的是一条有地址的记录，不是把整个旧窗口重新塞回 attention。

前面的笔记示例留下了两种地址：用户约束和失败测试。决定与进度可以直接读笔记，原始要求和关键输出则回读对应条目。地址本身不会判断重要性，模型仍需决定什么值得记、何时需要查。

06 / 版本地图

版本地图：三个能力分三次落地

0.140.0

模型获得换窗出口

PR #27488 加入 direct-model-only new_context。窗口没价值时，模型不用先花 token 做 summary。

0.143.0

compact 生命周期换了内核

PR #29743 把手动与自动 compaction 都接到 fresh-window replacement；0.142.x 稳定 tag 尚无该模块。

0.150.0

notes/history 接住连续性

PR #39827 加入私有 notes 与只读 history 扩展，让新窗口不只剩一个干净 prompt。

0.151.0

代码继续迭代，默认值没变

history ID 合同和 notes 一致性语义继续调整；TokenBudget 仍是 UnderDevelopment / false。

07 / 可用性边界

可用性边界：发布不等于能直接用

即使二进制版本够新，完整链路也不只一个总开关。0.151.0 的配置结构把 token_budget.enabled、use_history_notes_extension、提醒阈值、guidance message 与 fallback buffer 分开；history/notes 扩展还要求 OpenAI provider 和 Codex backend 认证。

你看到的现象能说明什么还不能说明什么
版本 ≥ 0.143.0硬切实现已在二进制源码范围内当前 thread 已启用 TokenBudget
/compact 完成compaction lifecycle 跑完底层一定生成了 summary
版本 ≥ 0.150.0history-notes 扩展代码已分发provider、认证与子开关都满足
旧 transcript 仍在durable record 可能可恢复模型当前仍在 attention 它
notes 写得很完整新窗口有较好 checkpoint原始约束已被无损保存

还有一个容易混在一起的数字：修复图片在 compaction 前被重复保存，和 TokenBudget 取消摘要，是两条不同优化。前者可能减少图片型任务的重复上下文成本；后者省掉摘要请求、却会增加 checkpoint 与按需回读成本。没有配对 usage 数据，不能把某个“约 10%”直接算到这条新架构头上。

08 / 结论与边界

结论：上下文不再等于全部记忆

传统 compaction 的基本假设是：当前 prompt 快满了，就把过去浓缩成一份 replacement summary，让模型继续把它当作记忆。TokenBudget 的假设更激进：当前 prompt 只是一个会过期的工作窗口，真正需要长期保存的是任务状态和可寻址事实。模型应该提前知道预算、及时做 checkpoint、允许窗口被整体替换，再从历史里按需恢复。

不是把旧窗口压得更小，而是承认旧窗口可以被丢掉。连续性改由 checkpoint + addressable history 承担

这更像长期任务基础设施，而不只是聊天记录压缩。但在本页固定的 0.151.0 中，它仍是默认关闭的开发中能力；所读材料没有完整的后端 history 保留合同，也没有真实 token 节省和完成率的公开对照，checkpoint 质量仍依赖模型。准确的结论是：这份稳定版已包含无摘要、可换窗、可查询旧记录的实现，但不能据此说所有 Codex 会话已经采用它。本文没有核验此后的默认开关或产品 rollout，不预测它何时成为默认。

研究边界

本页核对的是公开源码、tag 与本机 feature 状态。它没有替 OpenAI 承诺 rollout 时间，也没有把 private notes/history 当作永久存储，更没有用单次观察替代长程任务实验。待验证项保留在专题证据库。
