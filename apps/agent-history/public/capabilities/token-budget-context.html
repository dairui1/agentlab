先记住一句话TokenBudget 不是 Codex 当前默认 compaction；它是已经随稳定版分发、但仍默认关闭的新实现。

这次变化最容易被两个说法带偏：一个是“Codex 已经取消 Compaction”，另一个是“这只是换了个摘要算法”。都不准确。更精确的说法是：Codex 保留了 compaction 的命令、事件与 hook 生命周期，但在 TokenBudget 分支里，replacement 已经从“旧消息的 summary”变成“新的 canonical context window”。

01 / 先给答案

先给答案：上了，但不是默认路径

代码已经进入 Codex 的稳定发行版。模型主动请求新窗口的 new_context 最早出现在 0.140.0；手动 /compact 与自动 compaction 在 TokenBudget 下统一改成硬切窗口，最早出现在 0.143.0；用来跨窗续接的 notes/history 扩展，最早进入 0.150.0。

但“随稳定版发布”不等于“所有会话已经在用”。在当前核验的最新稳定版 0.151.0 里，TokenBudget 仍标为 UnderDevelopment，默认值还是 false。这台机器安装的 Codex CLI 0.149.1 也报告同样的 feature 状态，配置文件没有主动开启它。

准确的发布结论

实现已发布：是。完整链路从哪个版本具备：0.150.0。现在是不是默认新压缩方式：不是。普通会话还能不能做摘要 compaction：能，而且默认配置仍会走传统 selector。

02 / 两套路径

没有全局取消：两套 compaction 并存

CompactTask 的第一道判断就是 Feature::TokenBudget。开启时，任务交给 compact_token_budget；没有开启时，仍会根据 provider capability 和 RemoteCompactionV2 在 remote V2、remote V1 与 local summarization 之间选择。也就是说，TokenBudget 是一条实现分支，不是把旧代码一刀删掉。

Summary replacement

把旧对话浓缩成新的 active history

到阈值后调用 local 或 remote compaction，生成 summary 或 opaque compacted item，再把 replacement history 装回当前 thread。旧消息是否还能影响模型，取决于摘要或保留尾段里有没有留下它。

触发/compact 或自动阈值
核心动作summarize / compact response
默认状态仍在使用
Fresh window replacement

丢掉旧 prompt，重建标准初始上下文

同样的命令和阈值进入 TokenBudget 分支后，不再请求模型或服务器生成 conversation summary，而是安装一个新的 window ID，并重新注入 canonical initial context 与当下 world state。

触发new_context / compact / auto
核心动作start_new_context_window
默认状态关闭
03 / 硬切窗口

硬切窗口：名字不变，replacement 变了

0.143.0 的注释写得很直白：TokenBudget compaction 会跳过 model/server summarization，改为安装 fresh context window。手动与自动入口最后都汇合到 start_new_context_window。旧 user、assistant 与 tool output 不再整批进入下一次 model request；新 prompt 只从标准注入内容与当前 world state 重新起步。

客户端生命周期被刻意保留：PreCompact 与 PostCompact hook 仍会运行，ContextCompaction item 也照常发出 started/completed。因此从 app-server 或 UI 的表面事件看，它仍然叫 compaction；仅凭这个 item，不能判断底层究竟做了 summary 还是 fresh window。

04 / 三层状态

三层状态：窗口、notes 与 history

把这套系统理解成“RAM、checkpoint、cold archive”很有帮助，但要记得它只是类比。当前 context window 是模型正在 attention 的工作集；notes 是模型主动维护、可跨窗口生存的私有工作笔记；history 是后端提供的只读、按需查询的旧窗口记录。

01 / ACTIVE

Context Window

速度最快，也最短命。只放当前推理真正需要的工作集。

会被 replacement 整体换掉
02 / CHECKPOINT

Notes

保存目标、决定、进度、关键引用与下一步。模型能读写。

跨窗口生存，但仍可能写漏
03 / RECOVERY

History

列窗口、列 item、定点读取或按字面搜索旧记录。

只读、最终一致，不常驻 prompt
notes 不是 history 的摘要副本

好的 checkpoint 应该保存“现在处于什么状态”和“哪里能找回原始事实”，而不是试图把十几万 token 再压成一篇小作文。这样窗口 B 不必先吞回窗口 A 的全部内容，遇到具体疑问时再查对应 item。

05 / 定点恢复

定点恢复：window_id + item_id

history.read_item 的参数要求非常具体：完整 window_id 加目标 item_id。不知道 ID 时，可以先 list windows、list items，或按 role、tool namespace、tool name 与字面内容搜索。它恢复的是一条有地址的记录，不是把整个旧窗口重新塞回 attention。

Goal: 修复 OAuth 登录超时。 Decision: 保留 token refresh API，只调整客户端 retry。 Progress: auth/session.rs 已修改；login_test 还有 2 个失败。 References: 用户约束 → window 01… / item a83f 失败测试 → window 01… / item e912 Next: 检查 reconnect 路径。

这个结构的关键不是格式好看，而是把两类信息拆开：决定与进度直接放在 notes，容易继续；原始要求与关键工具输出留地址，需要时精确回读。指针本身不会理解语义，模型仍要判断什么值得记、什么时候值得查。

06 / 版本地图

版本地图：三个能力分三次落地

0.140.0

模型获得换窗出口

PR #27488 加入 direct-model-only new_context。窗口没价值时，模型不用先花 token 做 summary。

0.143.0

compact 生命周期换了内核

PR #29743 把手动与自动 compaction 都接到 fresh-window replacement；0.142.x 稳定 tag 尚无该模块。

0.150.0

notes/history 接住连续性

PR #39827 加入私有 notes 与只读 history 扩展，让新窗口不只剩一个干净 prompt。

0.151.0

代码继续迭代，默认值没变

history ID 合同和 notes 一致性语义继续调整；TokenBudget 仍是 UnderDevelopment / false。

07 / 可用性边界

可用性边界：发布不等于能直接用

即使二进制版本够新，完整链路也不只一个总开关。0.151.0 的配置结构把 token_budget.enabled、use_history_notes_extension、提醒阈值、guidance message 与 fallback buffer 分开；history/notes 扩展还要求 OpenAI provider 和 Codex backend 认证。

你看到的现象能说明什么还不能说明什么
版本 ≥ 0.143.0硬切实现已在二进制源码范围内当前 thread 已启用 TokenBudget
/compact 完成compaction lifecycle 跑完底层一定生成了 summary
版本 ≥ 0.150.0history-notes 扩展代码已分发provider、认证与子开关都满足
旧 transcript 仍在durable record 可能可恢复模型当前仍在 attention 它
notes 写得很完整新窗口有较好 checkpoint原始约束已被无损保存

还有一个容易混在一起的数字：修复图片在 compaction 前被重复保存，和 TokenBudget 取消摘要，是两条不同优化。前者可能减少图片型任务的重复上下文成本；后者省掉摘要请求、却会增加 checkpoint 与按需回读成本。没有配对 usage 数据，不能把某个“约 10%”直接算到这条新架构头上。

08 / 结论与边界

结论：上下文不再等于全部记忆

传统 compaction 的基本假设是：当前 prompt 快满了，就把过去浓缩成一份 replacement summary，让模型继续把它当作记忆。TokenBudget 的假设更激进：当前 prompt 只是一个会过期的工作窗口，真正需要长期保存的是任务状态和可寻址事实。模型应该提前知道预算、及时做 checkpoint、允许窗口被整体替换，再从历史里按需恢复。

不是把旧窗口压得更小，而是承认旧窗口可以被丢掉。连续性改由 checkpoint + addressable history 承担

这确实更像长期任务基础设施，而不只是聊天记录压缩。但它还没有完成产品化闭环：默认开关没放开，后端 history 的保留合同不完整，checkpoint 质量依赖模型，真实 token 节省和完成率也没有公开对照。现在最合适的判断不是“Codex 已经告别 Compaction”，而是：Codex 已经把一条无摘要、可换窗、可恢复的上下文管理路径装进稳定发行版，正在等待它从开发能力变成默认产品行为。

研究边界

本页核对的是公开源码、tag 与本机 feature 状态。它没有替 OpenAI 承诺 rollout 时间，也没有把 private notes/history 当作永久存储，更没有用单次观察替代长程任务实验。待验证项保留在专题证据库。
