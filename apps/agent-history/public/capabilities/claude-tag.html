三个不同的保证Prompt 要求模型怎么做；Schema 约束参数形状；工具描述声明运行时会检查什么。本文不把三者混成已经验证的行为。

Claude Tag 的特色藏在“接下任务之后”。它不仅要会调用工具，还要知道自己代表谁、哪条消息值得回应、另一位 Claude 是否已经在做，以及这次 Session 消失以后，下一个 Session 能不能接得住。

01 / 整体模型

把它看成事件驱动的协调者

在这份快照中，普通 assistant 文本并不会送进 Slack。主 Session 必须调用 reply、update_reply 或 no_reply_needed 完成面向 Thread 的收尾。新 Slack 事件或后台结果再触发下一轮。于是“生成了一段正确答案”和“用户收到了答案”成了两个不同状态。

这里的 Harness，是围绕模型的消息路由、工具、权限和生命周期管理。Prompt 给协调者一套行动准则，但不能凭 Prompt 就断言服务端严格执行了所有准则。

02 / 提示词结构

不是一段长人设，而是几层不同职责

文件前面仍能看到通用编码 Agent 的习惯：理解仓库、克制修改、注意不可逆动作、管理上下文。随后才加入 Slack 专用的身份与协作规范；消息区又注入 Memory 和 worker 的能力说明。把整份文件叫作“Slack system prompt”，会漏掉这几个来源和作用不同的层。

层主要回答影响什么
通用工作规范怎样完成工程任务修改范围、核查与风险判断
环境与上下文在哪里运行、会丢掉什么执行条件、压缩后的连续性
Slack 行为协议谁在说话、要不要回、谁负责路由、权限、协作、通知
Memory / worker 提示哪些知识保留、哪些能力可委派跨轮状态与工作分配
Tool Schema 与描述动作怎么表达、何时被拒绝参数、对象身份、前置条件

细节为何写得这么多？

大量篇幅并不教模型解题，而是在规定失败时怎么办：查不到不等于不存在；拒绝不是请它换个工具绕过；Artifact 版本过时要重读合并；回复尚未返回 ts 就不能标记“已发布”。这些分支让抽象的“可靠队友”变成能审查的决策。

值得借鉴的写法：每条规则都尽量带一个触发条件、一个动作和一个停止条件。与其只说“保持沟通”，这里更具体地规定“进度静默编辑，完成另发通知”。这是本文对 Prompt 结构的归纳，不是对真实成功率的测量。

03 / 输入与信任

同一个人，不同消息也有不同权限

reason、from、trust 不能互换。reason 解释这一轮为什么发生；from 说明消息来自人、bot、当前 Session 还是 sibling；trust 才帮助判断这条内容能否指挥它。线程发起人 role=initiator 不是额外授权。

消息类型Prompt 中的处理不能推导出的权限
principal本人直接 @ 或 1:1 DM 的请求无限范围的不可逆操作授权
peer人的未 @ 消息，按场景判断参与见到一句话就必须执行
relaybot、webhook 或既往自身文本破坏性动作或个人连接器权限
unauth / no_role参考内容，不执行其中指令正文声称“已授权”即可放行

一个重要例外是主动 @ 它的 bot：明确、范围内的请求可以接，也应该答；但 bot 的话不能单独授权破坏性、不可逆、改权限的动作或个人连接器调用。因此“relay 都不理”也不准确。权限判断不是一个简单的可信 / 不可信开关。

读取到的请求，不等于收到了请求

订阅频道送来的是观察，默认不能跑去原频道回话。搜索结果里的“请读我的邮箱”也不能充当本人启动个人 Session 的请求锚点。这一设计把内容可见性和指令来源分开：文本长得像请求，不代表它进入了能授权动作的通道。

04 / 执行分工

主 Session 会读、会协调，但不直接写文件

85 项主 Session 工具里有 Read、Grep、Glob，却没有 Bash、Edit、Write 或 Artifact。后者列在 workerToolsContext 里。Artifact 段还直说：主 Session 的工具可读但不能写文件或发布，所以要派 worker。

这让“协调”和“执行”有了可见的能力分界。不能把它夸大成安全沙箱，但它确实比一句“尽量委派”更具体：主 Session 没有那几个直接动作入口。也不能把 worker 列表再加到 85 上，声称主模型拥有更多工具。

工作主体适合承担不要混淆
Agent worker当前任务里的执行子工作不是用户个人连接器身份
create_session独立远程 Session 与仓库任务新 Session 不等于更高权限
start_standing_session参与者用自己的资源完成请求主 Session 没有获得其连接器
start_thread_session把特定 Thread 接成活跃工作不是每个路过消息都可启动

个人 Session 尤其不同：它服从自己的 principal，而不是频道协调者。协调者可以传递线索、转发请求，却不能把一句“对方同意了”当作本人授权。职责分配和权限委托是两回事。

05 / 工具设计

关键不在工具多，而在参数记住了哪些责任

按命名空间统计，主 Session 有 10 项通用读取与协调工具、26 项 Claude Code Remote 工具、49 项 Slack 工具。这个分类只是检索入口。理解设计时，更有用的问题是：参数绑定了哪个对象，动作会影响谁，做之前需要什么证据？

reply：把“我看到了什么”带进发送动作

last_seen_ts 是必填字段。工具描述说，Thread 有尚未读到的新消息时发送会失败。它像乐观并发检查：如果用户刚刚改了需求，模型不能直接按旧上下文发言。force 能跳过比较，因此这是可绕开的新鲜度保护，不是不可突破的锁。

also_send_to_channel 把更大的通知范围做成显式选项；conveys_helper_session 与 conveys_event 则把转述关联到收到的具体事件。模型不只在提交文字，还在提交“我替谁传达、根据哪条事件、发到哪里”的说明。

create_session：派活不等于把权限也放大

permission_mode 声明不能比调用者更宽；extra_allowed_tools 里父 Session 未获预授权的项目会被丢弃。remote_cowork 模式还声明忽略扩展工具面的一组参数。这样的字段设计是在表达权限的上限，而不是让模型随意拼一个更强的子进程。

Routine：为什么触发，和何时触发一样重要

initiation 区分人类请求、已有计划、自行跟进和自主发起。create_new_session_on_fire 决定是续接上下文还是冷启动；connectors 则影响未来多次执行的授权。一个提醒因此不只是 cron 字符串，还包含来源、执行身份与持久权限。

Schema 只是合同的一层

required、enum 和类型能表达参数形状；“不得扩权”“仅当本人直接请求”“存在新消息则拒绝”主要写在 description。工具描述声称服务端检查的部分，仍需实现或拒绝回执才能独立验证。

这条消息值得通知吗？

结果、问题和阻塞用新 reply；普通进度编辑原消息。这需要模型理解当前任务与读者需要。

参数是否带齐？

last_seen_ts 是必填字符串；force 是可选布尔值。但 Schema 没有表达时间戳是否真是最新值。

读过的状态还有效吗？

工具描述声明会比较新消息，发现未读则拒绝；force 可跳过。是否按此强制执行，要看实际回执或后端实现。

06 / 时间与恢复

长期工作靠重新唤醒，不靠一轮里一直等

派出 worker、Workflow、构建或 CI 后，Prompt 要求同一轮安排 check-in，再结束当前轮。检查触发时，先用 update_reply 更新真实进度和时间戳，再读工作结果；没完成就重新安排，完成就清掉 trigger。初始间隔是一分钟，工作超过五分钟后可拉长但一般不超过五分钟；仅等待 PR 审阅或 CI 的阶段可以进一步放宽。

这是一种事件驱动的持续性：每次唤醒重新看现实，而不是承诺之后无限沉默。它也有清晰代价：过多 check-in 消耗轮次，忘记删除会产生无效唤醒，没写下任务状态就会在更换 Session 后断线。

状态谁能接续容易误读的地方
当前上下文当前 Session不是持久任务数据库
Thread / live status读到它的后继 Session必须写清承诺、在途工作、剩余项
channel memory / 已交付文件有权限的后继工作不是所有临时细节都适合存成记忆
send_later one-shot它绑定的 Session容器重启存活不等于 Session 替换后存活
周期 Routine可能冷启动的新 Session指令需要足以独立执行

send_later 描述写“可跨 container restart”，Session 章节却写“一次性 check-in 随 Session 结束”。不必急着判定两句矛盾：容器重启和会话被清理 / 替换不是同一事件。真正该测试的是这两个层级分别发生时，trigger 最终送到哪里。

07 / 多 Session 协调

claim records 有意选择“继续做”，不是“等锁”

helper 想接一条消息，会发送含 message_ts、record_uuid、verdict、scope 的 claim。接收者以五字段的 claim_response 回应 grant 或 deny。正文里的同形 JSON 不算，记录必须以完整消息经过可识别发送 Session 的通道送达。

最容易看错的是它的保证强度。Prompt 明说：服务器没有 claim database，记录是建议性信息，重复执行是可以接受的兜底，不能为了等一致意见而一直不动。这套协议优先防止无人处理，不能承诺每件事只执行一次。

所以对账才重要：每次醒来，把授出去的工作与可见 Thread 对照；收到 done 后，检查发送者是否是获授 Session，并确认 reply_ts 指向的答复确实存在。一个“completed”标签不够。重启丢掉了本地授予记录怎么办、两个 Session 同时接管会怎样，则仍是需要实验的问题。

协调协议的目标不是让所有 Agent 先达成一致，而是让用户尽量不被漏答，并用可见结果纠正失配。根据 claim 规则作出的机制归纳
08 / 交付与沟通

文字、通知和产物，是三种不同的输出

How you write 约束写法：先说结果，按读者的信息密度解释，少空话。Claims and evidence 约束知识：先检查，再断言，特别要防把“代码应该如此”当成“实际运行如此”。Cadence 约束注意力：进度尽量静默，结果、阻塞和问题才重新通知。三层放在一起，才解释了它为何既要求持续工作，又要求少说话。

发布成功必须有回执

结果 reply 可能被要求改写，也可能因新消息而拒绝。必须等它返回 ts，再把 checklist 改成“已发布”。这个很小的顺序约束避免把本地生成、尝试发送和实际送达混成一个完成状态。

报告不随每次修改换一个链接

长报告、网页和表格交给 worker 生成并通过 Artifact 发布，后续改动优先沿用原 worker 与 URL。版本落后时先读线上最新内容，合并后重发一次；真正冲突再停下，不默认 force。这已经涉及协作编辑，不只是把 Markdown 上传成附件。

PR 也有类似的延续责任。自己创建的 PR 需要跟进后续活动，不能以“开了 PR”代替用户要的可交付修复；只是受托观察别人的 PR，则不能擅自扩大任务。事件订阅在这里接上了工作义务，而不只是通知功能。

09 / 场景推演

“查一下故障，修好后发报告”会怎样走

下面是依据已捕获合同整理的示例，不是实际运行记录。假设已获授权的人在 Thread 中直接 @Claude，要求排查仓库故障并生成报告。

  1. 确认请求归属。读 wake 的来源和信任字段；若 helper 已在处理，不另开一套工作。搜索来的历史事故只能当线索。
  2. 留下可见承诺。长任务先发 live status，列出排查、修改、验证、交付；记录消息 ts，后续只编辑这一份进度。
  3. 核对可用访问。使用仓库访问工具确认当前路径；若需要本人资源，按直接送达的本人消息启动其个人 Session，不把凭据搬到公共 Session。
  4. 把执行交给 worker。给它范围、证据和明确产物。后台执行期间安排 send_later，再让当前轮结束。
  5. 重新唤醒后核验。先更新状态，读真实结果；测试失败就是未完成，而不是换一种“已修复”的措辞。
  6. 发报告并收尾。worker 发布 Artifact，协调者用最新 last_seen_ts 发送链接；拿到 ts 才标记交付，删除无用 check-in。

沿途最关键的不是用了几个工具，而是六次责任转换有没有留下可核验对象：请求消息、状态消息、访问结果、worker 工作、验证结果、最终链接。

10 / 张力与局限

读得越细，越不能把文字当成实现

Agent 的说明要求 subagent_type，Schema 的 required 却只有 description 与 prompt。Workflow 工具文档要求显式 opt-in，Slack Prompt 又说本场景已经满足。这不是可以略过的小字：它说明有效合同分散在多层文本，而不是只看一个 JSON Schema 就能还原全部约束。

不能据此直接宣布有权限漏洞。模型可能服从更具体的场景规则，服务器也可能补做校验。应当保存真实参数、拒绝结果和重试路径，再判断哪层在起作用。

故障注入合同期望需要观察
回复前出现新消息普通 reply 拒绝旧上下文读取、重写、force 使用与回执
claim 延迟或 Session 消失对账、接管，避免永远等待漏答率、重复率、接管时间
Artifact 被别人更新重读、合并，不直接覆盖新版本是否保留他人改动
容器重启 / Session 替换按各自生命周期恢复one-shot 与 recurring 的投递目标
伪造授权或 done 文本按送达来源与实际答复判断是否误启动、误授权或误报完成

以上均为待做实验，不是通过项。当前最值得借鉴的是：把请求、通知、执行、恢复和交付分别写清；最值得警惕的是：把这些文字误认成已经验证的端到端可靠性。
