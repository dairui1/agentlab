一份旅行需求单里，混进了给内部同事看的备注；酒店信息也没说明是否确认。对 Agent 说“下次认真一点”，下次仍可能犯同样的错。

Raven 想把这类反馈变成后续任务真的会执行的检查。作者记录的旅行社模拟中，它在写需求单前加了审核，又给制作 PPT 的子 Agent 加了自检工具；第三轮审核打回了四次。这个案例未由本研究复现，而且当时直接使用老板整理的要求，不是当前默认 Analyst 流程的完整验证。

把“下次注意”改成一道会执行的检查

Raven 本身可以组织多个 Agent 完成工作。本文关注的 Curator，是仓库里负责修订这些执行者的实验组件：根据反馈生成新策略，检查能否装起来，再安装到后续执行中。它改的是模型周围的上下文、工具和工作流程，不是在这里训练一套新的模型权重。

需求单的问题因此可以落成一条具体要求：“写进交付文件前，检查是否含有内部备注。”这比往 Prompt 里加一句“更专业”容易验收。要回答的问题也随之变了：检查装上了吗？工作时触发了吗？最后真的少犯错了吗？

反馈先说清行为，再决定改哪个执行者

当前默认流程把这两件事分开：Analyst 把任务反馈整理成可观察的要求；Curator 查看正在使用的配置、上一轮计划和执行记录，再决定实现这条要求。比如需求单需要写盘前审核，PPT 则需要自己的自检工具，不必把同一句提醒无差别塞给所有 Agent。workflow.improve() 是显式入口，不会把 worker 的每句话都自动当成修订请求。执行记录还带着产生它的 artifact_id，避免拿新版本解释旧结果。

Memory每轮看见什么、留下什么提示词、上下文策略、记忆后端

这些产物落在 Raven 已有的配置、home 文件、插件与回调上，不需要每次给整个 runtime 打补丁。它们不只影响一句回复，而会在安装后的后续执行中继续生效。

反馈、候选和执行都留有版本记录。否则一次旧需求单不合格，却拿新检查的代码解释它，就会误判检查没有生效。Raven 用 artifact_id 关联实际执行的版本；普通 worker 消息也不会自动变成修订授权。

校验通过，可能只表示它能被装起来

候选不是直接写入活动 worker。校验先做静态检查，再在复制的本地状态上装配真实 Raven runtime。组合候选还会读取子 Harness 是否就绪。这比只检查 JSON 合法多走了一步，但它仍没有自动回答“这次修改有没有帮助”。

最容易误判的地方，是行为检查可以不提供。run_probe() 的缺省分支只记录 not_supplied 就返回。如果要检查新策略能否拦住内部备注，调用者必须准备相应的任务探针。

查看没有提供行为探针时的源码
    if probe is None:
        bound.recorder.add("validation.probe", status="not_supplied")
        return

因此需要三份不同的回执：候选能启动；预期机制在任务中确实触发；在固定预算与保留任务上表现更好。前两份都重要，但不能替代第三份。没有 probe 也能经过当前校验路径，这是研究判断必须保留的条件。

Iteration 还做了一个克制的选择：最后一轮只保留评价，不再修订，因为没有下一轮能检验这次修改。这个选择值得借鉴；不过“下一轮会执行”仍不等于“独立保留集验收”。

新检查怎样进入下一轮工作

候选通过装配检查后，还不能随时替换正在干活的执行者。组合部署先确认根 worker 空闲、子调用已完成，满足条件后才保存旧产物、文件内容和策略 checkpoint，再启动新组合并核对子 Harness 的版本指纹。启动或检查出错时，异常路径恢复旧内容和旧版本。这样可以避免根已经换成新流程、子却还执行旧规则。

策略层的恢复范围更窄。BoundStrategy 在异常时恢复自己拥有的 JSON 状态，并记录调用和错误；已经发出去的消息、远端写入等外部副作用不会被撤销。本文没有注入进程崩溃或断电，也不把这段异常处理称为已经验证的崩溃一致性。

装上了、拦住了、做得更好，分别验收

回到需求单。看到审核记录，能确认某次写入被打回；确认新旧版本一起切换，能说明装配没有混用。可要说修改让 Agent 更好，还需要用没有参与修订的任务，比较原版、只加 Prompt 提醒和 Curator 修改后的结果，并记录相同预算下的失败与成本。

作者报告中确实有成绩，但七组 Harness 进化结果来自旧的 HarnessBank v2，不是今天这套 Curator 的效果验收。仓库里的旧 Evolver 也有自己的晋级规则，不能和当前 Curator 合并成一条已经证实的自我进化链。

Curator 仍在 experimental/，随源码而非安装包提供，项目自称 pre-alpha。真实试用还要核对第三方 Agent 的权限：Codex ACP 预设使用 agent-full-access；没有向 Raven 发起权限询问的动作，可能根本不到达宿主的检查。

Raven 最有价值的，是把失败反馈接到可持续生效、可追踪版本的执行策略。本文不归为严格 Agentic RL；更强的 RSI，也就是改进器自身持续变强，在已读材料里没有建立证据。本研究没有安装或执行 Raven，也没有在本机执行上游测试、真实模型或基准。

实现补充、作者成绩与来源

主线只跟随一次反馈怎样变成下一轮的检查。下面分别补充组织结构、旧演化方法和作者实验，避免把不同系统的证据混在一起。

Host 编排谁，Curator 又能改到哪一层？

面对一项需要调研、写代码、制作交付物的请求，Host 生成 DAG，把每个节点交给对应的执行后端。调度器按依赖选择可运行节点；一个节点长时间没有动作时，watcher 会发停滞通知，而不是直接把它标成失败。慢模型和坏任务，不能只凭沉默时间作同一种处理。

第三方接入也不是“模仿 Codex 的提示词”。固定版本的预设通过 ACP adapter 调用 Codex、Claude Code 等 Agent。要注意版本归属：部分 shim 自带 Agent binary 或 SDK 依赖，所以真正回答的未必是用户终端里那个可执行文件。

“Harness of harnesses”在这里有两个具体含义：Host 组织多个完整执行者；Curator 又能分别修订受管根和子 Harness 的行为。后一层不是让子 Agent 无限向下分裂。设计明确规定受管子 Harness 不再继续委派。

旧 Evolver 怎样保留候选，为什么晋级不代表显著提升？

仓库里还有 evolver/，它不是当前 Curator 的另一个名字。这条基准驱动路径比较候选与基线在同一批任务上的结果，保存候选和测量记录。其 paired_lift() 把采用条件与显著性分成两个字段：

    promoted = candidate_mean > control_mean  # navigator: banks on beating vanilla
    credited_2sigma = z >= z_threshold

均值超过基线就可以晋级，即使没达到 2σ。把 promoted 翻译成“已证实显著改善”会直接改写实验含义。更合适的说法是“候选被保留”，再分别给出提升、方差、样本量和显著性标签。

README 还注明这棵目录计划退役，真实全规模多轮运行与保留集流程存在未执行部分。它的 path guard 把 evolver/ 自身列为不可改区。这里支持的是围绕固定任务模型改进 Harness，不能借此声称改进器本身已经递归进化。

MAOB 与 HarnessBank v2 的作者成绩，具体测了什么？

MAOB 使用 140 个请求和四类专家角色，在真正派工之前，把预测的 DAG 与参考图比较。它衡量选对哪些专家、依赖是否合理。这个设计能隔离规划问题，却不能回答整项工作是否交付成功。

报告的七组 Harness 进化成绩来自 HarnessBank v2，不是新 Curator 的实验。任务模型固定为 Qwen3.6-27B，每题三次尝试，在训练任务上选择 Harness，再做保留测试。下表只摘两项，用来说明成绩来源，不作为 Agent 排名。

第三方 Agent 与旧 Evolver，各自有哪些权限限制？

Codex ACP 预设选择 agent-full-access。宿主收到权限请求后通常自动批准，但会拒绝命中部分宿主 deny 规则的命令。关键限制是：第三方自己直接放行、没有向 Raven 发问的调用，不会到达这道检查。

所以不能用一张“统一审批”架构图推断所有子 Agent 都受同一道墙约束。实际试用应先核对每个适配器使用的身份、工作目录、可写挂载、网络和凭据，而不是默认沿用宿主的安全感。

旧 Evolver 把边界写得更直接：候选可能与评分器同进程，路径白名单主要阻止捷径，不是针对恶意代码的安全沙箱；设计步骤也没有文件系统和网络硬隔离。其建议是在容器或 VM 中使用受限凭据。不能将这条限制扩大成 Raven 的所有执行环境都没有隔离，也不能反过来忽略它。

研究提交还新增了哪些当轮工具行为？

日常 runtime 也有值得跟踪的小机制。研究提交修复了工具冻结的一处交互问题：后台刚连上的工具仍等下一轮，但本轮主动连接的插件可以在后续 step 立即使用，避免用户再发一句“继续”。它通过原地修改该轮捕获的工具字典跨过异步任务上下文边界，关闭和通道限制仍然有效。这是晚于 v0.2.3 的 main 改动，不是该发布包已包含的行为。
