01 / 先说结论

先说结论：这不是一只普通 MCP

普通 MCP 往往是一个进程加一组工具。Kimi Computer Use 被 Kimi Code 提升成了 capability：CLI 同时检查 Plugin、App、后台服务和系统权限，缺哪一层就补哪一层；安装中断后也能从当前状态继续。

它的主循环并不神秘：列出 App，读取 AX 树与截图，按 index 或像素坐标执行一个动作，再重新观察。真正有区分度的是执行层：macOS 版把截图和输入放进独立 launchd/XPC 服务，尝试把事件直接送进目标窗口，而不是搬动用户的真实鼠标。

Kimi Code 负责把能力接进 Agent；KimiCU 服务才是桌面权限与系统输入的实际持有者。本专题的核心判断

03 / 四层架构

四层架构：Kimi Code 不直接碰桌面

Plugin manifest 声明 Skill、stdio MCP 和白名单工具；Kimi Code 安装器再下载 App、清理旧服务、复制到 /Applications、注册 launchd，最后发起权限请求。检测时，这四种状态是分开报告的，不会把“Plugin 已安装”误写成“Computer Use 已可用”。

04 / 观察合同

观察：AX 树与截图是一份快照

get_app_state 可以返回完整状态、只有截图，或只有 AX 文本。只要带 AX，它就把这次观察缓存起来，让后续动作通过 node index 找目标；像素坐标则以这张截图左上角为原点，执行时再映射回真实窗口。

这也带来一条硬约束：界面变化后旧 index 和旧坐标都不再可信。Skill 明确要求重新读取状态；二进制里的错误路径还会识别菜单重排、AX identity 改变、坐标越界和缓存年龄。它没有假装 locator 永远稳定。

动作成功不等于任务成功

Electron/Web 输入可能已经送达，但 AX 读不回文本。这时工具会返回 verified:false 或要求截图验证，而不是编造一个成功回执。

05 / 后台输入

后台输入：不抢鼠标是怎么做到的

签名二进制链接了 AppKit、ApplicationServices、CoreGraphics、ScreenCaptureKit 与 Swift XPC。静态字符串同时出现 AXUIElementPerformAction、窗口定向事件位置、按 PID 投递输入和后台输入 fallback。结合工具说明，可以确认它至少组合了两条路：原生控件优先走 AX action/value；需要渲染层焦点时，向目标窗口做不移动实体指针的后台点击和键盘投递。

这不是“所有 App 永不切前台”的数学保证。官方文档已经保留了少量系统弹窗会唤起前台的例外；Skill 也承认 Chromium 拖拽不可靠、Electron 右键不接受同一条合成路径。Windows 更直接：它可能短暂激活窗口并占用真实键鼠。

06 / 权限与信任

权限与信任：真正有权的是谁

macOS 的辅助功能与屏幕录制权限授给 KimiCU.app，不是 Kimi Code 的 Agent 进程。launchd 注册的 ai.kimi.cu.service 暴露 Mach service，MCP 端通过 XPC 问服务状态并请求动作。正因如此，从 Agent shell 运行 doctor 看到没权限，并不能证明后台服务没权限。

发行可信度比随手下载的脚本高一层：当前 App 由 Beijing Moonshot Technology Co., Ltd 的 Developer ID 签名，开启 hardened runtime，并带 stapled notarization ticket。但它仍是专有二进制；公开仓库只能审计安装与接线，无法完整审计截图、输入、XPC 和 telemetry 的内部实现。

另一个需要正视的边界是 telemetry。二进制静态字符串包含独立 telemetry 模块和上报端点，但静态检查不能证明默认开关、字段、触发条件或每次动作是否上报。这里应记录为待验证项，而不是直接下“会上传截图”或“完全本地”的结论。

两者最相似的不是工具名，而是恢复合同：观察必须先于动作，界面变化后不能复用旧元素，超时或弱回读时必须重新观察。Kimi 的优势是把这套规则直接写进可安装 Skill，接口也更标准；它的未知仍集中在专有原生服务里。

08 / 研究边界

研究边界与下一步实测

本次可以确认架构、安装状态机、工具面、签名身份和二进制暴露出的系统框架；不能确认真实 App 覆盖率、后台点击成功率、复杂弹窗行为、截图是否离开本机，以及 telemetry 的默认策略。要补齐这些结论，需要在隔离 macOS 用户下完成一次受控安装，再用原生 App、Electron 和 Chromium 各跑一组可逆任务。

安全上，官方 Skill 已要求删除、发送、提交、付款前再次确认，官方文档也明确不建议用于资金、账号和对外发布。实际接入 AgentLab 或日常工作时，还应把动作前确认做成宿主 policy，而不是只依赖模型读到的一段 Skill 文本。
