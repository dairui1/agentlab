Agent 正在改代码，你补了一句“先别发布”。工作台显示发送成功。可它究竟是收下了这句话，还是已经把它放进正在工作的那一轮？

如果后台可以切换 Codex、Claude Code 或别的 Agent，这个问题会更难：同一个“发送”按钮，背后可能是不同的递送方式。OAR 想让工作台有记录可查，而不是只凭按钮变灰、消息冒出来就猜任务进度。下面的消息是解释机制的场景，不是实际运行记录。

工作台统一入口，原版 Agent 仍负责执行

OAR 是一个 TypeScript 库，不是另一个 Coding Agent。工作台用它发现已安装的 Agent、打开会话、发送输入和观察结果；实际改代码的，仍然是接入的原版程序或 SDK。Codex 走 app-server，Claude Code 走 CLI 的 stream-json，Pi 则在进程内调用 SDK。

这种统一能省掉每换一个后端就重写消息界面的工作。但调用方式相同，不表示动作含义相同。工作台还要问：这个后端能否在当前轮补充要求？排队内容会不会随进程退出而丢失？子 Agent 的活动能不能单独看见？OAR 保留这些差异，让应用按实际能力处理。

这句“先别发布”，可能只是排到了下一轮

有的后端可以把新要求送进当前轮，有的只能留给下一轮。OAR 把这两种动作分别叫作 steer 和 queue。如果当前轮已经结束，第一次补充可能被拒，工作台再改为排队。对你而言，这仍然是同一句要求，不该在界面里变成两条消息。库用 inputId 关联它们，再分别留下每次投递的回执。

01steer 请求inputId = A · request = R1
02拒绝当轮注入response → R1
03queue 请求inputId = A · request = R2
04接受排队response → R2 · queued

合成示意：一个输入、两次尝试。不是任何真实 Agent 的执行轨迹。

返回 accepted 以后，也不能直接显示“已读”。Claude 的回执可能只表示内容已经写进程序的输入通道；Codex、Claude 还能通过原生消息确认同一输入再次出现，Pi 则缺少已证明的请求关联，不能凭文字一样就强行配对。接受、原生回显、进入模型请求、产生语义效果，是四个不同层次。目前会话投影只保存它实际掌握的回执和观察，没有通用的“模型已消费”状态。

本地合成探针确认：补充被拒、改为排队接受之后，界面投影只有一个逻辑输入，记录仍有两次尝试。这也不是 exactly-once 保证。若进程在动作发出后、回执保存前消失，宿主仍须处理“不知道是否送达”，不能拿相同 inputId 当作原生服务一定去重的承诺。

界面的进度，应该从记录里算出来

为了回答“发出去以后发生了什么”，OAR 把三类内容按顺序记在一起：工作台发出的请求、后端给出的回执、原生 Agent 发来的活动。源码分别叫它们 request、response 和 frame。消息界面、工具活动和任务状态都从这份记录计算，不必各自维护一份可能互相矛盾的进度。

实现界面时，哪些记录不能直接去重？

events() 是便捷阅读面，rawEvents() 和 records() 才保留底层记录。一个原生 frame 能读出三个事件，三个事件共享 seq；没有已知语义的 frame 也可能读不出事件。因此按 seq 对扁平事件去重，会把同一帧的第二、第三个事实删掉。本地探针用一帧两项事件确认了这个行为。

还有一个小但重要的命名细节：扁平流的 turn_started 可以来自应用发出的 prompt request。之后仍可能收到 busy 拒绝。它是操作起点，不是模型已开始工作的凭证。正确做法是一起读取 request、response 和后续原生结束，而不是见到 started 就锁定“已运行”。

“无损”也有范围。Claude 的 get_settings 回读可能携带用户环境配置，适配器特意消费但不记录这一行。这里追求的是可追踪的会话事实，不是全进程字节级抓包；更不是对所有敏感字段自动脱敏。

子 Agent 先结束，不能让父任务跟着结束

主 Agent 把一项检查交给子 Agent。孩子很快报告完成，主任务却还在改代码。这时工作台不能把“子任务结束”显示成“整项工作完成”。OAR 先记录活动属于哪个会话、哪个 Agent，只有明确知道父子关系才连起来。

等主任务结果时，库会过滤孩子的完成通知。本地合成探针先送来子任务的 completed，主任务结果仍为空；这确认了过滤逻辑，不代表真实 Codex 子线程已经在本机跑通。

看不清子树，也应该是界面里一种明确的答案。Kimi 或 Antigravity 的选定传输没有提供完整子活动，工作台不能从工具名称和文本猜一棵看起来完整的树。源码把这种可见性叫作 opaque。

会话归属和子 Agent 用量，具体怎样记录？

OAR 用 sessionId 与 agentPath 保存归属：Claude 的子活动可以挂在同一流的路径下；Codex、Cursor、Grok 的子活动则可能拥有独立 session ID。ACP 记录器不会因为一条通知不是根 session 就把它丢弃。turnEndAfter 只接受指定根会话、根 Agent 的结束。

用量也一样。根 session.usage() 不自动加上独立子 session 的数字；同 session 内则按 agentPath 保留最新累计量，避免每次通知都重复累加。没有报告时是 null，不是零成本。要算全树账单，宿主还得核对原生计费是否已包含子调用。Grok 源码就记载过父 prompt 账单包含子模型调用的口径，盲加父子会再算一次。

接口能少猜状态，不能替产品托管任务

采用前先处理权限。Claude 以 --dangerously-skip-permissions 启动；Codex 默认 approvalPolicy: never，并覆盖 sandbox_mode 为 danger-full-access；ACP 权限回调优先选择 allow_always。其设计理由是无人值守嵌入时不能等人工审批，但产品必须自己提供隔离，不能把“不会弹窗”理解为“更安全”。

哪些配置和反向调用，容易被误当成权限边界？

Codex 的例外配置是宿主进程环境中的 OAR_CODEX_SANDBOX；设为 inherit 时不加覆盖，让原配置生效。由于这里直接读 process.env，不能想当然地只把同名变量塞进 SessionOptions.env，就认为它改变了这段启动选择。

ACP 还有一条容易忽略的反向执行链：runtime 可以请宿主创建 terminal。实现检查命令非空、cwd 为绝对路径后直接 spawn，并没有将目录限制在初始工作区之下。需要的是受限执行身份、挂载和网络，而不是只在 UI 上显示“当前项目”。

也不能把“支持 toApp 记录”理解为“已有完整审批与追问产品”。Codex 适配器记录意外到来的 server request，但不自动应答；Cursor 的若干厂商请求则明确拒绝，让原生产品走自己的 fallback。这些不同处置仍可能影响停滞与交互。接入前应逐项核对，而不是拿一张统一协议图替代运行合同。

还要给等待加一个真正的总截止。库里的 timeoutMs 不是硬截止：超时发出 abort 后，函数继续等后端报告结束。本地合成探针设置 10 ms 超时，100 ms 后仍未返回，直到注入合成退出记录才结束。它没有伪造完成，但调用方必须安排自己的收尾，不能直接把任务再发一次。

OAR 适合成为多 Agent 工作台的接入层。数据库、日志保护、进程清理，以及外部动作失败后怎样核对，仍是产品要补上的工作。它让差异有据可查，没有让差异消失。

实现细节与研究范围

正文关注消息怎样变成可核对的进度。各后端能力、恢复和验证细节留在下面；完整行号、哈希和未知问题也保留在证据索引中。

七种后端分别怎样接入？

Codex 走 app-server，Claude Code 走原版 CLI 的 stream-json，Pi 直接调用进程内 SDK。其余四个通过 ACP，但各自还有厂商扩展。这与 MiMo Agent 的黑盒接入有一处共通点：都不是复制一份 system prompt 就宣称复刻了 Agent。区别在于 OAR 首先服务嵌入式产品接口，而不是训练与基准评测。

同名的 steer 也有不同后果。Codex 用 expectedTurnId 让原生服务仲裁“要改的还是不是那一轮”；Claude 写入 stdin 后，由自身时序决定进入当前模型步骤还是下一轮；Grok 的 sendNow 则可能取消旧 prompt 并启动新模型轮次。源码注释记录了中断工具再次发出的现象。对有副作用的动作，这不能简化成“无损追加一句话”。

重连界面、恢复原生会话和跨产品迁移，有什么不同？

在同一个 Session 实例里，cursor 让订阅者从 afterSeq 之后补读内存中的记录，再接实时流。这解决的是观察者重连。它没有把内存 log 自动放进数据库，也没有把尚未送出的内存 queue 变成持久任务。

native resume 则重新打开原生会话。原生 session ID 可以相同，OAR 的新流仍从 seq 0 开始。应用必须为新流另分配 streamId 并一同持久化；否则 conversation reducer 会把较小的 seq 当成读过的记录。本地探针中，复用旧 streamId 时输入数仍为 1，换成新 streamId 才是 2。

需要落盘时，Voyage 提供显式 JSONL 格式：header 描述 runtime 与会话，record 保存原始记录，end 表示捕获收尾。文件没有 end，可以识别为不完整捕获；但这里没有 fsync，也不应把同步 writeSync 写成断电事务保证。原生 payload 可能包含用户内容，日志的访问控制和分享脱敏同样属于产品责任。

恢复时换模型也不能只相信传入参数。Codex 的新建路径用 config 设置 effort；恢复路径刻意避免该覆盖重建模型设置，而是在原生线程上回读、更新。统一入口之下，需要保留这种厂商级处理。

至于从 Claude 迁移到 Codex，本文没有看到可直接交付的统一会话迁移保证。跨宿主 handoff、通用热切换 Session.configure 与远程 oar serve 仍出现在后续计划中，不能把路线图读成 v0.10.2 已有功能。

超时与停滞观察的具体行为是什么？

promptAndWait({ timeoutMs }) 是本文最建议调用者仔细读的一处。超时后，它发出 abort，然后继续等待 runtime 自己给出 turn end；这段等待没有第二个截止时间。这样的设计不伪造完成结果，但调用方若把 timeoutMs 当成“最晚返回时间”，仍会挂住。

本地合成探针：10 ms 超时，100 ms 后仍未返回

我们构造一个只接受 prompt 和 abort、始终不发 turn end 的内存适配器。超时确实触发 abort，但 100 ms 后 Promise 仍 pending。直到探针注入合成 exited 记录才结束，结果保留 interrupted 与 runtime_exited 失败。这不是某个真实模型卡死的复现，而是公共 helper 的可重复合同检查。

查看六项探针回执

observeStalls 解决的是“多久没有新事实”，不是“进程一定死了”。它报告静默时长和最后记录，由宿主决定是否提醒、中断、处置 Session 或重建环境。

一个可用的产品需要再加独立总截止与收尾策略，并记录最后游标及未决副作用。不能简单地超时就重发任务：原调用可能已执行，只是回执没回来。另一方面，内核完整保留 log，若干查询每次扫描全量记录；长会话的内存和延迟也需由实际负载验证，不能仅因小测试很快就认定可无限积累。

本地使用 Node 24.14.0 与 pnpm 11.22.0，按 frozen lockfile 安装并禁用安装脚本，先构建库，再以 CI=1、移除 OAR_TEST 执行 vitest run tests。首轮受构建时序和本地监听权限影响失败；构建完成、允许测试的 loopback 服务后完整重跑通过。没有更新上游快照来迁就测试，也没有运行真实账户 backend。

固定提交的 CI 记录另有 3 个系统的常规检查，加上 3 个系统 × Claude、Codex、Pi 的 9 个行为 job。它们使用真实 harness 配脚本模型端，能检查 API 到原生程序再到 provider 请求的链路，比只 mock 一个适配器更有价值。但不能据此宣布七个 runtime 的真实模型任务全部可靠。后端不可用还存在 skip 机制，job 绿色也不等于每个行为 case 都执行了。

作者文档保留了不少实验过程，阅读时要注意时点。例如 steer 调查明确写着 pre-0.6 的旧状态，当前代码已补上输入身份；部分能力矩阵的现场证据备注也落后于后来适配器注释。本文以固定实现为准，作者的现场观察单独标记，不把旧调查表直接当现版本行为。

分类上，本文将 OAR 视为原生 Agent 接入与可观察性基础设施。它没有展示策略优化训练，或自动修改自身后独立评估的闭环，不归为严格 Agentic RL 或 RSI。
