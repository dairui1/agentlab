Goal Mode

模型说“做完了”，和系统允许它停下来，是两回事。Codex 与 Claude Code 都有 /goal，却把目标、续跑和完成权放在了不同地方。

先记住一句话Codex 把 goal 放进持久控制面；Claude 把 goal 放在每轮出口。

假设任务是“把认证模块迁完，相关测试全绿，lint 干净，别碰无关文件”。普通 turn 结束时，模型很可能已经改了一部分，也可能刚跑完一轮失败测试。Goal Mode 真正要解决的，不是如何把这句话再念一遍，而是：现在该不该开下一轮，谁来决定，以及“完成”这个结论要凭什么成立。

01 / 整体模型

整体模型：同一句 /goal，两条控制回路

表面上，两边的使用动作几乎一样：敲下 /goal，给一个可验证的终点，然后让 agent 自己往前走。可只要追到一轮结束的地方，分叉就出现了。

Codex 先在 thread 上保存一条 goal。每轮结束后，runtime 看这条记录是不是仍为 active；是，就给同一个 worker 塞进隐藏的目标上下文，再开一个正常 turn。最后还是这个 worker 调 update_goal，申报 complete 或真正的 blocked。Claude Code 则把 condition 挂在 session 的 Stop hook 上。worker 想结束一轮时，另一只小模型只看对话：unmet 就把理由带回下一轮，met 会清掉 goal；如果 evaluator 判断目标已经不可能完成，也会清掉 hook，但留下 failed 记录。

Claude 把 goal 放在出口；Codex 把 goal 放进控制面。这是整篇最值得记住的一句话
02 / 产品入口

产品入口：一个保存目标，一个设置条件

OpenAI 在 2026 年 5 月把 Goal Mode 标为 Codex 的正式能力；Goals feature 现在也是 stable、默认开启。Codex 把命令写作 /goal <objective>，空参数用来查看，另有 pause、resume、clear 和编辑路径。临时 session 不让建 goal，因为没有持久 thread 可挂。

Claude Code 从 2.1.139 起也提供原生 /goal。官方叫它 completion condition：一个 session 同时只有一个，重新设置会直接替换，clear、stop、off 等别名会把它拆掉。设置以后立刻开工，不用再补发一条 prompt。两边的正文上限恰好都是 4,000 字符，但“字数一样”并不代表状态模型一样。

最新版把“谁能发起 goal”也变成了产品问题

Claude Code 2.1.227 在支持该入口的交互式主会话里提供模型工具 ProposeGoal。默认情况下，模型只能提出一条可验证的完成条件，等用户按一次确认才会真正设置；只有当 condition 直接承接用户已经说清楚的结果时，才允许跳过确认。它改变的是 goal 的入口，不是完成权限：设好以后，仍由 Stop evaluator 判断能不能停。

03 / 目标状态

目标状态：系统到底记住了什么

Codex 的 ThreadGoal 很朴素：thread_id、目标正文、状态、可选 token budget、已用 token、已用秒数和时间戳。它没有把计划、当前 checkpoint、失败原因、验收清单全都塞进数据库。那些细节仍可能留在 plan、对话、文件或外部系统里。goal row 负责的是更窄的一件事：这张工单是否还活着，以及 runtime 应不应该继续为它记账和开 turn。

Claude 的公开合同更轻。当前 session 里有 active goal，transcript 里会留下 goal_status 记录；真正决定“还活着吗”的，是 Stop hook 还在不在。状态页展示 condition、运行时间、已评估 turn、token spend 和最近一条 evaluator 理由；终态则区分 achieved 与 failed。它们有用，却不是一套和 Codex 六状态对等的生命周期 enum。

Goal 不是 Plan，也不是 Memory

Plan 回答“打算分几步走”，memory 帮模型记住背景，goal 则在 turn 边界上决定工作是否还要继续。三者可以互相喂材料，但谁也不能替代谁。计划全勾完了，不自动证明目标达成；对话被压缩了，也不应该顺手把 goal 的生死抹掉。

这层分离很重要。长任务真正怕的往往不是忘了一个文件名，而是聊天看起来告一段落以后，系统把“一轮结束”误认成“目标结束”。Codex 用 thread 状态把两件事拆开；Claude 用 Stop hook 把正常停机拦在门口。它们都承认了同一个事实：只靠模型记得“我还没做完”，不够。

04 / Codex 控制面

Codex 控制面：一个 goal 横跨六层

Codex 这套实现不轻。/goal 只是露在水面上的开关，下面至少串了六层：TUI 解析用户动作，protocol 定义跨组件的数据，state DB 持久化一条 thread goal，模型工具约束 worker 能做什么，accounting 记录使用量，runtime 再处理续跑和停机。一个功能横跨这么多层，维护成本不小；换来的好处是，暂停、阻塞、用量限制和完成不会只剩 prompt 里的几个词。

模型能看见三个工具：get_goal、create_goal、update_goal。其中最值得看的不是数量，而是缺了什么。worker 不能自己 pause、resume、把 goal 标成 budget-limited 或 usage-limited；update_goal 只收 complete 与 blocked。人负责改意图和恢复，runtime 负责资源边界，worker 负责对工作结果表态。这个分工不是万无一失，但至少没有把所有状态按钮都塞给同一个模型。

05 / Codex 续跑

Codex 续跑：thread 空闲以后，runtime 再开一轮

普通 turn 收尾时，Codex 的 runtime 不会直接照着上一条回答再发一遍。它先拿一把 goal-state permit，读取 thread 上当前那条 goal，再确认状态仍为 active。只有这些条件都成立，才构造一条内部 continuation item，交给 try_start_turn_if_idle。这把锁解决的是一个很现实的竞态：用户刚按 pause，旧状态不能在同一瞬间又偷偷启动一轮。

新 turn 收到的隐藏上下文会重新带上完整 objective、已用与剩余 token，并提醒 worker：当前 worktree 和外部状态才是事实；上一轮的记忆只能帮忙定位，不能替代检查。模板还把完成审计写得很重：目标里每一项明确要求、命令、产物和 gate，都要找到能证明它的当前证据；证据弱、缺失或只“看起来没问题”，就继续做，不许把成功定义缩到现有成果刚好够得着的位置。

thread becomes idle → read persisted goal → status == active ? yes: inject internal goal context → start a regular turn no: clear active accounting → stay stopped

这里有两个边界。第一，所谓“自动”只是省掉用户逐轮催促，不是越过工具权限；高风险动作照样要走原审批。第二，它是活着的进程里触发的新 turn，不是机器关了还会在暗处跑。Plan turn 也不会仅凭隐藏 goal input 被悄悄启动。跨 turn 不等于永远在后台运行。

06 / 状态与预算

状态与预算：暂停、阻塞和没额度不是一回事

Codex 现在有六个 goal 状态。active 表示可以继续；paused 是用户暂时按住；blocked 是 worker 在严格条件下确认当前真的走不动；usage_limited 来自供应商或会话级用量边界；budget_limited 是这条 goal 自己的 token budget 到线；complete 才是目标达成。状态多不是为了显得专业，而是为了让恢复动作不犯傻：额度耗尽时猛点 resume，和用户暂停后继续，根本不是同一个问题。

Codex 把中途改方向留在控制面；Claude Code 的公开 /goal 入口则是查看、替换和清除 condition。两边都没有因为 goal 在跑，就拿走用户的接管权。

07 / Claude 出口闸

Claude 出口闸：先等后台，再问 evaluator

Claude Code 的实现要轻得多，因为它没有为 goal 新造一整套 thread state machine。/goal 是一个 session-scoped prompt Stop hook 的快捷包装。worker 跑完当前 turn，准备停下；如果没有后台工作悬着，hook 才把 condition 和到目前为止的 conversation 送给配置的小型快速模型。默认 Claude API 上是 Haiku，但第三方 provider 的默认值可能不同，所以不能硬写一个固定模型版本。

后台分支很实用。主 worker 先停，不代表它刚派出去的 agent 或 task 已经把结果交回来；2.1.227 会临时摘掉 goal hook，跳过这次评估，最后再挂回去。真轮到 evaluator 时，角色分离才开始发挥作用：做事的人说“差不多了”，不等于闸门就开；新模型会从零看一遍 condition 和已经公开的证据。unmet 的理由让下一轮知道缺什么，impossible 则让一个已经走不通的目标停止空转。代价也很直白：每次实际评估多一次小模型调用，而且裁判能看的材料有边界。

08 / 评估视野

评估视野：独立裁判也会看漏现场

这可能是 Claude /goal 最容易被误会的一点：独立 evaluator 不等于独立验收环境。官方写得很清楚，它不能跑命令，也不能读文件；它只能判断 worker 已经放进 conversation 的东西。测试确实全绿，但 worker 没贴结果，裁判可能给出 false negative；测试还红着，worker 却写了一段很像完成报告的话，裁判也可能被带向 false positive。角色独立解决了“自己给自己盖章”的问题，却没有自动解决“证据和现实一致”的问题。

工作区现实对话里出现的证据Claude evaluator 可能怎么看真正该修什么
测试已通过贴了命令与 exit 0有条件判 met再核对约束项，不只看一条绿灯
测试已通过没有结果可能判 unmet让 worker 把验收证据写进 transcript
测试仍失败如实贴出失败应判 unmet，并说明缺口继续修，不要改写 condition
外部依赖永久不可用原因与尝试都说清楚可以判 impossible把它当失败终态，不要冒充完成
测试仍失败只写“应该好了”存在误判 met 的风险condition 明确要求命令、退出码与约束证据

因此，Claude 的好 condition 不只是“所有测试通过”，而是“运行哪条命令、结果如何进入对话、哪些文件不能改、什么情况算到时间上限”。Codex 也需要同样清楚的验收合同，只是它的 continuation prompt 会主动要求 worker 回到 worktree 逐项审计。那让它更靠近现场，却仍然不是独立裁判。

09 / 恢复语义

恢复语义：续用一行状态，还是重建一枚钩子

关闭再回来以后，最能看出两边把 source of truth 放在哪。Codex 重新读取 thread 的持久 goal：objective、状态、tokens used 和 time used 都是那条记录的一部分。active 的 goal 可以重新进入续跑；paused、blocked 或 usage-limited 则先把状态摆给用户，由用户决定是否恢复。对话压缩不该删除这条独立记录，但这仍不是“离线工作”：机器和宿主不运行时，没有 runtime 帮它开新 turn。

Claude Code 在恢复 session 时，从 transcript 里的最新 goal 状态重建 active condition 与 Stop hook。condition 会回来，但 turn count、timer 和 token-spend baseline 会从零开始；已经 achieved、failed 或 cleared 的 goal 都不恢复。换句话说，它保住的是“出口还要检查什么”，不是跨 session 连续的一份计量账本。

两个“恢复”都是真的，只是恢复的对象不同

Codex 续用持久 goal 状态与累计用量；Claude 续用 condition，再重建 session hook。前者更像拿回同一张工单，后者更像从会话记录里重新挂上验收闸门。别因为计数归零，就说 Claude 忘了目标；也别因为 Codex 留着 row，就说它离线期间一直在干活。

11 / 完成权限

完成权限：自证与外审，各自会在哪里失手

Codex 的 worker 最接近真实现场。它能读文件、跑测试、看 git diff，再按 continuation prompt 做 requirement-by-requirement audit。可最终的 complete 仍由它自己调用，runtime 不会再派一个独立模型重验。这套方案容易出现的错误，是 worker 把一组看似覆盖目标的检查当成全部证据，或者被自己刚写完的结果说服。工具权限被窄化了，完成判断没有彻底外包。

Claude 恰好反过来。worker 不能自己打开闸门，独立 evaluator 会再看一次 condition，因此不容易因为一段自信的收尾话就直接停。但它没有工具，也看不到未被 surfaced 的文件与命令结果。它的典型错误不是“没有第二双眼睛”，而是第二双眼睛站在控制室里，只能看 worker 递出来的监控画面。

问题Codex 的答案Claude Code 的答案
谁接触工作区workerworker
谁说完成worker 调受限工具独立 evaluator 放行 Stop hook
完成前的主要 guard强 completion-audit prompt + 当前状态检查角色分离 + condition 对 transcript 的复核
最危险的盲点自证，检查面可能比目标窄裁判无工具，证据可能与现场脱节
怎么补把验收项写成可执行 gate，保留独立 CI/人审要求 worker 把命令、退出码和约束证据显式放进对话

所以这里没有一个诚实的“谁赢了”。若任务的权威证据主要在工作区，Codex 的自证链更直接；若最担心 worker 过早收工，Claude 的出口裁判更有价值。真正稳的系统还会把两者都没完全解决的事补上：可执行验收、外部 CI、人工审批、资源上限，以及对“现在说不清”的明确状态。

12 / 结论与边界

结论与边界：Goal Mode 不是更长的 prompt

把主线收回来：Codex 把 goal 变成 thread 上的持久控制面对象，runtime 管状态、计量与续轮，worker 用窄工具申报完成或真正阻塞；Claude Code 把 condition 变成 session 出口的 Stop hook，先避开尚未收束的后台工作，再由独立 evaluator 读 conversation，决定继续、成功结束或以 impossible 失败结束。一个把控制权铺进系统内部，一个把控制权集中在 turn boundary。

这两种设计真正共同的地方，是都不再把“assistant 发了一条 final”当作任务自然结束。长任务需要一个独立于普通回答的停止合同。合同至少要写清四样东西：想要的最终状态，不能破坏的约束，用哪条命令或哪份产物证明，以及何时因为资源或外部依赖停下。目标越含糊，循环越久只会把含糊放大。

产品能力的边界

Codex 的持久状态和完成审计，不保证 worker 每次都能覆盖全部验收项；Claude 的独立 evaluator 能拦住一部分过早停止，却只能判断 conversation 里已经出现的证据。ProposeGoal 又把入口做得更主动，但没有改变这条完成链。哪套设计在同等任务上更少误判，仍要靠同任务、同工具、同预算的对照 eval，而不是架构图替它作答。

最后还有一条很实际的安全边界：/goal 负责让任务跨 turn，不负责替你授权。Claude 明确要求 trusted workspace 且 hooks 可用，未获批工具仍会询问；Codex 也沿用原 permission profile。能连续工作，只代表循环的开关换了位置，不代表机器拿到了更多权力。

一句话模型Codex 把 goal 放进控制面；Claude 把 goal 放在出口。两边都会续轮，开关不在同一层。
别混淆独立 evaluator 不等于独立验收环境。它只看 transcript，没有 shell 和文件视野。
残余风险Codex 贴近真实 worktree，却仍由 worker 自己申报 complete。强提示词不是第二个裁判。
共同边界自动续 turn，不会自动扩大工具权限。Goal loop 和授权系统仍是两层。
