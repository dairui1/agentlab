Code Mode：把确定的步骤交给程序

查三份资料，筛出同一个版本，再把结果拼起来。这中间真的每一步都需要模型再想一次吗？

2026-10-07 · Pi 与 Codex 源码短评

Code Mode
  1. 少一次往返
  2. Pi 已经内置
  3. 脚本怎么结束
  4. 哪里该停下来

我更愿意把 Code Mode 理解成一种分工：模型决定要做什么，程序接手已经确定的步骤。它不是让 Agent 更会写代码，而是让 Agent 不必用一轮轮对话模拟一个循环。

少的不是工具调用，是中间的模型往返

假设要查三个仓库的版本。普通工具调用可以每查一个就把结果交回模型，也可以由 harness 支持批量调用。Code Mode 则让模型写一段短程序：发出查询、提取版本、比较结果，最后只输出差异。工具仍然执行三次；能省掉的是中间那些不需要新判断的往返，以及整份结果进入上下文的负担。

Pi 的 codemode 和 Codex 的 exec 都提供了这种组合入口。收益来自批处理和选择性输出，不来自 JavaScript 这个名字。把十页搜索结果打印回去，上下文照样会涨；把查询、判断、发布硬塞进一次执行，也未必更好。

最近的 Pi，已经不只是一个扩展

搜“Pi Code Mode”容易先找到 Luan 的扩展。可到 9 月 30 日，这个仓库已经移除自建运行时，转用 Pi 0.99 的内置能力；10 月 5 日的配置也直接用了 codemode.mode: "only"。所以讨论近期 Pi，不宜继续把旧扩展当成当前实现。

当前原生实现把脚本放进 QuickJS/WASM，通过注入的工具访问外部世界。工具多了，也不用把所有 schema 一次塞满：脚本可以先 searchTools()，再 describeTool() 看签名。这里有个很实际的修复：main 的未发布记录专门补上这些函数是 async 的说明，否则模型可能把没等完的 Promise 打印成 {}。目录再聪明，调用合同写错，仍然会白跑。

还有一个不能从“沙箱”二字跳过去的区别。Pi 内置工具经 ctx.executeTool() 派发；独立内核的文档却提醒，自己直接调用 tool.execute() 会跳过 Agent 的前后 hooks。Codex 的嵌套调用也进入工具运行时，而不是在 V8 里自己操作文件。限制脚本能碰什么，与检查工具获准做什么，是两件事。具体权限仍要看工具和宿主，不能只看引擎有没有沙箱。

Pi 与 Codex，最值得比较的是结束语义

Pi 每次创建新 VM，脚本结束后把结果交回。它并不保留上一段 JavaScript 的变量；需要接续的小状态用 store/load。这些写入只有脚本成功时才进入会话日志，恢复会话和分支时也沿各自路径读取。

Codex 同样用新的 V8 isolate 执行，但多了一层长任务交接：exec 可以先返回 running cell，模型再用 wait 收集后续输出，或明确终止它。这里的 yield_time_ms 是“多久交还一次控制”，不是“多久判任务失败”。读到 running 时，不该因为这次等待结束了，就把仍在做事的 cell 杀掉。

真正棘手的情况是：工具已经改了文件，脚本随后报错。Pi 的状态写入不会提交，文件修改却不会撤销。两个实现都要求认真等待需要完成的 Promise；脚本结束后，没等完的工作不能靠“我已经发出去了”来保证完成。Code Mode 不是事务。重试前先查副作用，尤其别把“脚本失败”读成“什么都没发生”。

让程序多做一点，不等于让模型少看一眼

我的判断是：独立查询、已知字段的过滤、确定规则的聚合，很适合放进一段短程序。发现陌生接口之后，要先让模型看签名；桌面操作之后，需要看新画面再决定；发布、付款或删除之前，可能需要用户确认。这些停顿不是低效，它们是任务里尚未确定的部分。

过滤还会改变模型能看到的证据。只输出“没有异常”，却丢掉被截断、权限不足和失败结果，模型得到的不是更干净的信息，而是更少的事实。比较稳妥的输出应保留错误、来源标识与截断状态，让后续判断有东西可核对。

值得追的不是“能不能把一切都包进 exec”，而是程序执行到哪里，就该把判断权交回来。要验证收益，至少得用同一模型、同一任务比较正确率、耗时、上下文量和失败恢复成本。本文只核对公开源码，没有运行这样的模型对照，也不把“少一次往返”写成已经测得的提速比例。
