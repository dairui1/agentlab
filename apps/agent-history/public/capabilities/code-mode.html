专题研究/Code Mode

Code Mode

Code Mode 是让 AI 写一小段程序来调用工具，而不是每一步都单独发出工具请求。比如“查三个仓库，找出版本不同的那个”，AI 可以把查询、比较和筛选写进同一段代码，由运行环境执行，最后只读到差异。工具依然在干活，只是中间那些规则已经明确的步骤，不再需要 AI 一次次接手。

同一个任务，两种做法

示例推演 · 三个仓库版本比较
  1. AI 发出查询查 A → 读结果
  2. AI 发出查询查 B → 读结果
  3. AI 发出查询查 C → 读结果
  4. AI 比较C 的版本不同

每份结果回到 AI，由 AI 决定下一步。这是逐个调用的示例；普通工具接口也可以支持批量或并行调用。

  1. AI 写程序查询 + 比较
  2. 运行环境与宿主执行查 A、B、C
  3. 程序筛选只输出差异
  4. AI 读结果C 的版本不同

工具还是查了三次，但中间数据可以留在程序里。少的是不必要的模型往返，不是查仓库这件事。

Code Mode / 从一个任务理解

查三个仓库，需要 AI 想几次？

接到“找出版本不同的仓库”，模型要先理解什么叫“不同”，决定查哪些仓库；真正去读版本的是工具。接下来的比较很简单：把版本号放在一起，按同一个规则筛选。普通工具调用可以把每份结果交回模型，也可以一次提交多个查询；Code Mode 则让模型连后面的比较一起写好。这里值得抓住的变化是谁在决定下一步：规则明确的部分由程序继续，遇到需要理解和取舍的地方再交回模型。它不是让工具更聪明，而是让模型不必亲自经手每一条数据。

  • 多写一段程序，省下了什么？从三个仓库换成三百个，差别开始明显。
  • 那我直接写 Shell 不行吗？分清执行代码、连接工具和组织步骤这几件事。
  • 谁在沿着这条路做？从 MCP 工具编排，到 Coding Agent 的内置能力。

Code Mode / 从一个任务理解

为什么要多写一段代码

查三个仓库，模型自己比较也不费事。换成三百个仓库，每次返回的还是整份配置文件，情况就变了：我们只关心版本差异，却要把大量无关字段塞进上下文，再让模型逐一找出版本号。程序可以在结果刚回来时就取出那个字段，比较完只留下几个异常项；查询之间需要传递的 ID 也可以原样使用，不必让模型重新抄写。Code Mode 想省的是这类搬运。另一个负担出现在调用之前：工具很多时，模型未必需要先读完全部说明，可以找到相关工具再看用法。这些收益各有来源，工具目录做得好、输出筛得准，才会真的省下来。

Code Mode / 从一个任务理解

和 Shell、MCP 什么关系

“写代码调用工具”听起来很像写 Shell，区别要看代码接到了哪里。Shell 天然接着操作系统的命令；REPL 提供交互式求值，可能还保留变量；Code Mode 讨论的是把 Agent 的工具接成程序能调用的函数，让模型用代码组织它们。一个数据库工具即使来自 MCP，也可以在这段代码里被调用：MCP 负责把工具接进来，Code Mode 负责怎么使用它。普通批量调用已经能一次提交几个独立请求，Code Mode 往前多走了一步，允许拿到结果后继续判断和加工，例如“只有版本缺失的仓库，再读取备用文件”。这种按结果往下走的能力，才是单纯打包几个请求所没有的。

所以看一个叫“Code Mode”的产品，先看它能接哪些工具、怎样执行和保存状态，名字本身没有规定这些细节。

Code Mode / 从一个任务理解

这条思路从哪里来

Cloudflare 和 Anthropic 的两篇文章，把这条思路讲得很具体。Cloudflare 在 2025 年 9 月把 MCP 工具变成 TypeScript 接口，让模型写一段代码，再放进隔离环境执行；问题从“模型要发几个工具请求”转成了“给它什么样的编程接口”。Anthropic 同年 11 月继续讨论：工具越来越多、返回值越来越大时，可以按需读工具说明，让代码先处理数据，只把有用的部分带回上下文。到了 Pi 和 Codex，这个想法进入 Coding Agent 的日常执行流程，接下来要解决的就不只是一段代码怎么跑，还有工具权限、会话状态和长任务怎么衔接。

  • Cloudflare · Code Mode2025-09-26，把 MCP 工具表达成代码接口。
  • Anthropic · Code execution with MCP2025-11-04，让工具说明和中间数据按需进入上下文。

Code Mode / 程序如何接手

沿着一次查询走下去

回到三个仓库的例子，这里有三个角色：模型写下查询和比较的规则，程序照着规则往下走，宿主负责真正调用工具。宿主就是运行 Agent、持有工具连接的外层程序。查询结果先送回 JavaScript，等程序筛出差异、调用 text() 输出，模型才重新接手。它拿到的已经是比较结果，可以直接回答，也可以再判断哪个版本该保留。

getVersion 是这个例子假设的查询接口，不是 Pi 或 Codex 的内置工具。

  • 程序怎么知道函数名和参数？先找到工具，再读它真正接受的输入。
  • 哪些动作能放进同一段代码？看数据依赖，而不只是数工具调用的次数。
  • 为什么模型只看到了差异？工具返回值与交给模型的输出，是两个地方。

Code Mode / 程序如何接手

先知道工具怎么用

模型不会因为会写 JavaScript，就自动知道当前会话接了哪些工具。一个搜索结果可能告诉它有“读取仓库”的工具，但参数究竟叫 repo 还是 path，返回的是文本还是对象，还要看完整说明。Pi 把这个过程拆成 searchTools() 找候选、describeTool() 读接口，也能一次查看整个命名空间；Codex 暴露 ALL_TOOLS，在相应配置下还提供工具搜索。找到说明后把它交回模型，再写真正的调用，比猜字段可靠。接口说明本身也会出错：Pi 的未发布修复里，就补过发现函数的异步声明。少写一个 await，读到的可能只是尚未完成的 Promise。

// Pi：先把工具说明交回模型，下一次执行再调用它。
const matches = await searchTools("查找文件");
if (matches.length === 0) {
  text("没有找到匹配的工具");
} else {
  text(await describeTool(matches[0].name));
}

Code Mode / 程序如何接手

把几个动作连起来

三个仓库互不依赖，可以一起查询；“先找仓库，再查版本”有先后关系，就得等第一步返回；“版本缺失时读备用文件”则要根据结果选一条分支。这些关系一旦写清，程序就能自己走完。并发时还要想好一项失败怎么办：Promise.all() 会在某项拒绝后报错，其他已发出的请求却未必停下；Promise.allSettled() 会留下每一项的结果，适合最后报告“两个查到了，一个没查到”。这类代码安排的是请求之间的关系，工具实际能同时跑几个，仍受宿主排队、限流以及资源冲突影响。

// 教学示意：getVersion 是虚构接口。
const names = ["A", "B", "C"];
const results = await Promise.allSettled(
  names.map((name) => tools.getVersion({ name }))
);
text(results.map((result, i) => ({
  name: names[i],
  ...(result.status === "fulfilled"
    ? { version: result.value }
    : { error: String(result.reason) })
})));

Code Mode / 程序如何接手

最后让模型看什么

工具返回给程序的内容，可以比模型最终看到的多得多。查到三百份配置，程序只输出三个版本差异，这是有用的筛选；可如果还有十个仓库没查到，却在输出时一并丢掉，模型就可能误以为其他仓库都一致。因此输出要围绕下一步判断来选：保留差异，也交代比较基准、查了多少、哪些没查成。检查错误时也要读返回值，不能只等异常，Pi 的命令工具会正常返回非零退出码，MCP 工具也可能在结果里标记 isError。文字通过 text() 交回，图片通过 image() 交回。Code Mode 的价值就在这里，但能不能筛对，和能不能查到一样重要。

// 输出示意，数值为教学假设。
{
  "baseline": { "name": "A", "version": "1.2" },
  "checked": 3,
  "differences": [{ "name": "C", "version": "1.3" }],
  "failed": []
}

Code Mode / Pi、Codex 怎么做

同样写 JavaScript，接法并不一样

理解了程序怎么接手，再读 Pi 和 Codex 的实现就容易了：它们都提供 tools 给代码调用，也都让程序自己决定输出什么，但把程序接入 Agent 的方式不同。Pi 的 codemode 很贴近现有会话，工具从会话取，成功后的少量状态也写回会话；Codex 的 exec 则把一次执行叫作 cell，代码没跑完时可以先交还控制，随后用 wait 继续等。这个差别会直接影响长任务怎么处理、下一段代码怎么接续。所以不能只看见两边都写 JavaScript，就把脚本原样搬过去。

写脚本时会遇到的问题PiCodex
把代码交给谁codemodeexec，未完成时再 wait
代码在哪运行新的 QuickJS / WASM VM新的 V8 isolate
怎样把内容交回模型text()、image()，顶层 return 也可输出text()、image() 等显式输出函数
怎样保留小状态成功后把 store 变更记入会话分支store/load 在同一会话的执行之间接续
  • Pi：沿会话走进运行时工具怎么选出来，结果和状态怎么回来。
  • Codex：一段还没跑完的程序exec 返回以后，cell 和工具请求去了哪里。

Code Mode / Pi、Codex 怎么做

Pi：嵌入现有会话

Pi 的原生实现没有另造一套工具。它先从当前会话里取出可调用工具，把它们接进一个新的 QuickJS VM；脚本调用 tools 时，请求再通过 ctx.executeTool() 回到会话执行，返回值转成 JavaScript 能继续处理的内容。这样，读文件、执行命令或调用 MCP 工具，都能串在同一段脚本里。需要留给下一段的小数据，用 store() 保存，只有脚本成功且状态发生变更时才写入会话记录，切换分支也跟着各自的记录走。这里研究的是 Pi 原生能力：Luan 的配置已经迁移到它，网上其他同名扩展则需要另看实现。

// execute.ts 中工具调用的关键语句，省略记录逻辑。
const outcome = await ctx.executeTool(tool.name, args, {
  signal: callSignal,
});
return toScriptValue(tool, outcome);

Pi 还通过 models 接入分类与图像模型；普通对话模型虽然可出现在目录里，不能从脚本里调用。本文使用的 main 快照含 1.0.4 之后的未发布改动。

Code Mode / Pi、Codex 怎么做

Codex：exec 与 wait

Codex 把一次 exec 当作一段可以持续运行的程序：代码在新的 V8 isolate 中执行，工具请求交给宿主。假如它还在等图像生成，exec 可以先交还控制权，给模型一个 cell ID；下一次用 wait 接着等的，仍然是原来的程序。理解这一点，就不会把“返回了”误当成“结束了”，更不会重复提交任务。

这描述的是本文固定的 Codex main 源码；具体产品是否启用此入口，要以那次会话暴露的工具为准。

Code Mode / 交出去以后谁负责

把步骤交给程序，也要知道它能走多远

到现在，例子一直在查数据。把任务换成“找出版本不同的仓库，并更新配置”，就得追问几件事：生成的代码能否直接读写电脑？通过工具改文件时，谁检查权限？文件改了一半程序报错，下一次还能记得哪些动作？这几个问题分属不同地方。沙盒约束代码本身能接触的环境，宿主处理工具请求，状态记录帮助后续执行接续，取消则尝试让仍在运行的工作停下。它们要配合起来看；一个环节做得好，不能替其他环节回答问题。

  • 代码和主机之间隔着什么？没有文件接口的程序，仍然可以通过工具改文件。
  • 谁来批准真正的动作？检查点应跟着工具请求走，而不只看外层脚本。
  • 下一段代码从什么状态开始？变量、会话记录和真实文件，保存方式不同。
  • 一直等不到结果，怎样停下来？交还控制、超时和取消，各自结束了什么。

Code Mode / 交出去以后谁负责

沙盒隔开了什么

Pi 把生成的代码放进 worker 里的 QuickJS / WASM VM，Codex 使用 V8 isolate；两者都不直接提供 Node、文件系统或网络访问。但代码仍然能通过工具读文件，因为真正读取的是沙盒外的宿主。沙盒限制了代码直接接触主机的能力，工具则有意开放了一条通路。判断它能做什么，要继续看这条通路接的是只读查询，还是能改文件、运行命令的工具。

Pi 为脚本 VM 设置 256 MB 内存，通过中断标志和终止 worker 处理停止请求；整段执行的 timeout_ms 需显式设置，默认没有期限。这里核对的是源码安排，没有做沙盒攻防测试。

Code Mode / 交出去以后谁负责

谁允许工具动手

如果一次普通的文件写入需要检查路径、请求用户批准，把它放进 Code Mode 后也应该经过这些检查。否则只批准“运行一段 JavaScript”，就可能顺带放过里面几十次写入。关键在工具请求怎样回到宿主：Pi 原生实现走会话的 ctx.executeTool()，Codex 把内部请求送进共享工具运行时；Pi 独立内核的文档还特别提醒，集成者若直接调用 tool.execute()，会跳过 Agent 的前后 hooks。这也解释了为什么研究权限不能停在“使用了某个沙盒”：同一个执行内核，用不同方式接工具，检查路径就可能改变。

目前沿源码确认了派发入口与这项接入警告，尚未逐个审计所有工具的授权流程。

Code Mode / 交出去以后谁负责

下一次还记得什么

这一段查到的仓库 ID，下一段还要用，就得通过 store/load 留下来：Pi 和 Codex 每次建立新的执行环境，普通变量不会自动保留。还要分清第三处状态，也就是工具已经改过的文件。以 Pi 为例，store 的变更要等整段脚本成功才写入会话，文件却在工具执行时就改变了。两处状态可能停在不同位置，这正是失败后不能直接重跑的原因。

Pi 的 store 跟着会话分支恢复；Codex 约定同一会话内可接续，跨进程恢复尚未核验。

Code Mode / 交出去以后谁负责

等不到结果怎么办

一个远端任务很慢，首先要分清是“暂时没有新输出”，还是“已经停止执行”。在 Codex 中，yield_time_ms 只决定等待多久先交还控制；收到 running cell 后，应该拿同一个 ID 调 wait，而不是再次提交任务。真要停下，用 terminate: true；Pi 则可以用 timeout_ms 限定整段脚本的期限。写代码时也要把该等的 Promise 等完，两种实现都不会因为你发出了请求，就自动保证它在脚本结束后继续完成。即使取消成功，远端已经接受的操作或已经写下的文件也未必撤销。重新开始前，先查结果，而不是先重发。

Code Mode / 怎样判断值得用

读懂实现以后，还要问什么

Code Mode 把一部分工作从模型搬到了程序里，但搬过去就更好吗？查三百个仓库可能很合适，只点一次按钮则未必值得额外写代码；一切顺利时省了几轮，出错后也可能要花更多时间查清哪一步已经执行。因此我们更关心它改变了什么任务，而不是接口看上去有多简洁。这会引出四个相连的问题：哪些任务真的更省，失败以后能不能接着做，Harness 要怎样保留过程，以及模型需要学会哪些新的判断。前面的源码能帮助设计比较，下面这些结论则要靠实验回答，本文还没有跑过这些对照。

  • 省下的往返，抵得过写代码的成本吗？把任务做对所花的总时间算进去。
  • 报错以后，还能接着做吗？看得见已完成的动作，才知道该重试哪里。
  • Harness 需要留下哪些记录？模型少读一些，不应让系统也少知道一些。
  • 模型怎样学会用好这套接口？既要会编程，也要知道何时交回判断。

Code Mode / 怎样判断值得用

什么任务更划算

最有希望的任务，是中间数据很多、处理规则又能提前说清的任务：查一批仓库、从日志中挑出错误、把几份结果按 ID 合并。相反，如果每一步都要看新画面再决定下一步，程序很难替模型多走几步；只做一次简单读取，发现工具和写代码甚至可能多花时间。比较时应该让同一个模型，用同样的工具和权限，分别尝试普通调用、批量调用和 Code Mode，把发现工具、生成代码、重试直到验收的时间全算进去。成功率相近后，再看耗时和 token 才有意义。否则一次失败得很快的执行，也会显得格外“高效”。

这里提出的是对照方法，不是性能结果。特别要保留批量调用这一组，避免把并发本身的收益全部算给 Code Mode。

失败后从哪里接着做

假设一段程序要更新三个仓库：A 已经写入，B 被权限检查拦下，C 还没开始。这时收到“脚本失败”，正确的下一步不是把代码再跑一遍，而是先确认 A 的改动，再处理 B，最后决定 C 是否继续。语法错误通常发生在动作之前，工具报错可能发生在中途，脚本全都跑完也可能改错版本，恢复方式自然不同。一个有用的实验是故意在首次写入之后制造异常，看系统能否从工具记录、部分输出和实际文件里找回进度，而不只会重试整段代码。把这些情况接住，才能谈长任务里的可靠性。

Harness 要多管什么

模型能发出请求，工具能执行动作，中间负责把它们接成一个持续工作系统的，就是 Harness。引入 Code Mode 后，它看见的最外层请求是一段代码，里面却可能藏着很多次查询和写入。如果日志只剩“exec 成功”，以后就很难回答到底改了哪个文件、用什么参数、在哪一步获得批准。更合理的做法是保留两层记录：外面是脚本、输出和结束原因，里面是每一次工具请求及其结果，彼此能对应起来。Pi 的内部调用记录和 Codex 的 cell / tool-call 身份提供了这种联系的入口；据此做审计与恢复，还需要继续把各个检查和动作记录齐全。模型可以少读中间数据，Harness 不能因此丢掉事实。

模型需要学会什么

会写 JavaScript 只是起点。模型还要判断哪些步骤值得合在一起、什么时候必须停下来读结果、出了错该留下什么信息。例如版本查询里漏掉一个失败仓库，代码照样可以正常结束，回答却会误导用户。如果要训练这种能力，奖励就应该检查任务的真实结果，而不只奖励代码能跑、调用次数少。评测也可以换一套工具命名和返回值，看看模型能否读懂新说明，还是只记住了旧接口。Code Mode 在这里提供了一种行动方式；只有再引入任务反馈、训练数据或奖励驱动的学习过程，才进入训练问题。本文没有运行这类实验，也没有据此判断 Pi 或 Codex 的训练收益。
