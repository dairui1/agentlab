专题研究/Code Mode

Code Mode

Code Mode 是让 AI 写一小段程序来调用工具，而不是每一步都单独发出工具请求。程序可以接着上一项结果做下一步，也可以循环、并发和筛选，最后只把需要的结果交回 AI。比如“查三个仓库，找出版本不同的那个”：AI 写好查询和比较的代码，运行环境执行它，AI 再根据差异回答你。

同一个任务，两种做法

示例推演 · 三个仓库版本比较
  1. AI 发出查询查 A → 读结果
  2. AI 发出查询查 B → 读结果
  3. AI 发出查询查 C → 读结果
  4. AI 比较C 的版本不同

每份结果回到 AI，由 AI 决定下一步。这是逐个调用的示例；普通工具接口也可以支持批量或并行调用。

  1. AI 写程序查询 + 比较
  2. 运行环境与宿主执行查 A、B、C
  3. 程序筛选只输出差异
  4. AI 读结果C 的版本不同

工具还是查了三次，但中间数据可以留在程序里。少的是不必要的模型往返，不是查仓库这件事。

这段程序长什么样
// 教学示意：版本工具是虚构接口，不是 Pi / Codex 内置工具。
const names = ["A", "B", "C"];
const rows = await Promise.all(names.map(async (name) => ({
  name, version: await tools.getVersion({ name })
})));
text(rows.filter((row) => row.version !== rows[0].version));

假定返回 A=1.2、B=1.2、C=1.3，输出就是 C=1.3。以 A 为基准比较，并未断言哪个版本正确。

Code Mode / 认识 Code Mode

先认识这件事

AI 不会因为生成了“查询数据库”几个字就查到数据。需要外部程序识别它的请求，执行工具，再把结果送回来。Code Mode 改的是请求的形式：AI 不只给出一次调用的参数，还能写出连接多次调用的程序。工具和数据来源并没有消失，多出来的是一个执行这段程序的运行环境。

  • 为什么会出现工具目录、模型往返与中间数据
  • 与相邻概念的区别普通调用、批量调用、Shell、REPL、MCP
  • 来路与相关工作Cloudflare、Anthropic 与程序化工具使用

Code Mode / 认识

为什么会出现

有些工作需要 AI 判断，有些只是在搬运和整理数据。读取一千条记录再筛出三条，没必要先让模型读完一千条；从一个接口取得 ID 再传给另一个，也未必需要模型重写它。Code Mode 把这部分交给程序，同时可以按需发现工具，缓解工具说明和中间结果占用上下文的问题。

收益到底来自哪里

少加载无关工具说明，少让中间结果进入模型，少做无需新判断的模型往返。这三项应分别衡量，并非每个实现都同时具备。

Code Mode / 认识

它与其他方式有什么区别

Code Mode 是组织工具使用的方式，不是一种语言，也不是 MCP 的替代品。普通调用把一次请求交给宿主；批量调用把几次请求一起交过去；Code Mode 还允许程序根据结果循环、分支和加工数据。Shell 或 REPL 也能执行代码，但能访问什么工具、保留什么状态、如何限制权限，要看具体接入。

概念负责什么别混淆的地方
工具调用请求执行功能可以批量，并非必然一轮一个
Code Mode用程序组织工具与数据里面仍会发生工具调用
Shell运行命令或程序不自动拥有宿主工具目录
REPL交互式代码求值是否持久、是否受限没有统一保证
MCP连接工具与资源的协议可直接调用，也可在代码中调用
工作流安排步骤与依赖可预写，也可由模型生成

来路与相关工作

“让模型写程序来用工具”不是某一家独有的点子。Cloudflare 在 2025 年 9 月的 Code Mode 文章中，将 MCP 工具转为 TypeScript API，让模型写代码调用；Anthropic 同年 11 月讨论了用代码访问 MCP、按需加载工具和处理数据。Pi 与 Codex 是这条思路在 Coding Agent 中的实现。这里列的是相关路线，不是发明优先权的判定。

Code Mode / 工作过程

一次调用怎样工作

模型先知道有哪些工具、怎样传参，再生成程序。运行环境执行代码，遇到工具调用时请求宿主执行，结果返回程序继续处理；程序通过输出函数把选中的内容交回模型。模型可能回答用户，也可能写下一段程序。这不是把模型放进循环里，而是把一部分循环移到了程序里。

  1. 模型读工具签名
  2. 模型生成程序
  3. 运行环境与宿主执行工具和处理数据
  4. 模型读选出的结果
  • 发现工具与读签名目录、参数、返回值
  • 组合、分支与并发哪些步骤可以一起做
  • 哪些结果交给模型数据过滤与证据保留

Code Mode / 工作过程

先找到工具，再看它怎么用

工具名不是完整说明。写程序前需要知道参数和返回值，否则可能工具找对了，却读错字段。Pi 提供异步的 searchTools()、describeTool() 和 describeNamespace()；Codex 合同列出 ALL_TOOLS，并在相应目录模式下提供搜索指引。发现是找候选，读签名才足以开始调用。

Pi 的发现代码与近期修复
const matches = await searchTools("查找文件");
text(matches);
// 实际程序还需处理空结果。
text(await describeTool(matches[0].name));

main 的未发布记录修复发现函数漏写 async 的说明，否则模型可能把 Promise 打印成 {}。

Code Mode / 工作过程

程序怎样连接多个动作

独立查询可以并发，依赖上一项结果的调用必须等待；重复结构可以循环，结果不同可以走不同分支。这是程序的控制流，不需要每一步交给模型重新生成。但“能并发”不代表工具一定同时执行：宿主可能排队或限流，操作相同文件或远端数据时还可能出现竞争。

并发不等于整体成功
// 教学示意：两个独立读取。
const [a, b] = await Promise.all([
  tools.read({ path: "a.json" }),
  tools.read({ path: "b.json" })
]);
text({ a, b });

Promise.all() 在一项拒绝时整体拒绝，却不自动撤销其他调用。想保留各项结果，可以用 Promise.allSettled()。

Code Mode / 工作过程

模型看见什么，由输出决定

工具结果先回到程序，不必全部回到模型。程序可只输出字段、统计结果或图片，减少无关数据和重新抄写。但输出也是证据选择：只留下“成功”，丢掉错误、截断和来源，后续模型就可能误判。过滤数据与隐瞒失败不是同一回事。

不同返回值不能当成同一种成功

Pi 的结构化工具可能返回包含错误标识的值，而不抛异常。MCP 的 isError、命令退出码和脚本异常是不同层的失败。图片用 image() 交回，不把 base64 当文本打印。

Code Mode / 具体实现

Pi 与 Codex：同一思路，不同合同

两者都让模型写 JavaScript 组合工具，但一家的脚本不是另一家的合同。Pi 原生 codemode 用 QuickJS/WASM，成功后把小状态写入会话；Codex exec 用 V8 isolate，配合 wait 接续未结束的 cell。入口、可用函数、状态保存与长任务交接需要分别读。

Code Mode / 实现

Pi 原生 Code Mode

Pi 从会话工具集建立可调用函数，程序在独立 QuickJS VM 中执行。工具请求通过 ctx.executeTool() 回到宿主，结果返回程序；脚本成功时，才把 store() 的修改写入当前会话分支。Luan 的旧扩展已转用原生能力，不能把它与其他同名扩展混作一个实现。

沿源码走一次派发
// execute.ts：关键语句摘录，中间记录逻辑省略。
const callable = ctx ? getCodemodeCallableTools(ctx.tools) : [];
const outcome = await ctx.executeTool(tool.name, args, { signal: callSignal });
return toScriptValue(tool, outcome);
// 只有 result.ok 才追加状态 entry。
result = await sandbox.execute(code, { signal, store });

会话决定能调用什么，内核执行代码和往返消息。

Code Mode / 实现

Codex exec / wait

Codex 的 exec 接收原始 JavaScript，在新的 V8 isolate 中执行，通过 tools 请求宿主能力。嵌套调用被转换为工具运行时的请求，保留 cell 和调用身份。程序可以先交还输出而继续运行，模型再用 wait 接续，比只等待整段结束多了一层生命周期管理。

嵌套调用进入共享工具运行时
// mod.rs L405-L415
let result = tool_runtime.handle_tool_call_with_source(
    step_context,
    call,
    ToolCallSource::CodeMode {
        cell_id: cell_id.to_string(),
        runtime_tool_call_id,
    },
    cancellation_token,
    Arc::default(),
);

这确认路由入口，不是权限安全的完整证明。当前产品是否启用这条路径，也不能由 main 源码推定。

Code Mode / 执行边界

程序在哪里运行，能做到哪一步

模型生成的程序需要执行，但不能因此任意读取主机、联网或取得凭据。运行时限制代码能接触什么，宿主决定工具能做什么；状态保存决定下一次怎样接续，生命周期决定何时结束。“用了沙盒”不能替代这四项检查。

  • 沙盒与运行时隔离、资源、宿主桥接
  • 工具权限与检查能力暴露不等于动作授权
  • 变量、状态与持久化一次执行与下一次之间
  • 等待、结束与取消交还控制不是任务超时

Code Mode / 执行边界

沙盒与运行时

沙盒把生成的代码与宿主隔开，只开放选定的入口。Pi 把 QuickJS 编译为 WASM，在 worker 中启动新 VM，工具请求通过消息桥回到宿主；Codex 合同使用新的 V8 isolate，不提供 Node、文件系统或网络访问。限制直接访问不意味着工具没有这些能力：工具仍可能执行命令或修改远端数据。

Pi 的资源与中断机制

原生工具给 VM 256 MB 内存；timeout_ms 可设置整段脚本期限，默认不设。宿主持有 deadline 与 abort signal，以共享中断标志配合终止 worker，避免 WASM 无限循环拖住宿主。QuickJS 是解释器，轻量编排和大量计算是不同负载。

代码里，工具怎样穿过沙盒
// worker.ts L52-L62：新 VM 及其资源、中断配置。
const vm = await QuickJS.create({
  wasm: data.wasm,
  memoryLimit: data.memoryLimitBytes,
  maxStackSize: MAX_STACK_SIZE,
  interruptHandler: () => Atomics.load(interrupt, 0) !== 0,
  wasi: discardOutput,
});
// bridge 发出 call 消息，host.ts L276-L280 从注册表取工具。
const tool = (isTool ? this.tools : this.globals).get(name);
const value = await tool.execute(args, { signal: pending.controller.signal });

这是不同文件的关键语句摘录，不是一段可直接运行的脚本。工具函数留在宿主，沙盒获得的是请求通道，而不是宿主的全部环境。

Code Mode / 执行边界

工具权限与检查

能调用函数，只表示入口被暴露，不表示可以无条件完成动作。读写权限、用户审批和前后检查要在宿主派发时落实。Pi 内置实现经会话接口派发；自行接入独立内核若直接调用 tool.execute()，会跳过 Agent 的前后 hooks。集成方式因此是权限研究的一部分。

读代码时要追到哪一层

沿“目录 → 参数校验 → 前置检查 → 审批 → handler → 结果记录”逐项核对。本专题确认派发入口，未审计所有工具的授权链，也没有做沙盒逃逸实验。

Code Mode / 执行边界

变量、状态与持久化

一段代码的变量不自动成为下一段的记忆。Pi 和 Codex 都为一次执行建立新环境，以 store/load 保存可序列化小状态。Pi 只有脚本成功才提交修改，并随会话分支恢复；Codex 合同说明同会话接续，本专题未核验跨进程恢复。会话记忆与已修改的文件还必须分开看。

状态提交与副作用并不同步

假定脚本改了文件、写入 store，然后抛错：Pi 不提交此次 store，但文件仍然改过。上一次成功的 store 可能落后于现实。Code Mode 不是事务，核对文件或远端回执再重试。

Code Mode / 执行边界

等待、结束与取消

“这次等待结束”不等于“任务结束”。Codex 的 yield_time_ms 决定多久先交还控制；收到 running cell 后，wait 继续收集输出，terminate: true 才明确停止。Pi 提供整段脚本的可选 deadline。两者都不能靠未等待的 Promise 保证完成，更不能把取消解释成外部动作已撤销。

三种结束要分别记录
  • 成功：程序返回，不代表任务验收通过。
  • 失败：保留部分输出，核对已经发生的动作。
  • 取消或超时：外部服务可能已经完成请求。

Code Mode / 研究问题

我们关注的，不只是能运行

Code Mode 是否值得使用，取决于任务、模型与宿主。能执行代码只是起点：还要比较是否更省、更准确，失败后能否恢复，工具记录是否可追踪，训练是否适应执行合同。下面是基于机制提出的研究判断和实验方向，不是已经测得的结论。

  • 性能与适用任务省下的成本是否超过新成本
  • 错误与恢复程序、工具与任务三层失败
  • Harness 设计目录、派发、轨迹与接续
  • 训练与评测从调用参数到完整小程序

Code Mode / 研究问题

哪些任务真正受益

机制上，重复查询、大结果筛选与确定规则的聚合是合理候选；只有一个简单动作，或每一步都要看新画面时，收益可能有限。生成代码、发现工具、启动环境和调试也花时间。模型往返更少不自动等于总耗时更低，必须在同一任务里比较。

一个可检验的对照

固定模型、工具、权限和任务，对比逐个调用、批量调用与 Code Mode；记录成功率、总耗时、token、发现成本与恢复次数。按单动作、重复查询、大结果和副作用任务拆开统计。没有运行这样的对照，不能宣称提速比例。

Code Mode / 研究问题

失败后，究竟重做什么

语法错误、工具拒绝和任务结果错误是三层失败：代码跑通不表示工具成功，工具成功也不表示用户目标达到。“文件已改，下一步报错”时，整段重跑可能重复写入。先确定哪些动作已经发生，再重做缺失部分，而不是把脚本失败当作从未开始。

值得做的故障实验

在首次写入后注入异常；取消远端请求；让并行查询一项失败；返回带错误或截断的结果。检查副作用、输出、store 和嵌套记录能否拼回同一个现场。

Code Mode / 研究问题

对 Harness 设计意味着什么

Harness 是连接模型、工具与执行环境的程序。引入 Code Mode 后，既要执行生成的代码，也要管理里面的每次调用。我的设计判断是：不能只保存“脚本成功”，还要追踪工具身份、审批、耗时、错误和副作用。模型可以少看中间数据，宿主却不能失去审计和恢复需要的事实。

两层轨迹，而不是一个状态灯

外层记录代码、运行身份、输出与终止原因；内层记录每个工具的参数、授权和结果。Pi 记录嵌套调用状态，Codex 保留 cell/runtime-tool-call 身份，但入口不等于完整审计产品。这是基于源码的设计推断。

Code Mode / 研究问题

对训练与评测意味着什么

模型需要学的不只是填调用参数，还包括读签名、写控制流、处理返回值和选择输出。该奖励短代码，还是任务成功、证据完整与可恢复？这里列为研究方向：使用 Code Mode 本身不是 Agentic RL，也没有证据说明某个实现已经带来更好的训练效果。

可研究，但尚未证明

用可重置任务比较不同工具合同下的迁移；让训练与测试使用不同命名、错误形状和状态语义，避免只记住 API。奖励应检验外部结果与权限，而不只看脚本退出成功。本专题没有运行训练或 RL 实验。
