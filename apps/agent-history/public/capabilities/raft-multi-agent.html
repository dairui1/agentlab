Raft 多智能体

从一篇博客，读到 Inbox 与 Held Draft 的实现

AgentLab · 源码阅读2026 年 9 月 26 日约 12 分钟

A 正准备发出“我来发布”，人类却刚刚补了一句“先别发布”。消息晚到几秒，合作就可能变成事故。Raft 试着在发送之前，给 Agent 一次重新看清现场的机会。

这篇从 Tenny 的 Is Having Agents in the Room Meant to Be Chaotic? 出发。不过，我们不把产品解释当作实现证据：往下看的是 CLI、daemon 和 server 怎样共同完成一次发送，以及哪些地方仍然留给模型自己判断。

问题不只是“谁先说话”

原文从一群 Agent 重复报数讲起，提出两个设计：Inbox 让 Agent 选择何时取用信息；Held Draft 在发送前检查上下文，过期就先保留草稿。它关心的不是给每个 Agent 排一个固定座次，而是推理与行动之间出现了哪些变化。

源码阅读要再往前追问一步：谁知道 A 看到了哪里？谁拦住发送？拦下来的内容存在哪里？这三个问题，对应了三个不同的责任方。只看一段 Prompt，回答不了它们。

原文配图：Raft / Tenny 的重复报数示意动画。它是设计演示，不是本文捕获的实验。

Inbox：知道有消息，和读过消息，是两回事

先看最短的一条路径。raft inbox check 要求当前是 managed runner，然后请求 daemon 的 inbox 接口。代理从待处理队列投影出目标列表和数量，连同 app items 返回。这条路径没有把所有正文一股脑塞进工作上下文，也不消费这些消息。[01][02]

但另一个名字很像的命令，做的事不一样。

先看哪里需要注意
raft inbox check
查看待处理目标摘要，不 drain，也不等于读过正文。
取出待处理消息
raft message check
非阻塞 drain，输出消息。它可能只拿到稀疏事件，因此不把最高 seq 写成连续已见游标。[03]
读某个目标的历史
raft message read --target <target>
普通历史窗口可以推进该目标的读取边界；--around 定位查看则不会。线程与父频道也不共用这条游标。[04]

假设 A 看到了 seq 100 的一条 mention，却没看过 seq 99 的撤销指令。如果系统只记“最大已读是 100”，99 就被悄悄划过去了。message check 不推进连续边界，正是为了避免把一次稀疏取消息误当成完整读过历史。

这比“有一个收件箱”更有参考价值：通知、正文可见性和连续读取进度，应该是不同的状态。后面的发送检查，靠的正是这种区分。

发送：本地先看一次，服务端再核一次

这条调用链可以从 CLI 的 messages.sendV2 往下追。daemon 代理并不只是补上凭据再转发，它会按目标拿到 pending messages 和 model-seen 边界，交给 planAgentInboxSideEffect。[05][10]

CLI
提交草稿与边界
请求包含正文、目标、草稿计数；存在可用读取边界时，附上 seenUpToSeq。
Daemon
本地预检
目标下还有未见的 pending 消息时，可以返回 local_hold。已见消息与未见消息分开处理，而不是只比较一个全局数字。[06]
Server
Freshness 检查
收到请求后，按目标检查边界之后是否还有新内容。非线程路径使用该 Agent 的 attention facts，线程路径使用消息锚点；它不是“整个房间所有事件”的简单版本号。[08]
Server
真正提交
需要 hold 就返回并结束；没有 hold 才继续调用 broadcastAndDeliver。[13]

两次检查不是同一件事做两遍。本地层能看到机器已经接下、但模型还没消费的上下文；server 则再用目标侧状态核对一次。某个本地分支选择 forward，只能说明它把决定交给了上游，不能说整条链路已经放行。

这里的 seen，是协议状态

它表示系统按某种规则记录了可见或读过的范围。它没有测量模型是否理解，更没有证明模型会服从“先别发布”。把这条边界当作理解证明，会高估 freshness 能提供的保证。

草稿：不是失败重试，而是重新做决定

最容易写错的客户端逻辑，是看到 HTTP 200 就记作“发送成功”。Raft 的 hold 响应也可能是 200，但状态为 held。CLI 会保留草稿，抛出 SEND_HELD_AS_DRAFT，并明确设为 retryable: false。这不是让网络层不加判断地重发。[10][13]

草稿落在 CLI 的本地状态中，按 Agent 和 target 保存；除了正文，还保存附件、mentions、时间、重复 hold 次数和读取边界。默认寿命是十分钟，读取草稿时检查是否过期。成功发送后才清掉它。[11]

沿发送实现，能找到几条明确的后续路径：

  • 改内容：普通 send 写入新的草稿，仍走发送检查。
  • 内容不变：--send-draft 读取保存的草稿，重新检查新鲜度。
  • 不再说：不继续发送；草稿之后会按 TTL 规则过期。
  • 明确绕过：--send-draft --anyway 让请求携带 continueAnyway。这个选择不是“通过了检查”，而是决定不让过期检查阻止发送。[07][08]

实现里还有个小但重要的区别：重复 hold 达到条件后，server 会建议 anyway；可实际绕过分支并没有把“已经 hold 三次”当成硬授权条件。界面建议何时绕过，与后端何时允许绕过，不是一回事。[15]

实现里的边界，比博客里的概念更具体

只展示三条，却可以推进整批边界

这是这次源码阅读最值得停一下的地方。server 的普通 hold 返回有界上下文，并报告省略了多少条。上游有一项测试构造五条新消息，断言只展示最后三条、省略两条，同时按这一批的最新序号确认读取。实现注释把它定义为聊天式的 read-through。[09][12]

于是，不能把所有层的 seen 都解释成“每条正文都进入过模型”。本地精确已见集合防的是稀疏消息跨越未见内容；server 的有界 hold 又选择了另一种取舍：限制上下文大小，告知有省略，并提供补读线索。省略的那条恰好是关键约束时，仍要看 Agent 是否补读。本文没有运行实验来回答它。

正常 CLI 会请求检查，不代表所有旧 API 都会

CLI 默认发出 draftReholdCount，会参与 freshness 请求判断。server 仍然有开关、请求字段与 force 模式的条件。缺少这些标记的 legacy 请求，不能被概括成“一律检查”。审核隔离的 withheld 模式则是另一条分支：可以返回 hold 信息，但不把新正文泄露给审阅者。[07][09]

发送前检查，不等于全局串行化

路由先求出 freshness 结果，再调用提交函数。仅凭这段顺序代码，不能宣布两个并发请求永远不会在检查与提交之间交错。要确认这一点，需要人为卡住检查后的时刻，让两个请求同时继续，再观察结果；普通的顺序请求测试回答不了这个问题。[13]

同样，暂缓“我来发布”这条消息，不会自动撤回已经执行的 shell 命令。消息协议能让 Agent 重新考虑，主机权限、外部系统幂等性和副作用验收仍然需要各自的机制。

多智能体的分工，不能只看谁调用了谁

我更愿意把这组实现看作共享工作区的协作协议：不是由一个总控 Agent 替所有人排好行动，而是让每个执行者在读取和提交时获得必要的信息，同时把可恢复的状态交给确定性代码保存。

但“没有总控 Agent”并不等于“没有协调基础设施”。这里仍有 server、daemon、消息序号、读取边界与草稿状态。到了“这项工作归谁”，Raft 又用 canonical task 的 revision 与可认领条件约束 claim；这与 freshness 是两套不同的保证。任务记录被认领，也没有替所有执行者锁住文件。[14]

值得借鉴的不是让更多 Agent 开口，而是把“看见了什么”和“准备提交什么”放进同一条可检查的协议。

接下来最有价值的验证，不是再画一张 Agent 拓扑图，而是做三件小实验：在并发检查与提交之间插入 barrier；把撤销指令放进被省略的消息；在相同模型和任务下比较重复执行、hold、override、耗时与 token 成本。它们目前都是待验证项，不是本文已经得到的结果。

关于 runtime 接入、任务认领、记忆恢复和权限，可继续读 Raft 协作架构研究。那一页保留完整横向范围；本文只追踪这篇博客引出的发送链路。
