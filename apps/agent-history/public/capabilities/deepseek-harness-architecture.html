要让 Agent 从本机改到远端环境工作，只把“读文件”换掉是不够的。如果文件从远端读，Bash 却还在本机执行，模型看到的目录和命令改动的目录就不是同一个。

DeepSeek Harness 为这类改动留出了替换位置：文件、进程、模型、工具和任务循环各自有接口，由插件提供实现。本文先解释插件如何组成一次运行，再看请求和历史怎样穿过它们。远端环境是帮助理解架构的例子，不是本次已执行的部署。

01 / 整体模型

整体模型：换执行环境，不先改循环

这里没有一个必须承包所有功能的大循环。模型适配器、工具注册表、会话日志，连默认 Agent Loop 都由插件提供。上层依赖约定的接口，而不是直接绑住某个实现；所以换文件系统时，不必先去重写循环。

负责装配这些插件的是 Cordis。插件把服务注册到共享上下文 ctx，也可以监听带明确数据类型的事件。注册时留下清理函数，卸载时反向撤销；源码把这套生命周期登记叫作 effect。这样，装进去的能力也有明确的撤出方式。

读源码时，先找某项能力的接口，再找提供它的插件和使用它的工具。默认 agent-loop 只是驱动请求的一种实现，并不是每种新能力都必须改动的地方。可替换也不等于随意拼装：远端文件和本机命令错配的问题，仍要由配置者避免。

02 / 启动组合

启动组合：这次到底加载哪些插件

“仓库里有这个插件”和“这次运行用了这个插件”是两回事。启动时选择一套命名配置，项目称为 Profile；它先加载预先打包的插件组合 Bundle，再叠加配置覆盖 Patch。内置 web 和 headless 共用基础组合，区别主要在用户或外部程序怎样调用它。

覆盖有先后：bundle、profile 自己的 cordis.patch.yml、home patch，最后是命令行 --patch。后来的配置可按行标识覆盖前面的值。因此，即便选了同名 profile，两台机器的最终插件组合也可能不同。

层负责什么最容易看错的地方
Bundle分发一组 Cordis rows 与对应插件代码它是默认组合，不是不可修改的内核
Profile patch定义这套 profile 的用户差异同名 profile 在不同 home 中可能不同
Home patch给全部 profile 追加本机政策只读仓库看不到它
CLI overlay本次启动的最后覆盖静态模板不能证明最终值

确认实际运行组合，要看该机器输出的最终配置 --dump-config。本研究没有这份运行记录，只能说明内置模板和组合规则，不能替某次部署断言它加载了什么。

03 / 核心脊柱

核心脊柱：一条请求怎样分给六个服务

用户或外部程序先通过 Agent 接口提交工作。默认 Agent Loop 驱动每一轮：从 Session 取历史，让 System Prompt 组装指令与工具描述，再通过 LLM 适配器请求模型。模型要求调用工具时，Tools 负责找到当前 Agent 可用的工具并检查执行条件。

这就是默认核心的六种职责。Web 界面、SDK、ACP 客户端和 headless 命令都能调用同一个 ctx.agents，不必各写一套模型循环。但会话历史能保存下来，正在运行的 Agent 对象不能跟着进程一起保存；下面把两者分开。

SERVICE GROUP · STATE

Session 与 Agent 保存不同种类的状态

ctx.sessions 持有 append-only 事件历史；ctx.agents 持有活着的 Agent handle。前者可持久化和重放，后者属于当前 runtime。

DURABLESessionEvent
LIVEAgent handle
RULE不要把两者当同一份状态
SERVICE GROUP · REQUEST

Prompt、Tools 与 LLM 在请求边界会合

System Prompt 汇总插件贡献的 section 和 schema；Tools 给出当前 Agent 可见的注册项；LLM adapter 最后解析 provider、model 与流式调用。

ASSEMBLYctx.systemPrompt
CATALOGctx.tools
ROUTEctx.llm
SERVICE GROUP · EXECUTION

Agent 是接口，Loop 是默认驱动

宿主面对 ctx.agents 创建和驱动 Agent；ctx.agentLoop 是实现这个接口的默认 driver。两者分开，才允许替换 loop 而不重写所有宿主。

04 / 回合执行

回合执行：输入怎样穿过 Turn 与 Step

先把两个计数单位说清：一次用户输入驱动的工作称为 turn；其中一次模型请求及随后的工具调用称为 step。模型看完工具结果再请求一次，就进入下一 step。输入在请求前被拒绝时，一个 turn 也可能没有任何 step。

默认循环先写 turn/start，再领取输入、经过 agent/pre-step 检查。即使输入被拒绝或改为空，也会写结束状态。所以“没有请求模型”仍可能有一条可查的处理记录。

模型请求也不是拿一份可变 messages 数组直接发送。loop 每次从 Session 派生历史，记录流式 chunk，再写聚合后的 assistant message；message 里的 tool-call 统一交给工具 pipeline。这样 UI 可以重放原始流，模型下一步又只读取被 surface 规则选中的历史。

05 / 持久状态

持久状态：SessionEvent 为什么是事实源

界面要重放逐字输出，模型下一次请求却需要完整消息。Session 没有为它们各维护一份独立历史，而是保存一条只追加的事件日志，再从中生成不同视图。assistant/chunk 记录流式片段，assistant/message 记录聚合消息；deriveMessages() 从同一日志生成给模型的内容。压缩对话也要留下事件，说明哪些内容被替换。

Session.append 在写入前先做 lossless JSON snapshot、surface 验证和重入检查。事件一旦进入内存 log，就分配连续 seq 并同步通知观察者；观察者抛错不会把已经接受的事件回滚。这条规则保护事实源不被监听器的偶发失败改写，但持久化 flush 仍由另一个 capability 负责。

“模型可见”不是一个临时数组里的状态。能进入下一次模型请求的内容，必须能从 Session log 重建。固定架构中的核心不变量

06 / 扩展协议

扩展协议：三类 Event 与 Waterfall

想给工具执行加一条规则，不必直接导入默认循环。插件可以监听对应事件，但要先分清规则要保存多久：消息和工具结果需要重开后仍能查到，进入 Session 日志；请求前改写、运行中续跑属于 agent/*；文件或工具的权限规则则挂在各自能力事件上。

事件域保存多久适合表达什么不该拿来替代什么
Session event进入日志，可持久化消息、turn、tool 结果与新增 durable state活 Agent handle
Agent event当前 runtimepre-step、request、status、continuation跨进程事实源
Capability event随插件生命周期policy、adapter、执行前后拦截具体 loop import

agent/pre-step、agent/request 和 tools pipeline 使用 waterfall。listener 若要把控制权交给下一层，必须显式调用 next()；不调用就是短路。这个语义让替换和拦截都很有力，也意味着遗漏一次 delegation 就可能改变整条运行链。

07 / 能力替换

能力替换：接口不变，实现可以换

回到远端读文件。工具需要知道“给一个路径，返回什么”，这由接口定义说明；文件从本机还是远端读取，由具体实现决定；最后，读文件工具把这个能力交给模型。项目把三个角色称为 Definition、Provider 和 Consumer。

换的是 Provider。只要请求和结果约定不变，工具仍调用同一个服务，不必因此改 Agent Loop。只有接口文件、没有实现或没有使用者，还不算接通了一项能力。

这也解释了为什么代码库 package 很多：它不是把每个文件都包装成产品，而是让 service definition、不同 provider 和不同 consumer 能独立组合。判断这一拆分是否值得，不能只数 package；要看 Provider 能否真的替换、Consumer 是否避开具体实现，以及失败语义有没有在 service 层说清。

08 / Agent 作用域

Agent 作用域：Preset、Scope 与 Isolate

一个进程里可以有多个 Agent。全局插件决定进程具备哪些能力，每个 Agent 的 preset 再选择自己用的那一组。preset 提供的服务放进独立的服务命名范围 isolate realm，避免两个会话的实现互相覆盖；Agent 的 scope key 则把工具、角色指令等注册项限定到自己的实例。

这里的 isolate 很容易被安全术语带偏。它隔开的是 Cordis service realm，防止一个 preset 的 provider 泄露到 root 或另一个 Session。它不是操作系统进程隔离，也不自动限制文件、网络与 subprocess。需要安全约束时，还得看 sandbox、fs policy、approval 和具体 Provider。

同一个 Agent，不止一个作用域

宿主通过全局 ctx.agents 找到 live Agent；Agent 的 preset 组合提供 Session 专属 service；Agent scope 再过滤注册项。把三层压成一个“agent config”，会丢掉最重要的所有权关系。

09 / 执行世界

执行世界：换 Provider 会移动什么

文件系统、subprocess、shell、terminal、LSP 和 sandbox 不是六条互不相干的工具链。架构要求共享执行世界的 capability 对齐 Provider。若 FS 指向远端 sandbox，而 Bash 仍调用本机 subprocess，模型会看到一个目录、命令却在另一个世界执行。完整替换必须沿依赖关系一起移动。

能力Definition 关心什么Provider 替换时要一起核对
FS路径、读取、写入与 policy eventworkspace root、artifact 与编辑工具
Subprocess / Shellspawn、signal、exit 与环境cwd、env、sandbox wrapper 与 PTY
Terminal / LSP长生命周期会话与协议是否与 FS、process 位于同一执行世界
Sandbox如何改写和约束 argv它约束的是哪个 process Provider

“Provider 可换”真正有价值的地方，不是换一个 class 名，而是让上层 Consumer 继续使用相同请求语义。反过来，安全属性也不能从接口继承：local、E2B 或其他远端实现必须分别审计 confinement、凭据传递、退出清理和持久化。

10 / 外部接口

外部接口：Headless、SDK 与 ACP

仓库给外部调用者留了三种不同表面。Headless 适合一次 command-in/text-out；SDK runtime 用行分隔 JSON-RPC 暴露完整 Session event 通知；ACP 则面向标准自动化客户端，提供 fresh session、prompt、cancel 和一次性 permission。它们共享 ctx.agents，但结果归属、取消、Session 生命周期和可观察性并不相同。

表面输出中断入口Session 语义
Headless最后一条非空 assistant text无会话级入口每次新建，一个任务后退出
SDK JSON-RPCevent / status / subagent 通知当前协议无 prompt cancel同 runtime 可用 session id 继续
ACPcommitted assistant chunkssession/cancel一连接多 fresh session，不支持 resume

这三种接口不能只按“有没有 JSON-RPC”归成一类。SDK 的 session/prompt 回执只表示消息已持久入队，不标识后来哪条 assistant message 属于它；ACP 等到 Agent idle，却只公开 committed text；headless 直接把进程生命周期当任务边界。接入系统必须选择自己真正需要的语义，而不是再包一层字符串协议。

11 / 变更路径

变更路径：新行为该放在哪一层

固定架构给出的默认顺序很清楚：先问这是不是持久事实，再问是不是运行中拦截，接着看它是否需要可替换 Provider，最后才考虑默认 loop 的生命周期本身是否改变。多数能力可以落在 SessionEvent、agent/*、tools/*、service registry、preset 或 host integration，不必先改 loop。

需求首选落点需要一起补齐
模型下次必须看见的新状态SessionEvent + projection持久化、回放、旧日志读取规则
改写请求或工具执行对应 waterfall eventdelegation、取消、失败语义
新的可替换执行能力Capability seamDefinition、Provider、Consumer
单个 Agent 的不同工具或 personaPreset + scoped registrationisolate、清理与宿主寻址
新的 UI 或外部协议ctx.agents + session/event所有权、权限与 result 归属
Turn/Step 基本生命周期变化Agent Loop架构文档、事件顺序与恢复不变量
12 / 结论与边界

结论与边界：可替换不等于任意组合

DeepSeek Harness 把 Agent 系统拆成了三个互相咬合的平面：Profile 与 patch 决定启动组合；service 与 typed event 决定运行时协作；SessionEvent log 决定哪些事实能够持久、回放并重新进入模型上下文。Agent Loop 是其中一个默认 driver，不是所有扩展都必须穿过的中心。

这套架构最强的约束也来自同一个地方。Provider 能换，不代表安全和性能等价；preset isolate 隔的是 service realm，不是操作系统；事件可回放，不代表外部副作用能撤销；SDK、ACP 和 headless 都能驱动 Agent，不代表它们的取消与结果归属相同。真正可靠的扩展，需要把能力放到正确的事件域和 service 上，再证明相邻生命周期仍能闭合。

固定提交只能回答静态职责

本文没有记录一棵实际 resolved plugin tree，也没有验证并发取消、崩溃边缘 flush、第三方 Provider 组合或 RC 之间的兼容性。要回答这些问题，需要固定 profile 的 --dump-config、带 seq 的 runtime trace、故障注入与版本迁移记录，而不是把架构意图当成运行结果。
