Pi Durable

一个先保存每一步，再把它显示出来的 Agent Harness。

Pi Durable 负责运行与语言模型的对话。每一步都以原子提交写入存储，客户端只显示已提交的数据。 进程停止后，新进程打开同一份存储，就能从最后一次提交继续。下面的每个面板都是可以操作的教学模型。

提交日志 · 一条原子提交序列 条目 任务 文档 提交项
每一步都是一个任务。

任务是一个小型状态机，每走一步就保存一个检查点。模型调用、工具调用和压缩都是任务。

每次变更都是一次提交。

一次提交可以同时添加条目、修改文档、创建任务。存储要么全部保留，要么全部不保留。

客户端只显示已提交的状态。

各个客户端都显示已提交的状态。手机重新连接后，看到的数据与笔记本一致。

译注：原页依据 Pi Durable 1.0.2，保留了原作全部 12 节和交互模型。 这里的进程、数据库、付款、Token 与费用均是浏览器内的教学模拟，不是真实 Harness 或测试回执。 “提交去重”不保证外部动作只执行一次。1.1.0 的源码核验和存储边界另见 AgentLab 研究。
用途

为 Agent 应用保存持久状态

Pi Coding Agent 面向一个人在一个终端里的工作。它把会话存进文件，但正在进行的运行留在进程内存里。 进程停止，运行也就停止，你得再让 Agent 继续。Pi Durable 则面向 Agent 应用： 它们会长时间运行，服务多个用户，在重启后接着工作，还会在运行期间更新代码。 下表把 Pi Durable 与通常将状态保存在内存中的 Agent 循环作了对比。

对比
发生什么 状态保存在内存中的 Agent 循环 Pi Durable
进程停止 正在进行的运行、未完成的回答和队列都丢失了。 新进程打开存储，从最后一个检查点继续。
客户端再次发送请求 Agent 可能收到两次相同消息。 相同的 requestId 会找到存储中已有的提交项。
另一台设备连接 下一次事件到来之前，设备上没有内容。 设备取得已提交的视图，包括流式文本和正在运行的工具。
尝试另一条路径 你得自己复制历史记录。 从某条条目分叉，新分支得到截至该条目的历史。各文档按自己的分叉策略处理。

文档内置文档与提交项

  1. 点击运行。每次提交先进入存储，然后才显示在对话记录中。
  2. 点击重置、运行。当 bash 出现输出时，点击终止进程， 再点击重开并 resume()。运行会自动继续，不必再点运行。
  3. 在 bash 开始之前，为它设置 replay: "safe"，再做一次第 2 步。 这次 bash 会重新执行。read 仍保留默认值 "unsafe"。
  4. 在首次回答过程中，等一次输出写入存储后再终止进程。已提交的部分会留在对话记录中，标记为中止的回答。
  5. 当某段输出还以虚线显示时终止进程，Harness 只会丢失那一段。 一段通常约为 100 ms 的输出；工具输出很大时，这个间隔可能更长。
提交去重 · Exactly-once submission

再次发送，不重复接收

手机发送“部署到预发布环境”。服务器保存消息，开始工作，但回复在网络中丢失了，手机便再次发送。 没有幂等键，Agent 就会部署两次。有了 requestId，第二次提交会找到第一次的提交项。

运行中输入

对话忙着工作时，新的输入怎么办

一次运行尚未结束时，对话处于忙碌状态。这时的新提交项会进入 pi.inbox 文档， Harness 在边界处把它加入对话记录。边界可以是一轮工具调用结束，也可以是整个运行结束，由提交项类型决定。 如果对话空闲，提交项就直接进入对话记录。

运行进行中

pi.inbox排队中

提交项类型 边界 结果
whenBusy: "steer" 当前工具轮次结束 提交项加入当前运行，下一次模型请求会包含它。如果运行先结束，这条 steer 就启动下一次运行。
follow-up 默认 整个运行结束 提交项启动下一次运行。
type: "write" 下一个边界 Harness 添加一条条目，不发送模型请求。
whenBusy: "reject" 无 submit() 抛出 ConversationBusy。

每个边界都会加入所有排队中的 write。默认还会加入一条 steer；运行结束时，再加入一条 follow-up。 想一次加入所有排队中的 steer 或 follow-up，可以在 Harness 设置中使用 steeringMode: "all" 或 followUpMode: "all"。 用 submission.abort() 可以移除排队中的提交项。

任务归属

任务归属与取消顺序

每个任务都有归属，可以归属于一个对话，也可以归属于另一个任务。 任务可以创建子任务，然后提交 waiting 状态。 等待中的任务不运行代码，直到子任务完成。README 中的例子是一笔结账任务， 同时向四张卡扣款。点击按钮，运行不同情况。

example.checkout · 策略 failFast

任务树空闲

事件日志

// "pay" 阶段创建四个归属于结账任务的 Payment 子任务，然后等待。
pay: async (task, runtime, ctx) => {
  await runtime.commit(async (tx) => {
    const payments = [];
    for (const card of task.input.cards)
      payments.push(await tx.createTask(Payment, { card }, { ownership: { kind: "task", taskId: task.id } }));
    return { status: "waiting", checkpoint: { phase: "decide", payments }, on: payments, policy: "failFast" };
  }, ctx);
},
// 每个 Payment 的取消处理函数退回已扣款项。先执行子任务的取消处理。

子 Agent 使用同一种归属模型。子 Agent 是一个归属于工具调用任务的对话。 如果工具调用取消或失败，子对话也会取消。子对话进入空闲状态之前，父对话一直保持忙碌。

带有 { background: true } 的任务构成一道边界。 父级取消后，它拥有的工作仍会继续，也不会让父级保持忙碌。 持久运行的后台子 Agent 就利用这道边界：每个子对话归属于一个锚定任务， 另有一个报告任务把每次回答作为后续输入发给父对话。

应用状态

文档与分叉

文档是带类型的 JSON，Harness 把它与对话记录一起存储。 一次提交可以同时修改文档、追加条目。因此，如果一次提交同时修改了文档和对话记录， 崩溃恢复后，两者仍然一致。每种文档都有一个作用域：会话、对话或任务。 对话文档还可以设置历史记录方式（latest 或 rewindable） 和分叉策略。分叉策略决定新分支的起始值。选择一个分叉点和一种策略，看看区别。

app.todos · 分叉策略：

父对话记录点击条目，从这里分叉 

const Todos = defineDoc<{ items: string[] }>({
  kind: "app.todos", version: 1, scope: "conversation",
  history: "rewindable", // "asOf" 需要 "rewindable"，因为它要读取历史值
  fork: "asOf",  // 新分支从什么值开始

});
await root.commit(async (tx) => { (await tx.doc(Todos, root.id)).items.push("编写文档"); }, ctx);

Harness 内置五种文档：

  • pi.agent：模型、思考深度、扩展、工具、指令和工作目录。 模型保存为提供商与模型 ID，扩展和工具保存的是名称，而不是代码。
  • pi.provider：一个 UUIDv7 会话标识，用于提供商的 Prompt 缓存。
  • pi.live：当前运行、流式回答、正在执行的工具，以及正在进行的压缩。
  • pi.inbox：排队中的提交项。
  • pi.usage：各个模型的 Token 用量与费用，以及会报告用量的工具的用量与费用。 失败和取消的尝试也计入其中。

分叉会获得新的提供商会话标识。

上下文管理

后台压缩

对话变长时，压缩任务会总结较早的条目，并在对话记录末尾追加一个 pi.compaction 条目，指向第一条保留的条目。 此后，模型收到摘要，而不是这个保留点之前的原条目。压缩期间，Agent 继续工作。 旧条目仍保存在存储中，因此工具还能读取它们。移动滑杆，改变 Token 数量。

上下文窗口：200,000 Token
已用 Token后台压缩区间（backgroundTokens）预留区间：下一次请求等待（reserveTokens）

状态观察

客户端显示已提交的状态

界面的所有数据都来自已提交的状态。 viewState() 提供实时的只读视图。 watch() 提供相同的视图，以及每次提交的操作，逐次调用回调。 较晚连接的客户端会拿到当前视图，Harness 不会重放旧提交。

一个对话，多个客户端

较慢的 watch 最多保留 100 帧尚未交付的数据。 达到上限后，Harness 用包含最新完整视图的一帧替换这些帧。 Harness 提交部分回答和工具输出的频率不超过每 100 ms 一次；工具输出很大时，间隔会更长。 watchEvents() 从提交中生成编程 Agent 事件，例如 message_update 和 tool_execution_start。

存储

存储后端

使用 SQLite 时，Harness 只把当前工作所需的数据留在内存中，较早的消息留在磁盘上， 直到需要时才读取。JSONL 后端则把全部记录保留在内存中。 同一份存储一次只能由一个进程使用，存储本身不会阻止第二个进程访问。
